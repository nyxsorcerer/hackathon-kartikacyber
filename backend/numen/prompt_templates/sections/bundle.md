## Finding bundle

For cve_analysis, finding_artifacts, and commit_analysis with a Vulnerability fix or Vulnerability introduced Verdict, write every required bundle file at these exact output-relative paths: {{ required_files | join(", ") }}. Pin the actual vulnerable upstream version, immutable source and dependencies in application.lock.json; do not label a fixed checkout or a synthetic substitute as the vulnerable application.

That lock is read at its top level, not from a nested object: "version" must be the vulnerable release, "source_ref" must be the full immutable revision it was taken from (hexadecimal, or omitted in favour of "local_inputs"), "local_inputs" maps each application file you bundled to why it is there and every one of those paths must exist under vulnerable-app/, and every entry of "images" must be asset-monitor-lab:0.1.0 or pinned by @sha256. Anything else you want to record can sit beside those keys.

The lab verifier rebuilds vulnerable-app/Dockerfile as its own project and then runs exactly one container from it. It builds with the classic builder and with network, so build the application the way it is really built: RUN is accepted and so is multi-stage, which means dependencies are installed at build time rather than vendored by hand. FROM must name asset-monitor-lab:0.1.0, scratch, an earlier stage of your own file, or any image pinned by @sha256, because a reproduction has to stay rebuildable; a floating tag is refused. asset-monitor-lab:0.1.0 is Debian bookworm with Python 3.12, curl, git, unzip and CA certificates, running as root by default, and nothing else: install the application's runtime, web server and database with apt-get in your Dockerfile. COPY and ADD sources stay inside the bundle unless they carry --from, which must name one of your own stages or a digest-pinned image. Build mounts and privileged build flags (--mount, --security, --network) are refused. Bundle files arrive owned by root with no execute bit, so always name the interpreter (CMD ["sh", "/app/start.sh"]). The verifier supports digest-pinned bases, networked dependency installation, RUN and multi-stage Dockerfiles under the same declared build contract.

Keep the bundle itself declarative so the lab verifier can rebuild it, and put everything the bundle needs under vulnerable-app/ because your workspace is destroyed with the run.

Your outputs are limited to 8 MB, so do not copy the application into the bundle and never ship a reduced copy of it instead. The lab build has network: fetch the application during that build at its immutable revision (a git clone checked out at the commit, or an archive verified against its digest) and bundle only what you wrote yourself.

Exactly one container runs, with no sidecars and no compose, so a database belongs inside that image and is started by your entrypoint before the application. The container has a writable root filesystem, its image's own user, an ordinary capability set, internet access, 2 CPUs, 6GB and 4096 processes, inherits no environment, and must serve port 8080. It has the run's whole budget to become ready, so an entrypoint may initialise a database, import a schema and finish a first-boot install.

poc.py runs in a separate container that has no internet, so an observed proof must come from the application rather than from the network. It is staged read-only and run as `python -I /workspace/inputs/poc.py` with the working directory /workspace, which is a different writable filesystem: one file, standard library plus httpx only, locating any data it needs from Path(__file__).parent rather than the working directory, writing only under /workspace, reading its target from the TARGET_URL environment variable, polling it until it answers because the application may take minutes to initialise, verifying the observed proof and exiting nonzero on failure. Reports and startup instructions must explain prerequisites, impact, reproduction and limitations.

If the vulnerable application cannot meet that contract, say so in report.md with the specific prerequisite it needs instead of shipping a bundle the verifier must refuse. If the supplied evidence cannot support a genuine vulnerable bundle, preserve the report and explain the missing prerequisites instead of inventing files; an incomplete bundle is kept as a draft.

The bundle is a draft: a Lab verifies it after the Operator's Approval, so never claim it reproduces.
