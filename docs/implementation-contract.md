# Implementation coordination contract

This is the shared contract for the first complete implementation, authorized by the user's “Build it” instruction. Preserve the PRD's outcomes and all three coding-agent choices. Each owner can make reversible local implementation choices within this boundary. Coordinate contract changes with the orchestrator before changing a consumer-facing shape.

## Ownership

- Backend agent: `backend/`, backend tests, migrations, domain services, scheduler/worker, API/security/persistence. Do not edit `runner/`, frontend, or root deployment files.
- Frontend agent: `frontend/`, its tests and package manifests. Do not edit backend, runner, or root deployment files.
- Runtime agent: `runner/`, root Dockerfiles/Compose files, runtime tests, and pinned agent/plugin/skill manifests. Do not edit frontend or backend modules.
- Orchestrator: root Makefile, bootstrap/backup helpers, integration fixtures/journey, documentation, cross-owner integration and final checks. When a correction belongs to another owner's active files, send it back to that owner.

All agents share the workspace. Preserve other owners' edits and adapt to their work. Read the PRD, design, and UI specification as governing context; these instructions settle serialization only.

## API

All paths below begin with `/api`. A session cookie authenticates requests. `GET /auth/session` returns `{authenticated: boolean, username?: string, csrf_token?: string}`. Login accepts `{username: "admin", password: string}` and returns the authenticated session shape. Browser mutations send `X-CSRF-Token` after login. Login allows 10 attempts per client address in 60 seconds, then `login_rate_limited` (429, retryable). An Approval (A15) is a mutation whose body carries `{password}`, checked against the Operator's password hash on that request alone: there is no re-authentication window, and a missing, empty or wrong password is refused with `approval_refused` (403, so the UI keeps the Operator signed in), also straight after a good Approval. Approvals are rate-limited like login in their own bucket (`approval_rate_limited`, 429), the password is stored and logged nowhere, and each granted one records an `actions` row `{action: approved, approved, ...}` on what it approved. Structured errors use `{code, message, fields?: object, retryable?: boolean}` with JSON; lists use `{items: array, next_cursor: string|null}`. Responses expose no secrets. IDs are strings; times use UTC ISO-8601.

Every HTTP response, the dashboard and its assets included, passes through `security.SecurityHeaders` (A15), which sets `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'` (`img-src data:` is the select arrow's SVG in `styles.css`), `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`, replacing any copy a route set. FastAPI's `/docs`, `/redoc` and `/openapi.json` are disabled: Swagger UI needs inline script, and nothing uses it. The built `index.html` loads only `<script type="module" src>`, and `frontend/src/csp.ts`, imported first, sets Zod's `jitless` so it never probes for eval. The dashboard is published on `127.0.0.1:${NUMEN_PORT:-8788}` only, and every other published port is bound to `127.0.0.1` too (`backend/tests/test_deployment.py`). The frontend renders diffs, reports, agent output, Transcripts, commit messages and served-content values as React text; Markdown reports use `react-markdown` without `rehype-raw`; `eslint.config.js` refuses `dangerouslySetInnerHTML`, `innerHTML`/`outerHTML` writes and `insertAdjacentHTML`.

### Domain records

Application fields: `id`, `asset_name`, `asset_url`, `product_kind`, `product_name`, `monitor_interval_seconds` (300 to 315,360,000: at least 5 minutes, at most 10 years; shown and entered in minutes, hours or days), `monitor_enabled`, `archived`, `source_generation`, `last_check_at`, `next_check_at` (both set by the scheduler and Check now), `repositories`, `unresolved_dependencies` (the active Own link's, else `[]`), `version` (latest observation or null), and `config`.

A repository is stored once per source URL and linked to each Application that uses it. GitHub URLs are normalized to `https://github.com/{owner}/{repo}` in lower case, without `.git` or a trailing slash; a WordPress.org plugin is `https://plugins.svn.wordpress.org/{slug}`. Its slug, ref and path are fixed when the row is created, so Applications sharing a URL share them. `repositories` lists the Application's links, the Own one first and then in the order they were added (by link id when two were added at the same instant), removed ones included: `repository_id`, `role` (`own` or `upstream`), `enabled`, `removed_at`, `locked_version`, `locked_version_source` (`manifest`, `operator` or `deployed`), `release_branch`, `release_branch_status`, `packages` (the packages a derived Upstream link stands for, such as `npm:react`; `[]` for hand-added and Own links), `source_kind`, `source_url`, `plugin_slug`, `source_ref`, `source_path`, `cursor` (GitHub head or SVN revision), `baseline_revision` (the Baseline: the head when the repository was first checked), `last_check_at` (last successful check), `last_error` and `push_webhook` (B02: null, or for an Own link with a Push webhook `{created_at, last_accepted, last_refusal}`; never its push id or secret). An Application has at most one active Own repository, which must be on GitHub, and may have none. Commits, snapshots, cursors and Triage belong to the repository, so a shared repository is polled and triaged once. Its new commits are triaged with the first linked Application that is not archived, links it enabled, and has Triage on; with none, they are not triaged. A GitHub repository is read only with a token from an Account with provider `github` (fine-grained, read-only: Contents and Metadata). Without one, the scheduler queues nothing for it and sets `last_error` to `github_token_required`; Check now queues the check, which fails with that code before any request. Every GitHub poll sends `If-None-Match` with the ETag of the last commit list; a `304` returns before any compare or commit request, advances neither cursor nor ETag, imports nothing and queues nothing (the check's result has `not_modified: true`). An Upstream GitHub repository also watches the Release branch of each Locked version that an enabled, not removed link of a not archived Application uses. The first branch that exists among `{major}.x`, `{major}.{minor}`, `release-{major}` and `v{major}` (the major and minor of `^v?(\d+)(?:\.(\d+))?`) is the Release branch; a check resolves a Locked version once, with `GET /repos/{repo}/branches/{name}`, and again only after it changes. `release_branch_status` is null for an Own link, a WordPress repository or no Locked version, `pending` until the next check resolves the current Locked version, `matched`, or `unknown` when no candidate exists (the UI says "release branch unknown"); then only the default branch is watched. Each Release branch keeps its own cursor and ETag in the repository's watched branches, is baselined at its head when first watched, and its new commits are imported with `branch` set to its name; a revision already imported from another branch is not imported again. A check is `not_modified` only when every watched branch answers `304`. Own and WordPress repositories watch their default branch only. WordPress.org plugins keep the SVN revision cursor and need no token.

The Application's source repository is its earliest linked repository that is not removed, whatever its role or on/off state; for a migrated Numen Program it stays the former source after an Own repository is added. Version recipes, version checks, audit contexts, CVE analyses and finding artifacts read it and fail with `repository_required` without one. `source_generation` is the Application's generation of that source: it advances only when the source repository's link is removed (the next earliest link then becomes the source), which clears the active recipe and the CVE cursor and marks audit contexts stale. Adding a repository or turning a link on or off changes neither.

Upstream repositories are derived from the Own repository by a `derive_upstreams` job. A check of an Own repository queues one, with idempotency key `derive:{application id}:{head}`, after its Baseline (when the link was never derived) and whenever an imported commit's `dependency_manifest` Pre-filter flag shows that it changed a manifest or lockfile; linking an Own repository that another Application has already checked queues one at once. The job reads `package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `composer.json` and `composer.lock` at that revision under the repository's path (`GET /repos/{repo}/contents/{path}?ref=`, raw). Direct dependencies are `dependencies`, `devDependencies` and `optionalDependencies` in `package.json` and `require` and `require-dev` in `composer.json`, without platform packages (`php`, `ext-*`, `lib-*`, `composer-*`). Versions come from the lockfile: `package-lock.json` v1 `dependencies` or v2/v3 `packages["node_modules/{name}"]`, `pnpm-lock.yaml` `importers["."]` (v6+, with the peer suffix removed) or its top-level maps (v5), `yarn.lock` v1 or Berry (the entry for the direct range, else the first), and `composer.lock` `packages` and `packages-dev`. Each package is mapped to its GitHub repository through `{npm registry}/{name}/{version}` (`latest` without a locked version, scoped names as `@scope%2Fname`) and its `repository` field, or for Composer through the `composer.lock` entry's `source.url`, else `{packagist}/p2/{vendor}/{name}.json` (the entry for the version, else the newest). The registry base URLs are `https://registry.npmjs.org` and `https://repo.packagist.org`; in test mode `NUMEN_NPM_REGISTRY_URL` and `NUMEN_PACKAGIST_URL` replace them. Packages mapped to one URL share one Upstream repository, found or created by URL (a derivation or request that creates it at the same time reads the other's row), and one link per Application. A new link is on at the first derivation and off afterwards, with the first package's Locked version recorded as `manifest`. An existing link gets the new `packages`, a new Locked version unless its source is `operator` or `deployed`, and is restored if it was removed. A derived link whose packages are all gone is marked removed and keeps its commits; hand-added links (no `packages`) and the Own link are never removed by derivation. A removed link that is added again by hand is restored as a hand-added link: its `packages`, `unresolved` and derived revision are cleared. A package with no repository metadata, a repository outside GitHub, a registry `404` or a registry body that is not its JSON object is listed in the Own link's `unresolved` (`unresolved_dependencies`: `{ecosystem, name, version, reason}`). A manifest that is not valid JSON or YAML, or is valid but of the wrong shape, fails the job with `invalid_manifest` and changes nothing; a failed derivation sets the Own repository's `last_error`. A derivation that added repositories sets `next_check_at` to now, so they get their Baseline on the next scheduler tick.

Push webhooks (B02, ADR-0006; models `PushWebhook` and `PushDelivery`, migration `c9d0e1f2a3b4`). Records:
- `push_webhooks` `{id, repository_id, push_id, secret, created_at, last_accepted, last_refusal}`, unique on `repository_id` (one per repository) and on `push_id` (32 lowercase hex characters). `secret` is the Push webhook secret encrypted with `Vault(NUMEN_INGRESS_KEY)`. `last_accepted` is `{at, event, delivery_id}`, with `event` `push` or `ping`, and `last_refusal` is `{at, reason}`; both are null until the first. Refusal reasons are `wrong_signature`, `event_not_accepted`, `delivery_id_missing`, `body_too_large` and `rate_limited`.
- `push_deliveries` `{id, push_webhook_id, delivery_id, body_sha256, received_at, processed_at}`, unique on `delivery_id` and on `body_sha256`. The nudge sets `processed_at` and prunes rows older than 7 days, so a body is unique among the last 7 days' deliveries.

The nudge (`domain.nudge_push_deliveries`, B02 and decision 16) runs in its own transaction in each 15 s scheduler loop, right after `schedule`. It first deletes the deliveries whose `received_at` is more than 7 days old. Then, for each Push webhook with deliveries whose `processed_at` is null, it reads those deliveries' ids and takes the first Application of `linked_applications` whose link to the repository is Own and in use (`in_use`: link enabled and not removed, Application not archived; `monitor_enabled` is ignored, as for Check now):
- With no such Application, the deliveries are marked processed and nothing is queued.
- With no GitHub read token (`domain.github_token`), the repository's `last_error` is `github_token_required` and the deliveries are marked processed, as A02's rule has it for the scheduler.
- Otherwise it locks the Application, then `active_source_check` locks the Repository. A queued check is reused, and with none it queues `source_check` with `repository_input(repository)`, the input `schedule` and Check now queue. In both cases the deliveries are marked processed (`processed_at` is now). A running or cancelling check leaves them unprocessed, so the first loop after it ends queues exactly one more.
- It never sets the Application's `next_check_at` or `last_check_at`, so scheduled polling keeps its interval.

Source checks are queued under the Repository row lock (B02, decision 16). `domain.active_source_check` first runs `SELECT repositories.id ... FOR NO KEY UPDATE`, held until the transaction ends, then looks for the repository's queued, running or cancelling `source_check`. `schedule`, Check now (`api.check_application`) and the nudge all look there before they queue one, so the three never queue two. The lock order is always the Application, then the Repository:
- `schedule` takes its due Applications `FOR NO KEY UPDATE SKIP LOCKED`.
- `check_application` and the nudge lock their Application `FOR NO KEY UPDATE` first.
- A worker's `source_check` holds its Repository `FOR UPDATE` while it inserts Jobs of the Applications linking it. Those inserts take a key-share lock on the Application rows, which `FOR NO KEY UPDATE` allows, so they never deadlock with the scheduler.
- A transaction that queues for several repositories locks them in link order. Two such transactions crossing over shared repositories can deadlock, and Postgres then aborts one of them.

`domain.links` orders by role (Own first), then `created_at`, then link id; `linked_applications` orders by `created_at`, then link id.

`config` contains `triage_mode` (`disabled`, `jev`, `pi`, `claude`; `codex` is refused with `validation_error` "Triage on Codex is refused until a no-tools restriction has been verified for it", though a configuration stored with it still loads), `profiles` keyed by operation, `cve_selectors` (list of typed selector objects), `cve_min_score`, `cve_versions` (subset of `3.0`, `3.1`, `4.0`), `cve_auto_analyze`, `active_recipe_id`, `monitor_interval_inherited`, `version_scheme`, `version_monitor_enabled`, `asset_origins`, `jev_connection_id`, and `jev_model_id`. Application `latest_version_check` supplies the latest failure independently of the last successful `version`. Agent operations are `commit_triage`, `commit_analysis`, `version_recipe`, `audit_context`, `cve_analysis`, `finding_artifacts`, and `patch_drafting`. A `commit_triage` profile on Codex, whether a default profile, an Application profile or the one an import resolves, is refused with `triage_codex_unsupported` (422); an import blocked that way records the commit as `blocked` with that reason. A `commit_analysis` or `cve_analysis` profile on Codex is refused the same way with `analysis_codex_unsupported` (422, "Analysis and CVE analysis on Codex are refused until a Codex mode without a shell has been verified"), because Codex always has a shell and those operations get only a read-only checkout and a write-only output directory (ADR-0004); a queued job with such a profile fails with that error, and an automatic Analysis is `blocked` with it. A `patch_drafting` profile on Codex is refused with `patch_codex_unsupported` (422, "Patch drafting on Codex is refused until a Codex mode without a shell has been verified") for the same reason.

Profile fields: `agent` (`pi`, `claude`, `codex`), `connection_id`, `model_id`, and nullable `reasoning_effort`. Server resolves defaults and validates every combination. These fields are identical for all operation submissions. Runtime receives a resolved provider/auth mode separately.

Commit fields: `id`, `repository_id`, `application_id` (the first Application that uses the repository: not archived, its link on and not removed; else the first that ever linked it. It is the context of commit pages and owns the commit's one Analysis; the Findings that Analysis opens are per affected Application), `revision`, optional imported `parent_revisions`, `message`, `author`, `committed_at`, `url`, `files`, `diff`, `diff_complete`, `prefilter`, optional `backfill` (true for a commit imported by a Backfill), optional `branch` (the Release branch it was imported from), `triage_status`, `triage_result`, `review_decision`, `verdict` (the newest Analysis's Verdict, null until one completes), `exposures` (one per Application an Upstream Verdict on the commit was checked for: `{application_id, application_name, verdict, state, reason, locked_version, tag, target}`; see Exposure below), `analysis_state` (null, or the latest Analysis job's `{status, job_id}` while `queued`, `{status: completed, analysis_id}`, or `{status: failed|timed_out, job_id, error}`; an automatic Analysis that has not started is `{status: waiting_for_cap, since, cap: application|account}` or `{status: blocked, error}`), and `analyses`. A diff is capped at 60,000 characters per file and 2 MiB in all; a capped diff, or one whose file patch the source omitted, has `diff_complete: false`. `prefilter` is the Pre-filter result recorded at import, `[{rule, paths}]` for the rules the change matches: `dependency_manifest` (`package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `composer.json`, `composer.lock`), `package_scripts` (a changed `package.json` line inside the `scripts` object as the hunk shows it, the `scripts` line itself, or a changed npm lifecycle hook: `install`, `prepare`, `prepublishOnly`, or `pre`/`post` with `install`, `pack`, `publish`, `start`, `test`, `stop`, `restart`, `version` or `shrinkwrap`), `ci_workflow`, `minified_or_obfuscated` (`*.min.js`/`*.min.css`, an added line over 1,000 characters, `_0x…` identifiers, `eval(atob(`, `String.fromCharCode(`) and `auth_or_crypto` (authentication, session, token, cryptography, signing, secret, key, permission and CSRF paths). It never changes `triage_status` or `review_decision`. Triage is one agent run with no tools and a 120-second deadline (`TRIAGE_SECONDS`), never a Herdr session. Its prompt carries the change as `facts.commit` (`message`, `author`, changed `files` paths, `diff` capped at 100,000 characters (`TRIAGE_DIFF_CHARS`) as its JSON in the prompt counts them, escapes included, and `diff_complete`, which is false for an incomplete or truncated diff), with no input files. The facts are appended as JSON with non-ASCII characters unescaped, so no diff pushes the prompt past the runner's 262,144-character bound. The runner returns the agent's raw reply as `{reply}`, and the broker accepts nothing else from a Triage run; application code takes the JSON object in it (from the first `{` to the last `}`, so a code fence or prose around it is tolerated), replaces configured secrets with `[redacted]`, and validates it against the Triage schema: `decision` (`security_candidate`, `unrelated`, `insufficient_context`), `title` (1–300 characters, a potential-issue title) and `reason` (1–2,000 characters), nothing else. Jev triage keeps its typed answer, which adds `change_kind`, `issue_type`, `confidence` and probabilities. Complete unrelated triage sets dismissed; uncertain input stays pending, and an unrelated decision on an incomplete diff becomes `insufficient_context`. A failed Triage run (a reply that fails the schema, a timeout, a provider error) sets `triage_status: failed` and `triage_result: {error, reason, attempt}` with no `decision`, so it is never read as unrelated, and leaves `review_decision` unchanged. Unless it was cancelled, lost its lease or its input changed, the worker queues the same Triage again with `attempt` n+1 and the same profile, not before n minutes, up to three attempts (`TRIAGE_ATTEMPTS`), and records `retry_job_id`. Each Triage run, agent or Jev, is stored as a Transcript: a `transcripts` row (`id`, `job_id`, `kind: triage`, `subject_id` (the commit), `data`, `size`, `created_at`) whose `data` holds the `prompt` and `reply` (Jev: the `request` body, which never holds the key, and the `response`) with configured secrets replaced by `[redacted]`, `status` (`completed` or `failed`), the `error` of a failed one, the `profile`, `run_id` and the runtime `execution` provenance. A failed run's Transcript is kept. Configured secrets are every Account credential (the Analysis keys and the GitHub read and write and NVD tokens among them), the Discord webhook URL and key, the vault key, every Push webhook secret and `NUMEN_INGRESS_KEY` (with a Push webhook stored and no `NUMEN_INGRESS_KEY`, `all_secrets` raises `vault_unconfigured` rather than skip one), and the run's own credentials (`all_secrets` plus the job's), each also replaced in its standard base64 form; the Operator password is stored only as a hash and never reaches an agent. Each completed commit, served-content and CVE Analysis also keeps an Analysis Transcript (A14): right after its run, before the fence, `Workflows.session_transcript` reads the broker's final session archive (`GET /internal/runs/{run_id}/session`: each native JSONL record in order, rendered as its role and content without its ids, timestamps or usage, then `=== Latest terminal view ===` and Herdr's screen) and redacts it the same way; with the Verdict, `store_analysis_transcript` publishes it as `transcript.txt` in an Artifact of `resource_type: transcript` (resource id the Transcript's id, manifest `{analysis_id, run_id}`), and only then adds a `transcripts` row `kind: analysis`, `subject_id` the commit, the served-content change, or `<application id>:<CVE id>` for a CVE Analysis, which runs per Application, `data: {status: completed, analysis_id, run_id, revision}`. A run whose session cannot be read (no session, a native backend, the broker down) records a `transcript_unavailable` job event, and one that cannot be stored (`artifact_too_large` over 64 MiB, `secret_in_artifact`) a `transcript_not_stored` event; neither fails the Verdict. Each Transcript records its `size` in bytes (a Triage one's `data` as JSON, an Analysis one's `transcript.txt`); migration `a7b8c9d0e1f2` backfills it for existing rows and indexes `subject_id`. Retention (A14, `domain.prune_transcripts`, which the scheduler runs at start and then hourly through `scheduler.prune`) deletes a Triage Transcript after 30 days, and while the Triage Transcripts together pass 256 MiB (`TRIAGE_TRANSCRIPT_BYTES`) the oldest go first, whether or not a Finding is about its subject. It keeps an Analysis Transcript whose `subject_id` is among `domain.finding_subjects` of all Findings, and deletes any other after 30 days with its `transcript` Artifact rows, and its revision folder is removed (`artifacts.remove_revisions`, as Finding deletion does) once that is committed. A deleted Finding's Analysis Transcripts age out the same way. Analysis (`commit_analysis`) returns exactly one Verdict: `verdict` (`Vulnerability fix`, `Vulnerability introduced`, `Malicious change`, `Security hardening`, `Unrelated`, `Insufficient context`; `schemas.VERDICTS`), `confidence` (`low`, `medium`, `high`), `title` (1–300 characters), `summary`, `evidence`, `open_questions`, `before_after`, `affected_behavior`, `vulnerable_ref` (a full revision, required with at least one evidence item for Vulnerability fix and Vulnerability introduced) and optional `addresses`: up to 50 commit SHAs (7–64 hex characters) or advisory ids (`CVE-…`, `GHSA-xxxx-xxxx-xxxx`, or another database's `PREFIX-id`) that the change addresses, kept in the result for linking to Findings. Nothing is run, so the result has no reproduction. Drafts are output files: report.md always, the Proof bundle (`artifacts.REQUIRED`) for Vulnerability fix and Vulnerability introduced, and `detection-rule.yar` (a YARA Detection rule) for a Malicious change, all saved with the analysis artifacts. A Malicious change also returns `indicators` (`files`, `hosts`, `urls` and `commands`, each up to 100 strings of 1–240, 1–253, 1–2,048 and 1–2,000 characters; no hashes, which application code computes) and `reachable_secrets` (up to 50 names of 1–300 characters, never values); the schema requires both for that Verdict only. Its review decision is `candidate` for Vulnerability fix, Vulnerability introduced and Malicious change, `dismissed` for Security hardening and Unrelated, and `pending` for Insufficient context, which puts the change in the Review queue. The opening Verdicts (`domain.OPENING_VERDICTS`: Vulnerability fix, Vulnerability introduced, Malicious change) open one `commit`-source Finding in each affected Application (`domain.affected_applications`: every Application whose link to the repository is on and not removed, the Application not archived; an Own link always counts, and an Upstream link counts unless its Exposure is `not_exposed`). In each such Application the change is linked to the Findings, in any state, that its `addresses` name (see Finding fields): a Vulnerability fix linked that way opens nothing, while a Vulnerability introduced or Malicious change fixes nothing and opens its own Finding as well. Vulnerability fix and Vulnerability introduced publish the drafted bundle to each such Finding that is Open or Confirmed, once per Application; a Dismissed or Remediated one keeps the evidence and bundle it was closed with, and `target_applicability` is never reset. An incomplete bundle is published as a draft (`artifact_state.status: draft`) and the job still succeeds. A drafted `vulnerable_ref` that fails validation (`invalid_finding_revision`) publishes no bundle: the Findings still open and alert, the job succeeds, and the error is kept as `bundle_error` in the Analysis and job results. A Malicious change publishes a static Proof and a cleanup report to each such Open or Confirmed Finding instead (see Finding fields). `workflows.check_verdict(result, served_content)` refuses a served-content Analysis that returns Vulnerability fix or Vulnerability introduced with `verdict_not_allowed` (422), which fails the job; commit Analysis may return all six. Analysis and CVE analysis request a 30-minute deadline (`timeout_seconds` 1800, `ANALYSIS_SECONDS`). A failed or expired Analysis sets `analysis_state` to `failed` or `timed_out` (error `timeout` or `runtime_timeout`) and leaves `verdict` and `review_decision` unchanged, so an expired deadline never reads as Unrelated. Migration `9f7a8ba3c2d7` rewrote Numen's stored commit analysis results (analyses and jobs) from its `category` to a `verdict` by the PRD's AC-A04 table, with `confidence: unknown` and Numen's confidence object kept as `numen_confidence`; Numen's other fields stay as they were, and each commit's `verdict` is its newest analysis's. Late manual review actions take precedence over automatic review-decision updates. The commit pages show `verdict` with its newest analysis's confidence (`unknown` for a migrated one), `analysis_state` as Queued, Waiting for cap (with its cap), Timed out after 30 minutes, Blocked or Failed (with the error message), and `prefilter` beside the Triage result even when Triage rejected the change; a `failed` or `blocked` Triage reads as Triage failed or Triage blocked, never as unrelated. The Review queue is a Show filter of the commit list (`verdict` Insufficient context, `review_decision` pending) and a dashboard panel fed by `review_queue`.

Exposure (A05, `backend/numen/exposure.py`, table `exposures`, migration `c2b3d4e5f6a7`): before its fence, an Analysis whose Verdict opens Findings computes the Exposure of each in-use Upstream link of the repository, never of an Own one. For GitHub, `Sources.github_mirror` makes a blobless bare clone (`git clone --bare --filter=blob:none` from `https://github.com`, or `NUMEN_GITHUB_GIT_URL` in test mode) in a temporary directory: nothing is checked out, git runs with no system or user configuration and no hooks, `GIT_ALLOW_PROTOCOL` is `https` (the base URL's scheme in test mode), and the read token reaches git only as `GIT_CONFIG_*` `http.<base>/.extraheader` (Basic `x-access-token`), never in its arguments; clone and each command have a 300 s timeout. The commit's backports are the commits with its `git patch-id --stable` that it does not reach among the newest 1,000 non-merge commits of the Release branches in `watched_branches` that the default branch (or `source_ref`) does not reach, or, for a commit the default branch does not reach, of every watched branch. A backport scan that fails or times out leaves the commit's own containment, so a release that only a backport fixes reads as exposed rather than every Exposure as unknown. The Locked version's tag is the first existing tag among `v{version}`, `{version}` and `{package}@{version}`, where the package is the link's first `packages` entry without its ecosystem prefix (none for a hand-added link) or the plugin slug. The tag contains the commit when it reaches the commit or a backport. A Vulnerability introduced or Malicious change is `exposed` where the tag contains it and `not_exposed` where it does not; a Vulnerability fix is `not_exposed` where the tag contains it, `exposed` where it does not, and `exposed` with reason "no release contains the fix yet" at every Locked version while no tag contains it. No Locked version, no matching tag, or a repository or tags that cannot be read (`mirror_unavailable`, `github_token_required`, `svn_error`) give `unknown`, which counts as exposed. For a WordPress plugin, `Sources.svn_tags` reads `svn log -v --xml` of `tags/`: a tag copied from trunk counts at its `copyfrom-rev`, one added without a copy at the revision that added it, and it contains every revision at or before that. Each Exposure also carries `target`, found even without a Locked version: for a Vulnerability fix the first release (by tag creatordate, or copy revision for SVN) that contains it, otherwise the newest release that does not (`{tag, version}` of a tag that names a version, or null). Semantic-version order is never used. After the fence, `domain.record_exposure` upserts one row per (Application, commit) with `verdict`, `state` and `data` `{reason, locked_version, tag, target, analysis_id}`; a repeat Analysis updates it. A `not_exposed` Application gets nothing else: no link, Finding, Proof, Remediation PR, Alert or Detection rule job (AC-A12); the Exposure is shown on the commit only. An Upstream link with no Exposure row counts as exposed, which matters only for linking a Verdict that opens no Finding: an Analysis leaves out each Application whose in-use Upstream link it read no Exposure for (one added or turned on while it ran), and queues its `exposure_check`, which runs its Playbook. Exposure is recomputed by an `exposure_check` job (input `repository_input(repository)`, on the Application) that `domain.queue_exposure` queues for an in-use Upstream link, unless one is already queued for that (Application, repository) or the repository has no commit of its current generation with a Verdict that opens a Finding: when `derive_upstreams` adds, restores or re-locks a link, when `POST /applications/{id}/repositories` adds or restores an Upstream link, when `PATCH /applications/{id}/repositories/{repository_id}` changes `locked_version` or turns the link on (a link that was off missed the Verdicts stored meanwhile, such as a later dependency, which starts off), when `PATCH /applications/{id}` restores an archived Application (each of its Upstream links), and when an Analysis finds after its fence that a link's Locked version is no longer the one its Exposure used, or that a link it read no Exposure for is in use. A 304 queues nothing. The check opens one mirror (or reads the SVN tags) and recomputes the link's Exposure to the latest Analysis of each such commit. After its fence it records each one, and for each that is `exposed` or `unknown` with no Finding of this Application it runs that Analysis's Playbook then, as the Analysis would have: the Finding with its one Alert, and the drafted bundle, or the static Proof with its `detection_rule` job and cleanup report. A Finding the Application already has is never re-published, and a change to `not_exposed` leaves Findings as they are. It records nothing when the link went out of use or was re-locked while it ran, and skips a commit whose Verdict changed. For a Finding the Application already has, open or confirmed, whose Exposure was not `not_exposed` and whose `target` was unknown before, it runs the Remediation PR step (`workflows.remediation_step`). A source check that is not a 304 queues an `exposure_check` for each Application with an `exposed` or `unknown` Vulnerability fix Exposure of the repository without a `target` whose Finding is open or confirmed, so a newly tagged fix release drafts its bump; a tag added without a new commit is seen at the next such check.

Deployed version check (A06, A11; `Workflows.deployed_checks`, `domain.apply_deployed_check`): an Own-repository Vulnerability fix Finding (Open or Confirmed) is checked against the version that Numen's version fingerprinting detected. A `version_check` checks every such Finding of its Application before its fence, and an Analysis checks the Finding it opens against the Application's latest observation. The check reads `serving_fix` when the Own repository's release tag for the detected version (`v{version}`, then `{version}`, from its read-only mirror) contains the fix commit or a backport of it with the same patch-id, and `before_fix` when it does not. It reads `unknown`, never a guess, with its reason, when no version check has run, when the recipe reads a repository other than the Own one, when the observation is `ambiguous`, `unknown` or `error`, when no tag matches the version, or when the tags cannot be read. The Finding stores it as `deployed_version_check`; `serving_fix` moves it to Remediated with cause `{by: deployed_version, observation_id, version}`. Only this caller makes that transition, and only for an Own Vulnerability fix: `transition_finding` does not check Verdict or role.

Advisory check (A09; `backend/numen/advisories.py`, migration `d3f4a5b6c7e8`). An `advisory_check` job `{repository_id, source_ref}` (a long kind) reads `domain.advisory_repository`, the Own repository else the source repository, at its head, and fails with `input_changed` (409) when that repository changed since it was queued. It is queued once per UTC day for each monitored, unarchived Application whose repository has a head (`domain.schedule_advisory_checks`, called from `scheduler.main` after `domain.schedule`; key `advisory:{application id}:{YYYY-MM-DD}`), by `Workflows.queue_derivation` for each unarchived Application whose `advisory_repository` is the polled repository (its Own repository, else its source repository), with its link not removed, when a commit imported after the Baseline touches a pin file (`advisories.pin_file`: a manifest, lockfile, `.nvmrc` or Dockerfile; key `advisory:{application id}:{head}`; the Baseline queues none), and by `POST /applications/{id}/advisory-checks`. `advisories.collect` reads:
- runtime pins `{name, version, field, source, reason}`: each Dockerfile `FROM` of the official `node` or `php` image at any depth (`field: dockerfile`, plus `image` and `tag`; `--` options and earlier stage names are skipped), and `.nvmrc`, `package.json` `engines.node` and `composer.json` `config.platform.php` at the source path (`nvmrc`, `engines`, `platform`);
- package pins `{ecosystem, name, version, source, direct, reason}` from the lockfiles (`source` is the lockfile it came from), each direct dependency with no lock entry included, and an Operator or Deployed Locked version of a derived Upstream link in place of the lockfile's (`source: "Locked version (operator)"` or `"(deployed)"`).

A version that cannot be read is null with a `reason` (`a moving tag`, `no tag`, `a variable`, `a range`, `no lockfile entry`). Its pin is never sent to a feed and reads `exposure: unknown`, never `not_exposed`. An unreadable manifest fails the job with `invalid_manifest` (422).

The feeds are fetched by worker code, never by an agent (`Workflows.advisory_feeds`), and cached in `advisory_cache` `{key, etag, modified, body, fetched_at}`:
- OSV: `POST {NUMEN_OSV_URL}/v1/querybatch` (`node` and `php` as the `Bitnami` ecosystem, `npm`, `Packagist`), then `GET /v1/vulns/{id}` only for a record whose `modified` changed;
- GitHub's advisory database: `GET {NUMEN_GITHUB_API_URL}/advisories` with the read token, by `ecosystem` and `affects` (100 packages a request) and by `cve_id` for each runtime CVE that OSV or NVD returned, since GitHub has no runtime ecosystem; revalidated by ETag;
- NVD: `GET {NUMEN_NVD_API_URL}?cpeName=cpe:2.3:a:nodejs:node.js:<version>:*:*:*:*:*:*:*` (or `cpe:2.3:a:php:php:…`) with the NVD key, reused for 12 hours, and outside Numen's AC-09 and AC-10 gates.

`NUMEN_OSV_URL` (default `https://api.osv.dev`) is read only in test mode, like the other base URLs. A feed's error is stored as `feeds[feed].error` and the others still match. Records whose aliases overlap are one vulnerability. Its ranges are the OSV events, GHSA's `vulnerable_version_range` (bounded by `first_patched_version` unless it has a `<` bound, or a `<=` bound that the patched version is not above, which it would narrow) and NVD's `cpeMatch` version fields, all as comparator lists. They are compared with the pin as semver for npm and the runtimes and as numeric tuples for composer; a range that cannot be evaluated reads `unknown`, which counts as exposed.

Each vulnerability is one `advisory_matches` row, unique on (`application_id`, `vulnerability`), with:
- `vulnerability`: the canonical id, the CVE id else the GHSA id else the first id;
- `aliases`: every id of its records, a stored row's aliases bridging a later record, so an alias learned later folds the rows it joins into the oldest that has a Finding, else the oldest, which keeps its key and Finding (a row with a different Finding stays beside it);
- `state`: `exposed`, `unknown` or `not_exposed`, the worst of its pins;
- nullable `finding_id`;
- `data`: `{pins: [{kind, ecosystem, name, version, sources, ranges: {feed: [[[op, version], ...], ...]}, state}], summary, severity, references, feeds, records}`.

Every stored row is read again against each collection, and a feed that fails or no longer lists the vulnerability keeps its stored ranges. The pins are stored as `applications.advisory_pins` `{repository_id, revision, collected_at, feeds, runtimes, packages}`, a deferred column served only by `GET /applications/{id}/advisories`. The job result is `{source_ref, runtimes, packages, unknown, matches, opened, attached, finding_ids}`.

Advisory Findings (A09, A11; `domain.attach_advisory`). An exposed or unknown row with no `finding_id` attaches to the Application's oldest Open or Confirmed `commit` or `cve` Finding that goes by one of its aliases (`domain.finding_aliases`: a `cve` Finding's `cve_id`, the non-SHA `addresses` of a commit Finding's source Analysis, and the aliases of rows already attached). That Finding moves to Confirmed with cause `{by: advisory, advisory_id}` and records an Action `{action: advisory_attached, vulnerability, aliases}`; no Alert is sent and no bump is drafted. Otherwise the row opens one Finding through `domain.open_finding`, with source `advisory`, `source_ref` and `subject_id` the vulnerability, cause `{by: advisory, advisory_id, aliases}`, `target_applicability` `affected` or `unknown`, and the one Alert (verdict `Advisory`, source the vulnerability). An exposed row then Confirms it with the same cause (A11's "Advisory check match"); an unknown one leaves it Open. A row that has a Finding is never given another, so the next day's check opens no duplicate and a Dismissed or Remediated Finding stays so. Deleting the Finding frees its row. `link_change` also links a fix whose `addresses` name an alias of a row attached to a Finding. An exposed (or unknown) Upstream Vulnerability fix that links to an Open or Confirmed advisory Finding runs its Upstream Playbook there (A06, A16; `run_playbook`): the Finding records `fix_commit_id`, which `domain.source_commit` reads, so its cell becomes `("upstream", "Vulnerability fix")` (`proof`, `remediation_pr`), it gets the fix's drafted n-day Proof bundle (or `draft_bundle`'s), `require_lab` allows its Lab after Approval, `exportable` is false, and the job result's `finding_ids` lists it. Its Remediation PR stays the advisory bump: `remediation_step` drafts no Upstream bump for it.

The advisory Playbook cell is `PLAYBOOKS[("advisory", None)] = ("report", "remediation_pr")`:
- `report` is `ready`: `advisories.report` renders it as plain text from the stored feed data;
- `remediation_pr` is `no_own_repository`, the draft's status, `no_fixed_version`, `not_direct` (a package only a lockfile names) or `not_drafted`;
- `require_lab` refuses a Lab for an advisory Finding without such a fix with `lab_not_allowed` (409), "An Advisory check match gets a report and a bump Remediation PR, never a Lab Proof".

`finding_json.advisories` lists the rows attached to the Finding, each `{id, vulnerability, aliases, state, finding_id, pins, summary, severity, references, feeds, records, updated_at, report}`.

Advisory bump (A06, A08). When a row opens a Finding and the Application has an Own repository, `draft_remediation` drafts `(subject: vulnerability, action: bump)` at the Own head, with the dependency from `advisories.target`. Only a version or tag that matches a fixed pattern is written:
- a runtime gives `{ecosystem: "runtime", name, version, edits: [{source, field, from, to}]}`: the lowest fixed version above the highest exposed pin, taken from the ranges' `<` bounds, which `remediation.runtime_files` writes into each Dockerfile `FROM` image token (the fixed version replaces the old one in the tag, `node:20.11.1-alpine` becoming `node:20.19.5-alpine`, and a digest after it is dropped), the first line of `.nvmrc`, `engines.node` and `config.platform.php`. A source that no longer holds `from` fails the draft with `pin_changed` (409);
- direct packages give `{ecosystem, names, version, versions: {name: version}}`, each written by `dependency_files` at its own fixed version.

`remediation_actions` is `["bump"]` for an advisory Finding with an Own repository and a target. A manual `POST /findings/{id}/remediation-prs {action: bump}` uses the row's target at the Own head and answers 422 `remediation_unavailable` without one. The pull request's branch is `asset-monitor/<vulnerability-slug>-bump` (`remediation.branch_name`: `asset-monitor/cve-2026-111497-bump`) and its title is `Asset Monitor bump for <id>`.

Remediation by a bump seen on the default branch (A09, A11; `domain.remediate_advisories`, the only caller with cause `version_bump`). An `advisory_check` that read the Own repository, once every row is read again with the feeds' latest ranges, takes each Open or Confirmed Finding that rows point to: the advisory Finding a row opened, or the commit or cve Finding it attached to. When, for every one of its rows, every collected pin of the row's runtimes and packages can be read and is outside its ranges, the Finding moves to Remediated with cause `{by: version_bump, advisory_id, revision, versions: {name: [version]}}` (`advisory_id` the first row's vulnerability). A pin no longer collected leaves the Finding as it is.

The Application page's Advisories tab lists the runtime pins (name, version or "Unknown" with its reason, `image:tag`, source and field, Exposure) and the package pins (ecosystem, name, version or "Unknown", source, direct, Exposure), each feed's record count or error, and the matches with their aliases, summary, pins, state and Finding link. Run Advisory check posts `/advisory-checks`. The Finding page shows one Advisory panel per `advisories` entry: the report in a `<pre>` with a copy button, the aliases, the state, the feeds, each pin's version, sources and each feed's ranges, and the lowest fixed version (the bump draft's version and edits, else the `remediation_pr` step's state). All feed text is React text, never markup. The Draft bundle callout shows only for a Finding with a Lab or a static Proof.

Served-content checks (A10; `backend/numen/served.py`, `served_probe.py`, migration `e5f6a7b8c9d0`). Records:
- `watched_pages` `{id, application_id, url, homepage, baseline, removed_at, created_at}`, unique on (`application_id`, `url`). `baseline` is `{user agent: {fetch_id, fingerprint, accepted_at}}`. `domain.sync_homepage` keeps the Asset URL as the one homepage page; `POST /applications` and `PATCH /applications/{id}` call it, and the migration gives every existing Application one. A new Asset URL moves the homepage to a page with that URL and no Baseline, or to the page the Operator already watched there (with its Baseline), and the old homepage is removed (no longer checked, history kept), as is every other page left on an old origin. Other pages share the Asset URL's scheme, host and port (default port included), at most 20 per Asset (`domain.MAX_WATCHED_PAGES`).
- `served_fetches` `{id, application_id, page_id, job_id, user_agent, status, fingerprint, summary, resources, error, created_at}`, indexed on (`page_id`, `user_agent`, `created_at`). `user_agent` is `browser` or `googlebot` (`domain.USER_AGENTS`). `status` is `fetched`, or `failed` when the page did not answer 200, with `error` `{status, error}` (the HTTP status, else null with the probe's error name, such as `HTTPStatusError` for a request the gateway refused or `budget` for a page past its user agent's byte share). `fingerprint` and `summary` (`served.summary`) are null and `{}` for a failed fetch. `resources` is `[{kind: page|script, url, final_url, status, sha256, size, content_type, error}]`, the page first, then its scripts in the page's order. Every response body is an Artifact `{resource_type: served_content, resource_id: <sha256>, path: content}`, published once per sha256 (a stored one is reused) and never secret-scanned, since evidence is kept as served. `Workflows.served_files(db, fetch, prefix)` reads a fetch back as `{prefix}page.html` and `{prefix}scripts/NN.js` (NN the script's place in the page). Served fetches and their bytes are never pruned.
- `served_changes` `{id, application_id, page_id, user_agent, fingerprint, fetch_id, previous_fetch_id, baseline_fetch_id, diff, triage_status, triage_result, review_decision, verdict, analysis_state, created_at}`, unique on (`page_id`, `user_agent`, `fingerprint`): one served-content change per distinct fingerprint, so each is triaged at most once. `fetch_id` is the first fetch that served it, `previous_fetch_id` the newest fetched one of that page and user agent before it, `baseline_fetch_id` the Baseline's, and `diff` is `served.diff(baseline summary, its summary)`. The Triage and Analysis fields are named as Commit's (`triage_status` defaults to `disabled`, `review_decision` to `pending`).

A `served_check` job (input `{}`, no profile, a long kind, exempt from the `source_generation` check like `served_triage`, `served_analysis` and `served_content_sweep`) runs one `probe` per Watched page that is not removed, homepage first: `recipe.py` is `served_probe.py`, `target.json` is `{url, user_agents: [browser, googlebot], max_scripts: 20, max_bytes: 7 MiB}`, and the policy is `workflows.SERVED_POLICY` `{served_content: true, methods: [GET], request_budget: 100, max_response_bytes: 1 MiB, max_total_bytes: 16 MiB}` with no origins. A result that does not hold exactly the two user agents with at most 20 fetched scripts each (the page's other scripts are listed `skipped`/`limit`, and still count in its summary), the bytes of every resource served with 200 or given a sha256, and outputs named by their own sha256 fails the job with `invalid_probe_result` (422); a runtime failure fails it too. After its fence it re-reads the Application, calls `sync_homepage`, locks the pages, skips a page removed meanwhile, publishes the new bytes, adds one ServedFetch per page and user agent, and, for a fetched fingerprint unlike that user agent's Baseline, gets or creates its ServedChange (`domain.record_served_change`; a concurrent check that creates it first wins). With no Baseline nothing is a change. Its result is `{pages, fetches, changed, matches, awaiting_baseline, failed}`, counting fetches. It is queued by `domain.schedule_served_checks` (called from `scheduler.main` in its own transaction after `schedule_advisory_checks`, not part of `domain.schedule`) once per interval window for each monitored, unarchived Application (key `served:{application id}:{unix seconds // monitor_interval_seconds}`), and by Check now for the Asset; `domain.queue_served_check` reuses an active one. No Application create or link path queues one. Its job subject is `{type: served, label: <Asset URL>, link: /applications/{id}?tab=served}`.

Accepting a Baseline (`domain.accept_baseline`, A10) is not an Approval: it takes no password and is protected by the session's CSRF token like any mutation. The fetch must be a `fetched` one of that page (else 422 `invalid_baseline`). A first Baseline per user agent is always accepted. A later one is accepted only when the fetch's fingerprint has a ServedChange (same page and user agent) that `domain.baseline_allowed` admits: its `verdict` is Security hardening or Unrelated (`domain.BASELINE_VERDICTS`, the A06 Served content cells), or, while its `review_decision` is `dismissed`, its `verdict` is Insufficient context (dismissed from the Review queue) or Triage declined it (`triage_status` completed with decision `unrelated`, no `verdict` and no `analysis_state`; decision 14). A Malicious change (even dismissed), an Insufficient context still in the Review queue, a declined change the Operator has since marked `candidate`, or an untriaged change with no Verdict gives 409 `baseline_not_allowed`. Accepting the Baseline's own fingerprint again changes nothing. It records an Action `{resource_type: watched_page, data: {action: baseline_accepted, user_agent, fetch_id, fingerprint, previous}}`, `previous` being the Baseline it replaced or null.

Triage and Analysis of served-content changes (A03, A04, A10; the A06 Served content column):
- Queueing. `domain.record_served_change` calls `domain.queue_served_triage(db, application, change)` in the savepoint that creates the change, so only the check that creates it queues its one Triage. By the Application's `triage_mode`: `disabled` leaves `triage_status: disabled`; `jev` gives `blocked` with `triage_result {decision: insufficient_context, reason, error: jev_triage_unsupported}` (Jev Triage reads commits only); otherwise `automated_profile(application, "commit_triage")` must have the mode's agent (else `triage_profile_mismatch`) and a `served_triage` job `{served_change_id}` is queued with it (`pending`); any DomainError gives `blocked` with its code and message.
- `served_triage` (a long kind): one tool-less agent run, no input files, `limits {timeout_seconds: 120}`, schema `SCHEMAS["served_triage"]` (commit_triage's). Facts `{page_url, user_agent, fingerprint, baseline_fingerprint, diff, diff_complete}`: `diff` is `json.dumps(change.diff, indent=1, sort_keys=True, ensure_ascii=False)` capped as its encoding fits 100,000 characters (`workflows.triage_cut`, shared with commit_triage), `diff_complete` whether nothing was cut. Reply parsing, validation, retries and the Transcript (`kind: triage`, `subject_id` the change) are commit_triage's (`Workflows.triage_run`). `triage_result` records `fingerprint` where a commit's records `revision`; `review_decision` follows the decision as for commits. A flag (`security_candidate`, or `insufficient_context`, which an incomplete diff's `unrelated` becomes) runs `start_waiting`, then `domain.start_served_analysis`.
- Automatic Analysis: `domain.start_served_analysis` queues one `served_analysis` `{served_change_id, automatic: true, shared: false}` per change (key `served-analysis:{change id}`) on `automated_profile(application, "commit_analysis")` through `domain.start_automatic`, which `start_analysis` shares: over a cap the change gets `analysis_state {status: waiting_for_cap, since, cap}`, without an API-key profile `{status: blocked, error}`, else `{status: queued, job_id}`. `served_analysis` is in `CAPPED_KINDS`, so it counts against the Application's and the Provider account's caps. `start_waiting` starts waiting commits and served-content changes together, oldest `since` first.
- `served_analysis` (a long kind): its input files come only from artifact storage (`Workflows.served_files`): `source/changed/<user agent>/` for every ServedFetch of the page with the change's fetch's `job_id` (both user agents of that check), `source/baseline/<user agent>/` for each user agent's Baseline fetch (the change's own `baseline_fetch_id` for its user agent, the page's current Baseline for the other), and `served-content.json` `{page_url, user_agent, files: {path: {url, final_url, status, sha256, error}}, diff}`, which lists every resource of those fetches, a not-stored one with `sha256: null`. Facts `{page_url, user_agent, fingerprint, baseline_fingerprint}`; no policy (no target fetch, no probe call); `limits {timeout_seconds: 1800}`. Schema `SCHEMAS["served_analysis"]`: `verdict` (the four of `SERVED_CONTENT_VERDICTS`), `confidence`, `title`, `summary`, `evidence`, `open_questions`, and `indicators` and `reachable_secrets` (required for Malicious change); no `vulnerable_ref`, `addresses`, `before_after` or other field. `validate_result` refuses a Vulnerability fix or Vulnerability introduced Verdict with `verdict_not_allowed` (422) before the schema check, so the job fails with that code. `report.md` is required (`missing_report`). After its fence it adds `Analysis {kind: served_analysis, subject_id: change id}`, publishes the outputs as its `analysis` Artifacts, sets `verdict`, `analysis_state {status: completed, analysis_id}` and `review_decision` from `VERDICT_REVIEW` (an Operator review after the job was queued wins). Its result is `{analysis_id, served_change_id, ...result}`. A Malicious change then opens the Application's `served_content` Finding for the change (`domain.open_finding`: subject the change id as `subject_id`, `source_ref` the page URL, cause `{by: verdict, verdict, confidence, analysis_id, served_change_id}`; a repeat Analysis reuses it) and, while it is Open or Confirmed, sets `source_analysis_id`, `evidence`, `static_proof {analysis_id, indicators}` and `cleanup_report {analysis_id, page_url, user_agent, fetch_ids, first_seen, secrets}`, then publishes `report.md`, `indicators.json` and, when drafted, `detection-rule.yar` as a Draft revision (`publish_finding_bundle` with `require_complete: false`, `source_ref` the fingerprint), which queues its `detection_rule` validation. `served.check_indicators` keeps a file only when it is a `source/changed/` path whose bytes no `source/baseline/` file holds (hashed by application code), and a host, URL or command only when it occurs in the changed fetches' bytes and in none of the Baseline fetches'; the rest is `rejected` with its reason, in `detection.check_indicators`' shape. `fetch_ids` are every ServedFetch of the page and user agent with the change's fingerprint, oldest first, `first_seen` the first one's time, and `secrets` the non-blank `reachable_secrets`. It gets no Remediation PR (`remediation_actions` is `[]`) and no Lab (`lab_not_allowed`), and `accept_baseline` refuses its fingerprint. Its result then adds `finding_id`, `artifact_revision` and `artifact_state`. A served Analysis is always exportable (`domain.exportable`).
- Runner operations: `workflows.RUNNER_OPERATIONS` maps `served_triage` to `commit_triage` and `served_analysis` to `commit_analysis`, and `Workflows.agent` passes the mapped name to `runtime_profile`, so the runner's fixed tool profiles apply (Triage with no tools; Analysis read-only, writing only to its outputs, no target fetch) and the Application's `commit_triage` and `commit_analysis` profiles are used. Prompts are `served_triage` and `served_analysis` (templates; `schemas.OPERATIONS` is unchanged).
- Failures (`worker.run_once`): a failed `served_triage` sets `triage_status: failed` with `{error, reason, attempt}` and is retried as commit_triage is (up to `TRIAGE_ATTEMPTS`, retry n after n minutes), never read as unrelated; a failed `served_analysis` sets `analysis_state` `failed` or `timed_out` with `{job_id, error}` and leaves the Verdict and review decision as they were. A Retry of a `served_analysis` job sets the change's `analysis_state` back to `queued`.
- A job with `served_change_id` has the subject `{type: served, label: "<page URL> · Browser|Googlebot", ref: <fingerprint[:12]>, link: /applications/{id}?tab=served}`.
- Detection rule validation (A07 Served content): `Workflows.detection_rule` for a `served_content` Finding scans stored bytes only, as `served_files` names them (`page.html`, `scripts/NN.js`): `changed/` the change's `fetch_id`, `parent/` its `previous_fetch_id` and `baseline/` its `baseline_fetch_id`. When the previous fetch is the Baseline fetch the baseline check is `skipped` with "The previous fetch is the Baseline fetch". `detection.checks(..., served=True)` keeps the check names and words the messages by fetch (`detection.SERVED_CHECKS`). A pass confirms the Finding with cause `{by: detection_rule, artifact_revision, job_id}`; a failure leaves it Draft and its state unchanged.
- Remediation (A10, A11): when a check's fetch matches its user agent's Baseline fingerprint, every Open or Confirmed `served_content` Finding whose ServedChange has that page and user agent becomes Remediated with cause `{by: baseline_match, fetch_id, page_id, user_agent, at}` (`transition_finding`, which records the Action). A Dismissed or Remediated one is unchanged, and the Operator's `POST /findings/{id}/transitions` remediates one too.

Opening (A08). An approved draft (`POST /findings/{id}/remediation-prs/{remediation_pr_id}/approvals`) queues one `remediation_pr` job `{remediation_pr_id, finding_id, diff_sha256}` with no profile. The job refuses a record whose repository is no longer the Application's Own repository (`not_own_repository`, 409), or that is no longer `approved` with that hash (`input_changed`, 409). It applies the stored diff to the `base_ref` snapshot again before any GitHub request. Only then does it make requests with the write token (`Workflows.write_client`, the only place they are made; `github_write_token_required`, 422, without a `github_write` account). `remediation.open_pull_request` works only on an `asset-monitor/` branch (`unsafe_branch` otherwise), named by `branch_name`:
- An existing branch is reused when its head commit's message and parent are this change's, else the job fails with `branch_exists` (409).
- A new branch gets one blob per changed file and a tree on the base commit's tree. Each file keeps its mode from GitHub's recursive tree, a new file is 100644, and a deleted one has `sha: null`. A path that is, or sits under, a symlink or submodule there is `diff_rejected`, and a truncated listing is `tree_truncated`. Then a commit whose only parent is `base_ref` and `refs/heads/<branch>`.
- Each touched path must be on GitHub exactly as the snapshot held it: its blob's git object id (`remediation.blob_sha`) equals the listed entry's `sha`, and a path the diff creates is not listed. A tarball applies `.gitattributes` (line endings, `export-subst`, `export-ignore`), so a mismatch is `diff_rejected` before the first write.
- An existing pull request for the branch (`state=all`) is reused, else a `draft: true` one is opened against the repository's `source_ref` (the branch its cursor and merge check follow), else its default branch.

Title, body and commit message are fixed application text: `Asset Monitor <action> of <short-sha>` (for an Advisory check's subject, `Asset Monitor bump for <vulnerability>`), the Finding's dashboard link, and `Approved diff SHA-256: <hash>` in the message. Writes are single requests that are never retried (`Sources.send`). A 4xx is `github_write_failed` with GitHub's status and message, bounded to 300 characters; a 5xx is the same but retryable; an unreachable GitHub is `github_unavailable`. A crashed attempt is recovered by lease expiry and finds its branch and pull request by name, so at most one is opened. The record becomes `open` with `data.branch`, `pull_number`, `pull_url` and `head_sha`, and an Action `{action: remediation_pr_opened, remediation, remediation_pr_id, diff_sha256, branch, pull_number, pull_url, head_sha}`. Nothing merges, moves a ref, writes a default branch or writes to any other repository.

Merging (A08). The Operator merges. Every source check, a 304 included, reads each `open` record of that repository with `remediation.pull_state` (`GET pulls/{n}`: `state`, `merged`, `merge_commit_sha`) through `Workflows.write_client`, before its fence: a fine-grained read token cannot read pull requests on a private repository. A failed read (such as `github_write_token_required`) is kept as the record's `data.error` and never fails the check; the next successful read clears it. Inside the fence, after the poll's commits are imported (`Workflows.pull_request_state`):
- `merged` with a `merge_commit_sha` that is a Commit of this repository (a merge commit, the squash commit or the last rebased commit, all on the default branch): the record becomes `merged` with `data.merge_commit_sha`, an Action `{action: remediation_pr_merged, remediation, remediation_pr_id, pull_url, merge_commit_sha}` is recorded, and `domain.transition_finding` moves the Finding to Remediated with cause `{by: remediation_pr, remediation_pr_id, pull_request (its URL), merge_commit}`. A Dismissed or Remediated Finding stays as it is.
- `merged` with a merge commit that no poll has imported yet: nothing changes until the poll that imports it.
- `closed` and not merged: the record becomes `closed`; the Finding is unchanged.

The Finding page's Remediation PRs panel is the Approval screen. Each record shows its `action`, `status`, `summary`, `error` (a failed draft, PR step or pull-request read), a warning for the `workflows` flag, `base_ref`, `branch`, a `pull_url` link (only an `http(s)` URL, `rel=noreferrer`) and its `diff` as React text with its full `diff_sha256`, never as markup. Each bidirectional control or zero-width character in the diff (U+061C, U+200B to U+200F, U+2028 to U+202E, U+2060 to U+2069, U+FEFF) is shown as a visible `⟨U+XXXX⟩` escape under a "Hidden characters" warning; the hash stays that of the stored bytes. Approve, on a `ready` or `failed` record, opens the same password dialog as Start Lab and posts `{password, diff_sha256}`. Draft patch and Draft revert post `{action}` for each of `remediation_actions`, disabled while that action's record is `drafting`, `approved`, `open`, `merged` or `closed`. With `own_repository` false it reads "No Own repository: Remediation PR steps are skipped."; with no record it follows the `remediation_pr` step ("Waiting for a release that contains the fix", "No release without the change to pin", "No fixed version is known yet", "Not a direct dependency: update the package that pulls it in", or that the cell has no Remediation PR). Draft pin and Draft bump appear like Draft patch. The Playbook panel lists each `playbook` step with its state ("Waiting for your Approval" for a Proof whose bundle is complete and a `ready` Remediation PR, "Waiting for a release that contains the fix", "No Own repository: skipped"). The Disclosure report panel shows `disclosure_report.text` as React text in a `<pre>`, a copy button and a link to `form_url`, and says Asset Monitor never sends it. The Remote target exposure panel adds the Exposure state, reason and Locked version (with its tag). The Lab panel and badge show only when the cell has a `proof` step (or there is no cell) and the Finding is not a Malicious change. The commit page lists each `exposures` entry with its Application, state and reason, a not-exposed one included. The Jobs page offers no Retry for `remediation_pr`, `patch_drafting` or `remediation_draft`.

A `merged` or `closed` record is not read again. An `open` one is read on every check, so a merge commit imported by a poll whose read failed is still seen by a later poll with nothing new.



Finding version arrays accept strings and structured evidence objects. The UI renders their product/range/version labels and preserves structured evidence when an operator edits unrelated fields. `GET /findings?view=summary` returns identity, source, lifecycle status and cause, Deployed version, `malicious_change` (whose row shows a Static Proof badge instead of a Lab one), versions, exposure, source links, artifact revision/completeness, timestamps, and nullable `lab_status` for the latest lab run; it omits artifact inventories, evidence, events, and lab histories. The register, Application counts, and quick search use this projection. The default list and individual finding responses retain their full fields. The register shows each Finding's source (`Commit abc1234`, the CVE id, `Advisory GHSA-…` or `Watched page /path`) and its State with the cause under it. The Finding page has a Lifecycle panel with the state, the cause and its time, and the Operator's Confirm and Dismiss (Open only) and Mark remediated (Open or Confirmed) buttons, each sending a required reason to `POST /findings/{id}/transitions`. Its History lists the opened, linked (the change's short revision, linking to its commit, and Verdict) and transition (from → to and cause) events, and older events by their action name. The Deployed version is a separate row ("Still serving code from before the fix", "Serving the fix" or "Unknown", with the check's reason) under the hint that a fix in the repository does not mean the Asset serves it. The commit queue and commit page link each Finding a commit opened or was linked to as `{State} finding · {Application}`, prefixed `Linked:` for a linked one. The commit review decision that sets `confirmed` is labelled Confirm revision, so Confirm names only the Finding lifecycle action.

Finding completeness is recorded with the published artifact revision in server-owned finding data. Edits preserve it, public responses omit the private record, and request bodies cannot override it. A missing or older revision summary is derived from published path/size metadata and integrity-checked Dockerfile/lock contents. Reading a finding describes its published bundle; full byte integrity remains enforced on preview, download, upload merge, and lab execution.

Each agent operation's prompt is rendered from its template in `backend/numen/prompt_templates/operations/`, which includes the shared sections it needs from `sections/` (`rules` for all; `attack-path` and `bundle` for commit analysis, CVE analysis and finding artifacts; `detection-rule` for commit analysis; `source-pin` and `audit-context` for CVE analysis and finding artifacts; `audit` for the three audit phases). Templates are Jinja rendered in a sandbox; operator versions saved through `/prompts` override the shipped defaults by name and apply to the next job. Numen appends `Facts:` and the run's facts as JSON after the rendered template, and a job whose prompt used a customized template records a `prompt_customized` event naming them. Finding regeneration sends bounded identity/source facts in the prompt and supplies operator fields and evidence in `finding.json`. Its linked `analysis.json` preserves analysis identity/results without the artifact inventory, alongside the integrity-checked original `analysis-report.md` and pinned source. Generation does not read every saved analysis artifact or inline file inventories and histories into the bounded runner prompt. Public analysis/detail responses retain their full artifact inventories.

CVE analysis drafts the full n-day bundle in its read-only analysis run, which builds and runs nothing, and creates or updates its Application's CVE finding, preserving an existing finding's title and lifecycle status. Analysis `result.finding_id` and job `result.finding_id` link to that finding; earlier analysis files remain immutable. Both CVE analysis and finding generation (unlike commit Analysis) require all paths in `artifacts.REQUIRED` and a valid pinning declaration before the job succeeds. Incomplete bundles are published as drafts, the job retains artifact/finding/analysis identifiers in `result`, and fails with `incomplete_bundle` and `partial_output_retained:true`. Finding generation receives the linked analysis JSON, original report and pinned CVE record as evidence. Generation never verifies reproduction or automatically closes a finding; unsupported lab build steps remain explicit prerequisites.

Job fields: `id`, `kind`, `application_id`, `status`, `progress`, `profile`, `created_at`, `started_at`, `finished_at`, `error`, `result`, `events`. Job submission returns `202 {job_id, status_url}`. Idempotency keys are supported. Profile/input changes create a new job; a retry reuses the recorded profile/input.

A plugin is used when it is `ready` and contributes the run's provider. `POST`, `PUT`, `PATCH` and `DELETE` on `/plugins` or `/plugins/{id}` return 405 `plugins_read_only`: adding or changing a plugin means editing `runner/plugins.lock.json` and rebuilding the runner image (A13).
- `POST /settings/webhook/test` queues a delivery of the Alert template reading `Asset Monitor: Webhook test` and the dashboard link; `GET /notifications` for delivery history (each row's stored fields: `application`, `account`, `source`, `verdict`, `link`, plus delivery state). Alerts (A12) go to Discord only, and only when a Finding opens and when a cap is reached. `domain.notify(db, event_key, *, verdict, link, application, account, source)` queues one per `event_key` (job idempotency key `notification:{event_key}`), inserting it under a savepoint so a concurrent worker that queued the same key first leaves the caller's transaction intact: `domain.open_finding` sends `finding:{id}:opened` with the Application name, the `source_ref` and `domain.alert_verdict(cause)` (`{Verdict} · {confidence} confidence` for a Verdict, else `Advisory`, as for a CVE-analysis Finding), and the first `analysis_cap_reached` row of a scope and UTC day sends `cap:{application|account}:{id}:{day}` reading `Cap reached`, with the Application name (link `/reviews?application={id}`) or, for an account cap, the Provider account's label (link `/settings?tab=accounts`). Findings the Operator creates (`POST /findings`), Triage, review decisions, other Verdicts and CVE eligibility send none. The delivery is `{content, allowed_mentions: {parse: []}}` with no embeds: `content` is `Asset Monitor: {verdict}` (`Alert` when none is stored), then `Application:`, `Provider account:` and `Source:` lines for the fields present, then the dashboard URL plus `link` when that is absolute. Commit messages, author names, agent text and Proof details are never stored or sent; a legacy Numen row sends only `Asset Monitor: Alert` and its link.
- `POST /notifications/{id}/retry` queues a standard accepted delivery job for a retained failed event.

## Runtime broker contract

The internal broker is authenticated by `X-Broker-Token` from `NUMEN_BROKER_TOKEN`. URL environment: `NUMEN_BROKER_URL`. Its default port is 8081. Frontend callers never access it.

`POST /internal/runs` accepts `{attempt_token, kind, profile, prompt, output_schema, inputs, limits, target_policy?}`; `build` and `repository` are refused as unknown fields, because no agent run builds anything or receives a repository mirror (ADR-0004, ADR-0005). `profile` extends the public profile with `provider_id`, `auth_type`, and a protected `credential` envelope. Inputs are an array of `{path, content_base64}`. Paths are safe workspace-relative files. Limits and kind map to hardcoded broker-controlled profiles; caller values can lower limits, not exceed configured maxima. Prompt/schema never contain credential values. The broker does not accept arbitrary container flags, host mounts, images, or command strings.

Kinds include `agent`, `probe`, `lab`, `detection_rule`, `capabilities`, and `account_login`. `agent` has an `operation` in the profile. Probe inputs include the recipe/script and JSON target input; lab inputs include the finding bundle; `detection_rule` inputs are `rule.yar` and the `changed`, `parent` and, except for a Backfill commit, `baseline` trees, each one archive input. `target_policy` scopes origins/methods and request budgets. With `served_content: true` (a Served-content check, A10) it has no origin list and allows any http(s) origin whose every resolved address, on every redirect hop, is public; its only private range is the subnet of the Docker network the broker's `NUMEN_SERVED_CONTENT_FIXTURE_NETWORK` names (demo VM only, empty by default), whatever the request carries. The gateway's `POST /fetch` body is `{url, method?, user_agent?}`, where `user_agent` is `browser` or `googlebot` (`gateway.USER_AGENTS`) and its absence keeps `Numen-version-fetch/1`. `backend/numen/served_probe.py`, staged as `recipe.py`, fetches a Watched page and at most 20 of its scripts as each of the pair, and `backend/numen/served.py` turns the bytes into Content fingerprints.

`lab_run` composes the vulnerable app under `vulnerable-app/` beneath the bundle's files, which win (A07): an Own-repository Proof gets the Own repository's snapshot at the Verdict's commit; an Upstream Proof whose link stands for packages at a Locked version (`domain.locked_packages`; a non-npm one is refused with 422 `lab_stack_unsupported`) gets the Own repository's snapshot at its `cursor` (its default-branch head) or, with no Own repository, a minimal private `package.json` whose dependencies are those packages at the Locked version; both leave out `manifest.json` and `.dockerignore` (`domain.LAB_DROPPED`). For the Upstream case it then reads each package's registry `dist` (`Sources.npm_version`) and its tarball (`Sources.npm_tarball`: only a URL under `NUMEN_NPM_REGISTRY_URL`, at most 64 MiB, matching the sha512 of `dist.integrity`, else 422 `package_untrusted`, before any broker call), stores it at `vulnerable-app/.asset-monitor/{name, / as -}-{version}.tgz`, and pins it with `remediation.dependency_files(..., "pin", dist, spec="file:.asset-monitor/...")`, which writes the `file:` spec to `package.json` and the lock root and keeps the lock entry's `version` with that `resolved` and `integrity`. Without a package or a Locked version an Upstream Proof's bundle is sent alone. `LabRun.data` records `source_ref` (an Own-repository Proof), `packages`, `locked_version` and `own_ref` (an Upstream Proof; `own_ref` null for a minimal app) or `bundle_only` (why an Upstream Proof is bundle-only). Completeness runs on the composed files. Before it composes anything `lab_run` refuses, with 409 `lab_not_allowed`, a tree that holds a known Malicious change: the Own repository's `Commit` rows with that Verdict that its read-only mirror (A05) finds the built revision (the Verdict's commit or the Own `cursor`) reaches, unless a `revert` Remediation PR of that commit is `merged` and its `merge_commit_sha` is in that revision too. A `lab` run carries and builds a whole application, so it is bounded like a build rather than like an analysis: its bundle travels as one compressed archive (up to 65536 expanded files and 512MB), its ceiling is `LAB_MAXIMA` (`timeout_seconds` 600 for the run, `build_seconds` 900, `image_bytes` 4 GiB, `memory_mb` 8192, `cpus` 4, `pids` 4096, `output_bytes` 64MB, `input_bytes` 512MB; ADR-0005), callers may only lower them, and the per-run 512-file limit no longer applies to it. The backend's lab defaults are 600 s, 900 s, 4 GiB, 6144 MB, 2 CPUs and 4096 pids, and it waits up to 1800 s for a Lab. `build_lab` accepts an ordinary Dockerfile — `RUN`, multi-stage and continuations included — and builds it with no network, after phase one: only a Node bundle (`vulnerable-app/package.json`) is accepted, otherwise `lab_stack_unsupported`, and a fixed container fetches its dependencies with `npm ci`/`npm install --ignore-scripts`, no credential (a `lab` request with one is refused) and egress only through a gateway allowing the `NUMEN_NPM_REGISTRY_URL` host; the Lab base's global npmrc sets `ignore-scripts=true` for npm in the build and the run too. `FROM` must name the bundled `asset-monitor-lab:0.1.0` (pinned Node 24.9.0 and npm), `scratch` or an earlier stage, `COPY --from` must name an earlier stage, `COPY`/`ADD` sources stay inside the bundle and are never URLs, and build mounts and privileged build flags are refused. The Dockerfile is read as the Engine reads it (`engine.instructions`, mirrored by `artifacts.dockerfile_instructions`): a comment line is dropped before continuations are joined, so a trailing backslash never continues one; a parser directive (`# escape=`, `# syntax=`) and a `$` variable in `FROM`, `COPY` or `ADD` are refused, because they would make the Engine build something other than what was checked. The build context gets exactly those instructions. A `LABEL` with the run's labels follows every `FROM`, so a failed or interrupted build's layers are removed with the run; cleanup also removes the `asset-monitor-lab-job:<run>` tag by name. A watchdog stops a build at `build_seconds` even through a silent step (`timeout`), and a built image over `image_bytes` fails with `lab_image_too_large`; either way no image is left. The application container then runs with a writable root filesystem, its image's own user and an ordinary capability set, on the internal job network only, with no route out and none to the application or control network. The run's `timeout_seconds` starts after the build. The container that runs `poc.py` keeps the bounded, nonroot, network-isolated profile, so an observed proof comes from the application and not from the network. A failing PoC's error stream is returned with its result.

A `detection_rule` run validates a Detection rule (A07) and never runs what it scans. It uses the probe image, which carries the pinned yara 4.2.3, with `network_mode none`, no credential (a request with one is refused) and no Docker socket; its ceiling is `RULE_MAXIMA` (`timeout_seconds` 600, `memory_mb` 1024, `cpus` 2, `pids` 64, `output_bytes` 8MB, `input_bytes` 256MB), which callers may only lower. The backend requests 1 CPU and the ceiling otherwise. A rule using `include` or the `console` module is refused before compiling. The result is `{compiled: false, error}` for a rule that does not compile, otherwise `{compiled: true, error: null, matches: {changed|parent|baseline: {files, count}}}` for each tree sent, with paths relative to the tree, at most 1000 files listed and `count` the full number. A scan error fails the run with `Detection rule scan failed`; it is never read as no match. It writes no outputs. See `runner/README.md`, Detection rules.

Every agent run is read-only. Its inputs, including `inputs/source`, the pinned revision's source snapshot without git history, are staged read-only, only `outputs/` is collected from it (Pi and Claude can write nowhere else; where Codex runs, its sandbox can write elsewhere in the `/workspace` tmpfs), and it has no Docker daemon, socket or client. Its tools are fixed per operation in `runner/numen_runner/adapters.py` by the flags that decide which tools exist, never by `--allowedTools`: Triage (`commit_triage`) gets no tools at all: Claude runs `claude -p --output-format json --tools '' --setting-sources '' --strict-mcp-config --mcp-config '{"mcpServers":{}}' --no-session-persistence` (plus `--bare` for an API key), Pi runs `--print --mode json --no-tools` with every discovery switched off, and Codex is refused because it has no flag that removes its shell. Every other operation writes under `outputs/`: Pi gets only its bundled read/list tools, `numen_write` under `outputs/`, and `target_fetch` for `version_recipe`; Claude gets `Read,Grep,Glob,Write,Edit` under `--restricted` and `--permission-mode dontAsk`, with `--settings` approving file edits under `//workspace/outputs/**` and, for `version_recipe`, the target MCP tool; Codex is refused for Analysis, CVE analysis and patch drafting too, and for the operations it still runs keeps its shell in its native `:workspace` sandbox with network off except for `version_recipe`; neither Pi nor Claude gets a shell tool. The credential-free gateway allows CONNECT only to the selected provider's hosts, plus `herdr.dev` for an agent run that hosts a Herdr session (`engine.gateway_config`; Triage never does); every other host, package and source registries included, is refused before any DNS lookup.

A commit analysis on an incomplete upstream diff (a merge or an oversized change) never stands as Unrelated or Security hardening: the snapshot has no history, so the whole change cannot be reviewed, and either Verdict is recorded as Insufficient context, so the commit stays pending in the Review queue. Analysis prompts require the attacker, least privilege, source, propagation, sink and trust boundary to be established before drafting a bundle, and a reproduction to deliver the payload only through that source as the least-privileged attacker and observe it at the sink, never by writing the payload into storage directly; a shortcut reports `not_reproduced`. Analysis itself reproduces nothing: its bundle is a draft for a Lab. A commit's `commit.json` input describes the revision only; earlier analyses travel separately as `prior-analyses.json`, labeled untrusted prior analysis to be used only as a checklist and never as a verdict, without their artifacts or finding links.

`ExecutionContext.progress` records runtime lifecycle events as job events, once per run and type. The recognised types are `lab_started`, `lab_application_exited`, `lab_dependencies`, `lab_build`, `lab_built` and `result_repair`, sourced from `RUNTIME_EVENTS` in `backend/numen/queue.py`. A runtime event only selects which row is written: the application substitutes its own fixed message and discards the runtime's, and runtime-reported provenance values are bounded before they become a row, because a workload reports both on a log its agent's own process shares. A milestone is therefore not evidence of what ran; the pinned provenance and the attempt record are. Runtime output, prompts, and credentials still never reach the timeline.

Submission returns `{run_id, status}`. `GET /internal/runs/{id}` returns `{run_id, status, progress, events, error?, result?, outputs?}`. Outputs are `{path, content_base64, sha256, size}`. `POST /internal/runs/{id}/cancel` stops/reconciles the run. `GET /internal/runs/{id}/outputs` retrieves validated outputs. Standard statuses are `queued`, `running`, `succeeded`, `failed`, `cancelling`, `cancelled`.

Implement real Pi, Claude, and Codex argv/protocol adapters, isolated container jobs, and capabilities/native login flows. Fixture modes may exist only in explicit test configuration. Unsupported credentials or unavailable engines fail truthfully. Sensitive credentials are never included in ordinary run responses or logs. Trusted native-login credential ingress requires a separate authenticated retrieval channel, deleted after successful vault ingestion; coordinate the exact minimal channel with backend owner.

## Ingress (B01, ADR-0006)

The Ingress is `backend/numen/ingress.py`, run as two Compose services from the app image. This section describes it as built in Phases 12 and 13, before any On-server agent exists.

- **Services and ports.**
  - `ingress-push` runs `python -m numen.ingress push`: the push listener on container port 8083, published on `127.0.0.1:${NUMEN_PUSH_PORT:-8791}`. Its healthcheck is a TCP connect, because an HTTP check would spend the listener's global bucket.
  - `ingress-agent` runs `python -m numen.ingress agent`: the agent listener on container port 8084, published on `127.0.0.1:${NUMEN_AGENT_PORT:-8792}`, TLS only. Plain http gets no answer. Its healthcheck is `GET https://localhost:8084/health` with an unverified TLS context, because the container holds the key, not the pin.
  - Both use the image `asset-monitor-app:0.1.0` with no build. They are off the `x-app` anchor, with `user: "10001:10001"`, `read_only: true`, `cap_drop: [ALL]`, `no-new-privileges:true`, `init: true` and `restart: unless-stopped`. Each has `depends_on: migrate: condition: service_completed_successfully`.
  - uvicorn serves each with `access_log=False`, `lifespan="off"` and `ws="none"`.
  - `make up`, `make logs`, `backup.sh`, `restore.sh`, `test-journey.sh` and `demo.sh` include both. Host ports per project: journey 18791 and 18792; demo 8793 and 8794 (`NUMEN_DEMO_PUSH_PORT`, `NUMEN_DEMO_AGENT_PORT`); demo test 18793 and 18794.
- **Routes and answers.**
  - **Push listener** (`push_app(factory, vault)`, B02). It records Push deliveries and nothing else; the scheduler's nudge turns them into source checks. A request is checked in this order:
    1. It takes the global `push` bucket. When that is empty, the answer is `429` `rate_limited` with `retryable: true`.
    2. A method other than `POST`, a path that is not exactly `/push/<32 lowercase hex characters>` (`PUSH_PATH`), or a push id not in the in-memory set of known push ids gets `404` `not_found`, before its body is read and with no query. Nothing is recorded or logged.
    3. It takes the push id's own bucket, `("push", <push id>)`, 60 a minute (`PUSH_PER_MINUTE`): `429` `rate_limited`, reason `rate_limited`.
    4. `X-GitHub-Event` other than exactly `push` or `ping`: `400` `event_not_accepted`, reason `event_not_accepted`. `X-GitHub-Delivery` missing or not 1 to 64 of `[A-Za-z0-9-]` (`DELIVERY_ID`): `400` `delivery_id_required`, reason `delivery_id_missing`.
    5. The body is read through `read_body` with `PUSH_CAP` (1 MiB): `413` `request_too_large`, reason `body_too_large`.
    6. In one transaction in the thread pool, it reads the push id's row again: a row gone after Turn off gets `404` `not_found`, with nothing recorded. It decrypts the current secret with `Vault(NUMEN_INGRESS_KEY)` and compares `sha256=<hex HMAC-SHA256 of the raw bytes>` with the `X-Hub-Signature-256` bytes through `hmac.compare_digest`. A mismatch or a missing header gets `401` `signature_invalid`, reason `wrong_signature`. Turn off and Regenerate therefore apply to the next delivery, without waiting for a refresh.
    7. A `ping` sets `last_accepted` to `{at, event: "ping", delivery_id}` and answers `200 {"status": "ping received"}`, with no `push_deliveries` row.
    8. A `push` inserts a `push_deliveries` row (`delivery_id`, `body_sha256`: the hex SHA-256 of the raw bytes, `received_at`) in a savepoint, with no `RETURNING`. A unique violation (the same delivery id, or the same body) answers `200 {"status": "duplicate"}` and changes nothing, `last_accepted` included. Otherwise it sets `last_accepted` to `{at, event: "push", delivery_id}` and answers `200 {"status": "accepted"}`.
    - A refusal sets `last_refusal` to `{at, reason}` (`UPDATE ... WHERE push_id`) only when the push id's `("refusal", <push id>)` bucket, 1 a minute, allows it. Every `at` is ISO 8601 in UTC. The body is never parsed: it is only hashed and signed.
    - Bucket takes stay on the event loop. Only the database work runs through `starlette.concurrency.run_in_threadpool`.
    - **Known push ids.** The app's `refresh()` replaces the set with a `frozenset` of `select(push_webhooks.push_id)`. `main()` runs it in a daemon thread, `refreshing`, every `REFRESH_SECONDS` (15), so a new push id is accepted within 15 s. A failed refresh keeps the set it has and logs only the exception's class, `Refreshing the known push ids failed: <class>`, because a query's error text can hold a push id.
  - **Agent listener.** Every request's body is read through `read_body` with the 64 KiB cap first, and a refused body gets `413` `request_too_large`. Then `GET /health` gets `200 {"status": "ok"}`, and every other method and path gets `404` `not_found`.
  - Neither answers `405`: a wrong method is a `404`. Neither serves `/api`, `/api/auth/login`, the SPA or `/assets`.
  - Error bodies are `DomainError(...).as_dict()`, `{code, message, retryable}`, with the codes `not_found`, `request_too_large`, `rate_limited`, `event_not_accepted`, `delivery_id_required` and `signature_invalid`.
- **Body caps.** `read_body(scope, receive, cap)` returns the body, or `None` to refuse it.
  - It refuses before the first `receive()` when any `Content-Length` header is not all digits or is over the cap.
  - Otherwise it adds up every `http.request` chunk as it arrives, and refuses as soon as the total passes the cap, so a chunked body is capped on the bytes read. A disconnect is refused too.
  - `BODY_CAP` (64 KiB) applies to every agent-listener request, and `PUSH_CAP` (1 MiB) to a Push delivery. The 16 MiB caps for a File manifest and for an upload come with their routes in Phase 16a.
- **Buckets.** `Buckets.take(key, limit, window=60.0)` keeps a sliding window per key, on `time.monotonic`.
  - A key is an identity (a push id, an agent, an Enrollment code) or a global name, never a client address.
  - A refused take is not counted, and a key whose window has emptied is dropped. Each process has its own `Buckets`, and uvicorn's single event loop needs no lock.
  - Wired on the push listener: the global `push` bucket (`PUSH_LISTENER_PER_MINUTE` = 120 a minute), `("push", <push id>)` (`PUSH_PER_MINUTE` = 60 a minute) and `("refusal", <push id>)` (1 a minute).
  - Wired by the routes that name them in Phase 15b: 600 requests a minute per On-server agent, 10 Enrollment attempts an hour per Enrollment code, and 60 requests a minute in all that name an unknown agent or code.
- **Cookies, headers and logs.**
  - `listener(app)` serves `http` scopes only. It removes every `Cookie` header, whatever its case, from the scope before routing, so a `numen_session` cookie changes nothing. No route sets a cookie.
  - It wraps the app in `security.SecurityHeaders`, so every response carries the dashboard's CSP, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`.
  - There is no access log, because it would record push ids. Nothing logs a header or a body. There are no websockets and no lifespan.
  - `numen.ingress` imports only the standard library, starlette's `JSONResponse` and `run_in_threadpool`, `cryptography`, `sqlalchemy`, `numen.config.secret_env`, `numen.models` and `numen.security`. It never imports `numen.api`, `numen.domain`, `numen.workflows` or `numen.worker`, where jobs, Findings and Alerts are made.
- **TLS key and pin.**
  - `NUMEN_AGENT_TLS_KEY` is a P-256 private key, as one line of standard base64 of DER PKCS#8.
  - `NUMEN_AGENT_TLS_PIN` is the lowercase hex SHA-256 of that key's DER SubjectPublicKeyInfo. On-server agents pin the key, not the certificate, and the Go agent of Phases 15a and 15b must use the same encoding.
  - At every start, `tls_files` refuses a key that is not P-256 with `ValueError`. It writes `key.pem` and a new self-signed `cert.pem`, each created with `O_EXCL` and mode 0600, into a fresh `mkdtemp()` under the service's `/tmp` tmpfs (`size=1m`, uid and gid 10001, mode 0700).
  - The certificate has CN `asset-monitor-agent-listener`, SHA-256, a random serial, and validity from one day before the start for 365 days.
- **Database roles.**
  - Migration `b8c9d0e1f2a3`, chained from `a7b8c9d0e1f2`, creates `asset_monitor_push` and `asset_monitor_agent` `NOLOGIN` when missing, in one `DO $$ ... IF NOT EXISTS (SELECT FROM pg_roles ...)` block. It grants nothing, and its downgrade drops no role.
  - Migration `c9d0e1f2a3b4`, chained from `b8c9d0e1f2a3`, adds the push tables and grants `asset_monitor_push` `USAGE` on the current schema (named through `format('%I', current_schema())` in a `DO` block), `SELECT` on `push_webhooks`, `UPDATE (last_accepted, last_refusal)` on `push_webhooks` and `INSERT` on `push_deliveries`, and nothing else. `asset_monitor_agent` gets nothing. Its downgrade drops both tables, and with them their grants, revokes that schema `USAGE` and drops no role. With no `SELECT` on `push_deliveries`, the role's inserts there take no `RETURNING` and no `ON CONFLICT` target.
  - `python -m numen.cli ingress-roles` creates a missing role the same way, then runs `ALTER ROLE <role> WITH LOGIN PASSWORD <password> CONNECTION LIMIT 5` and `ALTER ROLE <role> SET statement_timeout = '5s'`, composed with `psycopg.sql`. It grants nothing and can run any number of times.
  - Without both role passwords, it exits non-zero before it connects, naming `NUMEN_PUSH_DATABASE_PASSWORD` and `NUMEN_AGENT_DATABASE_PASSWORD` and `make init`. Otherwise it prints `Ingress database roles configured`, never the password.
  - `migrate` runs `alembic upgrade head && python -m numen.cli ingress-roles` on every start.
  - Each later migration grants and revokes only on the tables it adds. Phase 13's grants must also `GRANT USAGE ON SCHEMA` to the roles: backend tests migrate into non-public schemas, where `PUBLIC` has no `USAGE`, and a database restored by a release-1 `restore.sh` has a `public` without `PUBLIC`'s `USAGE`. `restore.sh` now re-creates `public` as initdb makes it (owner `pg_database_owner`, `USAGE` for `PUBLIC`), which is the ACL `pg_dump` assumes, so a restore keeps the source's schema privileges. Later phases size their SQLAlchemy pools under the connection limit, for example `pool_size` 2 and `max_overflow` 0.
  - `ingress-push` connects as `asset_monitor_push` with `pool_size` 2, `max_overflow` 0, `pool_pre_ping` and `hide_parameters`, so its error text never holds a bound push id. `ingress-agent` opens no database connection until Phase 15b. The journey's `ingress_check.py` proves both role logins, and its container's connection counts against the same limit.
- **Environment split.**
  - `ingress-push` gets exactly `NUMEN_DATABASE_URL` as `asset_monitor_push` and `NUMEN_INGRESS_KEY`.
  - `ingress-agent` gets exactly `NUMEN_DATABASE_URL` as `asset_monitor_agent` and `NUMEN_AGENT_TLS_KEY`.
  - `app` and `worker` also get `NUMEN_INGRESS_KEY`, which is not on the anchor, so the scheduler, `migrate`, `bootstrap-operator` and `backend-tests` do not.
  - `migrate` gets both role passwords.
  - Neither ingress service gets `NUMEN_SECRET_KEY`, `NUMEN_BROKER_TOKEN` or the database owner's URL. No service gets `NUMEN_AGENT_TLS_PIN`.
- **Networks.**
  - `ingress-push` is on `push-inbound`, a bridge that carries its published port, and on `push-db`, which is internal.
  - `ingress-agent` is on `agent-inbound` and on `agent-db`, which is internal.
  - `db` joins `application`, `push-db` and `agent-db`. Neither ingress service is on `application` or `control`, so neither resolves `app` or `runner-broker`. None of the four networks has a fixed name.
  - Production has no `stand-ins` network. `compose.test.yaml` defines it, `internal: true` with no fixed name (`asset-monitor-test_stand-ins`), and adds it to `fixtures` and to `ingress-push`, whose merged networks are `push-inbound`, `push-db` and `stand-ins`. The GitHub push stand-in reaches `http://ingress-push:8083` over it. No other service and no other overlay joins it (`test_the_stand_ins_network_is_only_in_overlays_and_internal`).
- **`make init`** (`scripts/init.sh`).
  - When `.env` already holds all five keys, it exits without Docker.
  - Otherwise, on an existing `.env`, it appends only the missing keys, after a newline if the file lacks a trailing one, and prints their names, never their values. It never changes an existing line or `.numen/bootstrap-password`.
  - `NUMEN_INGRESS_KEY` is a Fernet key, made like `NUMEN_SECRET_KEY`. Each role password is `secrets.token_urlsafe(32)`.
  - The TLS key comes from `openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -outform DER`, and its pin from `openssl pkey -inform DER -pubout -outform DER`.
  - A missing pin is derived from the existing key. A pin with no key, or a key that does not decode, stops init with nothing changed.
- **Backup and restore.**
  - `backup.sh` pauses and resumes `ingress-push` and `ingress-agent` with app, worker and scheduler. `pg_dump` writes the GRANTs to the roles.
  - `restore.sh` refuses a backup whose `deployment.env` lacks any of `NUMEN_INGRESS_KEY`, `NUMEN_PUSH_DATABASE_PASSWORD`, `NUMEN_AGENT_DATABASE_PASSWORD` or `NUMEN_AGENT_TLS_KEY`, before any service stops: "Backup deployment.env lacks <keys>. For a backup made before release 2, copy them from the current .env into its deployment.env."
  - It also stops and resumes both ingress services.
  - Before `DROP SCHEMA public`, it runs the migration's `DO` block through `psql`, so `database.sql`'s GRANTs load on a fresh volume. `migrate`, on resume or at the next `make up`, gives the roles `LOGIN` again.
  - The journey proves the push grants across that round trip. - Version recipes receive the release fingerprint map as `release-corpus.json` and only a coverage summary in the prompt. Numen writes `fingerprints.json` from the corpus unless the agent supplies an identical map. It sits on the application network and on the project's internal `served` network, with the aliases `toko-batik.test` (the demo PHP Application's Asset) and `cdn.clickfix-fixture.test`.
  - **The repository stand-ins.** In demo mode the fixture builds two bare git repositories, both with fixed authors and dates, so a rebuild gives the same shas: `asset-monitor-demo/shop` (the demo Own repository) and `asset-monitor-demo/react` (the stand-in React Upstream repository). It serves them behind the GitHub REST reads Asset Monitor calls, under `/repos/asset-monitor-demo/<repo>/`, and behind its writes:
    - `git/blobs`, `git/trees` and `git/commits`;
    - `git/refs`, which only creates a ref and answers 422 for `heads/main` or an existing ref;
    - `pulls`, kept in memory.

    It also serves a read-only clone route, `/git/asset-monitor-demo/<repo>.git`, through `git http-backend`. With `uploadpack.allowFilter` and `allowAnySHA1InWant` set, a blobless clone fetches its blobs lazily. `git-receive-pack` answers 403.
  - **The other stand-ins.** The fixture also serves the stand-in npm registry and the served pages. Its OSV, GHSA and NVD answers list the stand-in React2Shell and CVE-2026-111497 advisories only once each is published. Outside demo mode node2shell is published from the start, so the journey is unchanged.
  - **The admin routes, demo mode only:**
    - `POST /admin/demo/push {repository, commit}` commits one prepared directory from `tests/integration/demo_repositories/`. It is idempotent by commit message.
    - `POST /admin/demo/merge {repository, number}` squash-merges a pull request as `<title> (#n)`, or answers 409 on a conflict.
    - `POST /admin/demo/publish {advisory: react2shell | node2shell}` publishes an advisory.
    - `GET /admin/state` adds `published` and `demo_pulls`.
  - **The demo's `NUMEN_TEST_MODE`.** app and worker get `NUMEN_TEST_MODE=1` with the stand-in base URLs: `NUMEN_GITHUB_API_URL` (which GHSA uses too), `NUMEN_GITHUB_GIT_URL`, `NUMEN_NPM_REGISTRY_URL`, `NUMEN_PACKAGIST_URL`, `NUMEN_OSV_URL` and `NUMEN_NVD_API_URL`. In the demo project, test mode also does three things:
    - it relaxes the Discord-only webhook host check, so Alerts can go to the stand-in's `/webhooks/demo` when `DISCORD_WEBHOOK_URL` is unset;
    - it skips NVD request pacing;
    - it lets git clone over http from the stand-in.
  - **The runner-broker.** It gets `NUMEN_SERVED_CONTENT_FIXTURE_NETWORK=${COMPOSE_PROJECT_NAME}_served`, which is A10's demo range and is opened by this overlay only. It also gets `NUMEN_NPM_REGISTRY_URL=https://registry.invalid`, because the demo Own repository vendors its stand-in dependency.
  - **The driver.** `tests/integration/demo.py` seeds the demo and runs each step through the public HTTP API and the stand-in's admin routes only. It never edits the database and never requests an Approval route. The Operator's model keys reach its container by name only. It and `bootstrap-operator` run as the host user (`--user $(id -u):$(id -g)`), who owns the 0600 bootstrap password.
  - **The canned broker, test only.** `compose.demo-test.yaml` is explicit test configuration, never part of the demo. Only `scripts/test-demo.sh` adds it, through `NUMEN_DEMO_OVERLAY`, which `demo.sh` refuses on any project but `asset-monitor-demo-test`. Its `canned-broker` (`tests/integration/canned_broker.py`) answers `agent` and `capabilities` runs with canned replies, and every report says that no agent ran. It forwards `lab`, `probe` and `detection_rule` runs to the real runner-broker. The overlay points app, worker and scheduler at it with `NUMEN_BROKER_URL`. `compose.demo.yaml` never adds it, which `test_deployment.py` checks.
