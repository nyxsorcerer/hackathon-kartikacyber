# Implementation coordination contract

This is the shared contract for the first complete implementation, authorized by the user's “Build it” instruction. Preserve the PRD's outcomes and all three coding-agent choices. Each owner can make reversible local implementation choices within this boundary. Coordinate contract changes with the orchestrator before changing a consumer-facing shape.

## Ownership

- Backend agent: `backend/`, backend tests, migrations, domain services, scheduler/worker, API/security/persistence. Do not edit `runner/`, frontend, or root deployment files.
- Frontend agent: `frontend/`, its tests and package manifests. Do not edit backend, runner, or root deployment files.
- Runtime agent: `runner/`, root Dockerfiles/Compose files, runtime tests, and pinned agent/plugin/skill manifests. Do not edit frontend or backend modules.
- Orchestrator: root Makefile, bootstrap/backup helpers, integration fixtures/journey, documentation, cross-owner integration and final checks. When a correction belongs to another owner's active files, send it back to that owner.

All agents share the workspace. Preserve other owners' edits and adapt to their work. Read the PRD, design, and UI specification as governing context; these instructions settle serialization only.

## API

All paths below begin with `/api`. A session cookie authenticates requests. `GET /auth/session` returns `{authenticated: boolean, username?: string, csrf_token?: string}`. Login accepts `{username: "admin", password: string}` and returns the authenticated session shape. Browser mutations send `X-CSRF-Token` after login. Structured errors use `{code, message, fields?: object, retryable?: boolean}` with JSON; lists use `{items: array, next_cursor: string|null}`. Responses expose no secrets. IDs are strings; times use UTC ISO-8601.

### Domain records

Program fields: `id`, `asset_name`, `asset_url`, `product_kind`, `product_name`, `source_kind` (`github` or `wordpress`), `source_url`, `source_ref`, `source_path`, `plugin_slug`, `monitor_interval_days`, `monitor_enabled`, `archived`, `source_generation`, `last_check_at`, `next_check_at`, `last_error`, `version` (latest observation or null), and `config`.

`config` contains `triage_mode` (`disabled`, `jev`, `pi`, `claude`, `codex`), `profiles` keyed by operation, `cve_selectors` (list of typed selector objects), `cve_min_score`, `cve_versions` (subset of `3.0`, `3.1`, `4.0`), `cve_auto_analyze`, `active_recipe_id`, `monitor_interval_inherited`, `version_scheme`, `version_monitor_enabled`, `asset_origins`, `jev_connection_id`, and `jev_model_id`. Program `latest_version_check` supplies the latest failure independently of the last successful `version`. Agent operations are `commit_triage`, `commit_analysis`, `version_recipe`, `audit_context`, `cve_analysis`, and `finding_artifacts`.

Profile fields: `agent` (`pi`, `claude`, `codex`), `connection_id`, `model_id`, and nullable `reasoning_effort`. Server resolves defaults and validates every combination. These fields are identical for all operation submissions. Runtime receives a resolved provider/auth mode separately.

Commit fields: `id`, `program_id`, `revision`, optional imported `parent_revisions`, `message`, `author`, `committed_at`, `url`, `files`, `diff`, `diff_complete`, `triage_status`, `triage_result`, `review_decision`, and `analyses`. Triage adds `title` and `change_kind` (fix, hardening, introduction, unrelated, insufficient-context). Complete unrelated triage sets dismissed; uncertain input stays pending. Detailed analysis uses the five PRD categories and includes `title`, `finding_decision` (`finding`, `not_a_finding`, `needs_more_evidence`), `finding_reason`, `vulnerable_ref`, and `reproduction` (`status`, `summary`). Late manual review actions take precedence over automatic review-decision updates.

Commit analysis requests the CVE build capability. Supported findings are program/commit-scoped local findings; re-analysis reuses that finding while preserving its operator title/status. Fix findings must pin a verified parent revision; introductions must pin the analyzed revision. A Git application lock must match that revision. Finding generation reuses this validated vulnerable source instead of the current fixed checkout. Linked immutable analysis output remains separate from the finding's current artifact revision. Non-finding/uncertain analyses need a report only; finding verdicts require the complete artifact bundle and retain drafts on incomplete generation. Job results expose `commit_id`, `analysis_id`, and `finding_id` when present.

Resolve legacy commit parents and any vulnerable-source snapshot before acquiring the publication fence. Source I/O renews the job lease through a separate connection and must never run while that same job is locked by publication. Invalid revision proposals still retain the analysis/report and fail without creating a finding; publication remains fenced against cancellation and replacement attempts.

CVE fields: `id` (CVE ID), `program_id`, `title`, `description`, `published_at`, `modified_at`, `scores`, `match_status`, `eligible`, `eligibility_reason`, `applicability`, `affected_versions`, `fixed_versions`, `references`, and `analyses`. Score entries contain `version`, `base_score`, `vector`, `source`. Keep per-program match/eligibility separate from global records.

Finding fields: `id`, `program_id`, `kind` (`cve` or `0day`), nullable `cve_id`, `title`, `status` (`open` or `fixed`), `affected_versions`, `fixed_versions`, `target_applicability`, `source_commit_id`, `source_analysis_id`, `artifact_state`, `artifacts`, `lab_runs`, `created_at`, `updated_at`. `artifact_state` is `{status: "draft"|"complete", missing: string[], limitations: string[], vulnerable_version: string|null}`. Analysis records expose structured output under `result`; CVE `qualifying_score` names the gate witness.

Finding version arrays accept strings and structured evidence objects. The UI renders their product/range/version labels and preserves structured evidence when an operator edits unrelated fields. `GET /findings?view=summary` returns identity, operator status, versions, exposure, source links, artifact revision/completeness, timestamps, and nullable `lab_status` for the latest lab run; it omits artifact inventories, evidence, events, and lab histories. The register, program counts, and quick search use this projection. The default list and individual finding responses retain their full fields.

Finding completeness is recorded with the published artifact revision in server-owned finding data. Edits preserve it, public responses omit the private record, and request bodies cannot override it. A missing or older revision summary is derived from published path/size metadata and integrity-checked Dockerfile/lock contents. Reading a finding describes its published bundle; full byte integrity remains enforced on preview, download, upload merge, and lab execution.

Each agent operation's prompt is rendered from its template in `backend/numen/prompt_templates/operations/`, which includes the shared sections it needs from `sections/` (`rules` for all; `attack-path` and `bundle` for commit analysis, CVE analysis and finding artifacts; `source-pin` and `audit-context` for CVE analysis and finding artifacts; `build-sandbox` for build runs; `audit` for the three audit phases). Templates are Jinja rendered in a sandbox; operator versions saved through `/prompts` override the shipped defaults by name and apply to the next job. Numen appends `Facts:` and the run's facts as JSON after the rendered template, and a job whose prompt used a customized template records a `prompt_customized` event naming them. Finding regeneration sends bounded identity/source facts in the prompt and supplies operator fields and evidence in `finding.json`. Its linked `analysis.json` preserves analysis identity/results without the artifact inventory, alongside the integrity-checked original `analysis-report.md` and pinned source. Generation does not read every saved analysis artifact or inline file inventories and histories into the bounded runner prompt. Public analysis/detail responses retain their full artifact inventories.

CVE analysis generates the full n-day bundle in the analysis run and creates or updates its program's CVE finding, preserving an existing finding's title and operator status. Analysis `result.finding_id` and job `result.finding_id` link to that finding; earlier analysis files remain immutable. Both CVE analysis and finding generation require all paths in `artifacts.REQUIRED` and a valid pinning declaration before the job succeeds. Incomplete bundles are published as drafts, the job retains artifact/finding/analysis identifiers in `result`, and fails with `incomplete_bundle` and `partial_output_retained:true`. Finding generation receives the linked analysis JSON, original report and pinned CVE record as evidence. Generation never verifies reproduction or automatically closes a finding; unsupported lab build steps remain explicit prerequisites.

Job fields: `id`, `kind`, `program_id`, `status`, `progress`, `profile`, `created_at`, `started_at`, `finished_at`, `error`, `result`, `events`. Job submission returns `202 {job_id, status_url}`. Idempotency keys are supported. Profile/input changes create a new job; a retry reuses the recorded profile/input.

## Runtime broker contract

The internal broker is authenticated by `X-Broker-Token` from `NUMEN_BROKER_TOKEN`. URL environment: `NUMEN_BROKER_URL`. Its default port is 8081. Frontend callers never access it.

`POST /internal/runs` accepts `{attempt_token, kind, profile, prompt, output_schema, inputs, limits, target_policy?, build?}`. `profile` extends the public profile with `provider_id`, `auth_type`, and a protected `credential` envelope. Inputs are an array of `{path, content_base64}`. Paths are safe workspace-relative files. Limits and kind map to hardcoded broker-controlled profiles; caller values can lower limits, not exceed configured maxima. Prompt/schema never contain credential values. The broker does not accept arbitrary container flags, host mounts, images, or command strings.

Kinds include `agent`, `probe`, `lab`, `capabilities`, and `account_login`. `agent` has an `operation` in the profile. Probe inputs include the recipe/script and JSON target input; lab inputs include the finding bundle. `target_policy` scopes origins/methods and request budgets.

A `lab` run carries and builds a whole application, so it is bounded like a build rather than like an analysis: its bundle travels as one compressed archive (up to 65536 expanded files and 512MB), its ceiling is `LAB_MAXIMA` (`timeout_seconds` 10800, `memory_mb` 8192, `cpus` 4, `pids` 4096, `output_bytes` 512MB, `input_bytes` 512MB), and the per-run 512-file limit no longer applies to it. `build_lab` accepts an ordinary Dockerfile — `RUN`, multi-stage and continuations included — and builds it on a per-run bridge with network, because a vulnerable application installs its dependencies and initialises a database. What a bundle still may not do is float its base or reach the host: `FROM` must name the bundled lab image, `scratch`, an earlier stage or a `@sha256` digest, `COPY`/`ADD` sources stay inside the bundle unless they carry a valid `--from`, and build mounts and privileged build flags are refused. The application container then runs with a writable root filesystem, its image's own user and an ordinary capability set on that same per-run bridge, so it has internet; Docker keeps bridges apart, so it reaches neither the application nor the control network. The container that runs `poc.py` keeps the bounded, nonroot, network-isolated profile, so an observed proof comes from the application and not from the network. A failing PoC's error stream is returned with its result.

A run whose workspace is disk backed has its outputs collected from that volume by a fixed, credential-free container rather than carried inside the completion envelope, because Docker rotates a container log at its size bound and an envelope carrying an application bundle would arrive truncated instead of refused. Those outputs are validated exactly as inline ones are — normalized relative paths, regular files only, per-file and aggregate byte bounds, integrity hashes — and bounded by `output_bytes` and `ARCHIVE_FILES` rather than by a 512-file cap. The workload therefore neither reads nor hashes its own outputs on those runs, so the authoritative credential scan over published artifacts is the application's.

`build` is accepted only for an `agent` run whose operation supports it (`cve_analysis` or `commit_analysis`), and is rejected for every other kind or operation. A build run reproduces a vulnerable application rather than only reading it, so the broker grants it: a private per-run Docker daemon reachable at `DOCKER_HOST=tcp://docker:2375`, a disk-backed writable `/workspace` volume in place of the memory-backed one, a higher limit ceiling (`timeout_seconds` 10800, `memory_mb` 8192, `cpus` 4, `pids` 2048, `output_bytes` 512MB), `nofile` 4096, and proxy CONNECT access to source-hosting, package-registry, and image-registry hosts in addition to the provider's own. The workload still runs nonroot with a read-only image, dropped capabilities and no new privileges, and it never receives the host Engine socket. The daemon container itself is privileged, which nested containers require on Engine 20.10 without cgroup delegation; its own dockerd runs unprivileged inside the rootless image, it holds no Numen or provider credential, and it has its own egress network. Everything the daemon builds or runs is labeled with the run and destroyed with it, so a build run can reach the public internet through the daemon and anything it must keep has to be written to `/workspace/outputs`.

Two properties make a build run's result transferable to the lab verifier. The run's workspace volume is mounted into the daemon at the same `/workspace` path, because a bind mount's source resolves in the daemon's filesystem and not in the client's; a path outside `/workspace` therefore resolves against the daemon's own filesystem and silently yields unrelated or empty content rather than being refused, and `/workspace/share` is world-writable because containers the daemon starts cannot map back to the workload's user. The workload's own image seeds the volume, so ownership does not depend on which container mounts it first, and no capability or root user is needed to prepare it. `numen-lab:0.1.0` is streamed into the daemon's empty image store at startup, since it exists only in the host store and cannot be pulled; a missing bundled image is reported rather than failing the run. Conversely `build_lab` fetches a bundle's validated digest-pinned base when the host store lacks it and then builds with no network as before, so a base the agent tested is one the verifier can rebuild. That base is an immutable approved reference and is deliberately retained in the host store as a cache for later verifications rather than removed with the run, so repeated lab runs neither refetch it nor race each other's cleanup. Rejected builds are reported to the operator as fixed messages matched against the daemon's own log, never as daemon or agent output. The one runtime value such a message carries is the image reference Docker refused to pull (`build_rejected_image`), kept only when it matches `[a-z0-9][a-z0-9._/:@-]{0,199}` in both the runner and the backend, so no other daemon or agent text reaches the timeline.

Before preparing a build run the engine measures the Docker disk's free space and fails it with `build_disk_low` below `NUMEN_BUILD_MIN_FREE_GB` (default 10 GB); the measurement is advisory and never blocks a run when it cannot be read. A build run may also carry `repository: {url, ref}` (a canonical `https://github.com/<owner>/<repo>` URL from the program and a full immutable revision). Before the agent starts, Numen updates a shared mirror of it in the `numen-git-cache-<instance>` volume (`git clone --mirror` once, then `git fetch`, under a lock so concurrent runs take turns) through the run's own egress gateway, then clones it into `/workspace/repo` checked out at `ref` with `origin` set to the canonical URL. The mirror carries no run label, so cleanup keeps it, and only Numen's seeding step mounts it; the agent's container never does, so no run can alter what later runs receive. A failed seeding is reported (`repository_unavailable`) and the run continues. Commit and CVE analysis on GitHub programs request it. A commit analysis on an incomplete upstream diff (a merge or an oversized change) may conclude `not_a_finding` only when that run reported `repository_ready` and the result carries `diff_review: {range, files?}`, the complete range the agent diffed in `/workspace/repo`; otherwise it fails with `insufficient_diff`. Analysis prompts require the attacker, least privilege, source, propagation, sink and trust boundary to be established before building, and a reproduction to deliver the payload only through that source as the least-privileged attacker and observe it at the sink, never by writing the payload into storage directly; a shortcut reports `not_reproduced`. A commit's `commit.json` input describes the revision only; earlier analyses travel separately as `prior-analyses.json`, labeled untrusted prior analysis to be used only as a checklist and never as a verdict, without their artifacts or finding links. In a build run Pi's `numen_write` may write anywhere under `/workspace` except `inputs/` (its shell already can); only `outputs/` is ever collected.

`ExecutionContext.progress` records runtime lifecycle events as job events, once per run and type. The recognised types are `build_daemon_started`, `build_base_loaded`, `build_base_unavailable`, `build_daemon_lost`, `build_rejected_image`, `build_rejected_mount`, `build_rejected_disk`, `repository_ready`, `repository_unavailable`, `lab_started`, `lab_application_exited`, `lab_base_fetch`, `lab_build`, `lab_built` and `result_repair`, sourced from `RUNTIME_EVENTS` in `backend/numen/queue.py`. A runtime event only selects which row is written: the application substitutes its own fixed message and discards the runtime's, and runtime-reported provenance values are bounded before they become a row, because a workload reports both on a log a build run's agent shares. A milestone is therefore not evidence of what ran; the pinned provenance and the attempt record are. Runtime output, prompts, and credentials still never reach the timeline.

Submission returns `{run_id, status}`. `GET /internal/runs/{id}` returns `{run_id, status, progress, events, error?, result?, outputs?}`. Outputs are `{path, content_base64, sha256, size}`. `POST /internal/runs/{id}/cancel` stops/reconciles the run. `GET /internal/runs/{id}/outputs` retrieves validated outputs. Standard statuses are `queued`, `running`, `succeeded`, `failed`, `cancelling`, `cancelled`.

Implement real Pi, Claude, and Codex argv/protocol adapters, isolated container jobs, and capabilities/native login flows. Fixture modes may exist only in explicit test configuration. Unsupported credentials or unavailable engines fail truthfully. Sensitive credentials are never included in ordinary run responses or logs. Trusted native-login credential ingress requires a separate authenticated retrieval channel, deleted after successful vault ingestion; coordinate the exact minimal channel with backend owner.

## Quality and verification

Backend uses Python/FastAPI/SQLAlchemy/Alembic and PostgreSQL in Docker; SQLite may be used for cheap deterministic API tests, but PostgreSQL claim/lease behavior must be checked against PostgreSQL. Frontend uses React/TypeScript/Vite. The backend serves built frontend assets at `/` in deployment. All actual source fetches, job execution, and database changes remain observable and durable. Implement all requested workflows; do not fabricate monitoring results or mark provider mocks as verified compatibility.

Each owner delivers completed code and focused test/build evidence, plus exact remaining limitations. The orchestrator performs cross-service and browser integration before declaring the application complete.

## Verified implementation adjustments

- Initial source history establishes a baseline. A GitHub baseline imports only the newest page of history (up to 100 revisions), so large repositories stay within API rate limits. Subsequent unseen revisions can trigger optional triage. Commit jobs pin immutable revisions; a later head advance does not invalidate historical evidence.
- CPE selectors query NVD by product identity (`virtualMatchString` with wildcard version fields), because `cpeName` rejects wildcard versions. Deployed-version applicability is evaluated separately.
- Source snapshots omit binary media (images, fonts, audio, video) and hold up to 20,000 files / 64 MiB, so CMS-sized sources fit. Agent runs receive `source/` as one compressed archive input that the runner validates (regular files, safe paths, the same expanded bounds) and expands into the read-only input volume; other inputs keep the per-run input limit.
- Version recipes receive the release fingerprint map as `release-corpus.json` and only a coverage summary in the prompt. Numen writes `fingerprints.json` from the corpus unless the agent supplies an identical map. The corpus takes one installable package per release (an updater or patch package is skipped), drops the package's versioned top folder, and fingerprints only front-end files a site publishes as-is (`.js`, `.mjs`, `.css`, `.svg`, `.html`, readme/changelog/VERSION files); manifests, lock files, dependency metadata and hidden files are never fingerprinted or requested. It adds `probes` (files whose bytes differ between releases) and `resolution` (release groups the published files cannot separate). After a recipe's observe run, a version check runs Numen's own fingerprint stage (`fingerprint_probe.py`, budget 10, base URL from the recipe's `asset_base` on an allowed origin, a WordPress plugin directory, or the asset URL), fetching the probe that best splits the remaining releases until one group is left. The result narrows the observation: a single unmatched-free release becomes `detected` with medium confidence, several become `ambiguous` candidates, and a disclosure that contradicts the fingerprints becomes `unknown`.
- Automatic CVE analysis is held while a program has no successful source check; the baseline check dispatches held analyses.
- Audit context takes `max_functions` (1–100, default 24) per request: orientation lists significant functions most significant first, and Numen analyzes at most that many, each in its own agent run; any beyond the limit are recorded in coverage as `deferred`/`deferred_units` instead of failing the audit. A function analysis runs with a 1800-second deadline and is analysed once more (`:retry` phase) when it fails on its own (a timeout, invalid output, no document); broker, lease and cancellation failures still stop the audit. A selected path that is off by leading folders resolves to the one snapshot file it matches on a directory boundary; otherwise the function is recorded as failed. Function analyses run in parallel (`NUMEN_AUDIT_CONCURRENCY`, default 3), and the job's progress reports the stage and how many functions are analysed. An interrupted, failed, or cancelled audit continues instead of starting over: lease recovery, Retry, or an identical request (same source and skill revisions, focus, max functions, and agent profile) reuses the latest interrupted checkpoint's function selection and analysed functions (checkpoints store their records as `audit-functions.json`) and re-runs only unfinished or failed functions. A continued checkpoint is marked `continued_by` and never reused twice; `fresh` starts over. Synthesis receives the per-function records as `audit-functions.json` with only an index in its prompt, so record size does not reach the prompt bound. When synthesis follows the skill's `audit-context/DOSSIER.md` layout, Numen writes the `audit-context-building.md` entry document linking it.
- `POST /programs/{id}/audit-contexts` with `{refresh_from: <context id>, profile?}` refreshes that context for the current source head: the job keeps the base's focus and `max_functions`, reuses its orientation, keeps the documents of functions whose own file is byte-identical between the two snapshots, analyses functions in changed files again, records functions whose file was deleted as `removed`, and runs synthesis with the changed-file list (`coverage.refresh`: `from`, `from_revision`, `changed_files` (first 200), `changed_files_total`, `removed_units`). A base from another source generation or skill revision, or one with no analysed functions, is refused with `refresh_unavailable`; one already at the head with `context_current`. Finished contexts keep `audit-functions.json` for refreshes; an older context without it is rebuilt from its orientation and function documents. With program config `audit_auto_refresh` (default false), every source check queues such a refresh (idempotency key `audit-refresh:{program}:{head}`) when the newest context lags the head and no audit-context job is queued, running or cancelling; a refresh it cannot queue is recorded as an `audit_refresh_blocked` event and never fails the check.
- CVE analysis and finding artifacts start from the program's audit context (commit analysis judges the change on its own and never receives it): a complete one built at the analysed revision, else the newest complete one of the current source generation, else one with analysed functions at that revision, else the newest such. Its files arrive under `context/` (without `audit-functions.json`); above 4 MB the function documents are left out, and above that again the context is skipped with an `audit_context_skipped` event. Facts carry `audit_context: {id, source_ref, matches_revision, complete, functions_analysed, function_documents}` (null without one), the `audit-context` prompt section explains it as untrusted orientation to verify against the pinned source — at another revision possibly describing fixed code, so never evidence that a vulnerability is absent — and the job records `audit_context_supplied`.
- Jobs run concurrently. The worker runs `NUMEN_WORKER_CONCURRENCY` job slots (default 3) plus one slot that never claims long agent, lab, or login work, so source checks, CVE syncs, version checks, and notifications proceed during long audits. Claims stay row-locked (`SKIP LOCKED`) and attempts fenced. The broker runs up to `NUMEN_RUNNER_CONCURRENCY` workloads at once (default 4); each run has its own containers, networks, and gateway, and an agent run may use up to its 1 GiB memory limit. An attempt records every runtime phase it starts (`runtime_phases`), so failure handling and lease recovery cancel all of its runs and treat it as stopped only when each is terminal; once an operation is stopping, no new phase starts, and a phase that finds its attempt cancelled or lost cancels its own run.
- Agent runs have no execution deadline unless one is requested: the backend omits `timeout_seconds` and waits until the run ends, and requested agent limits refine the broker's defaults instead of replacing them. Audit function analyses request 1800 seconds; audit context has no cumulative time budget. Operators stop long runs by cancelling the job. Probe, lab, and login runs keep their time limits.
- A broker run is terminal only after owned workload cleanup is proved. Lost submission acknowledgement is resolved by authenticated attempt-token lookup; an unavailable broker/engine preserves cancelling/pending recovery instead of allowing overlapping replacement.
- API database transactions finish before an HTTP success is emitted, so a returned program/job/artifact identifier is immediately readable and a late constraint failure cannot follow a false success.
- Native connection setup supports protected cache import. Codex also supports device login, and Claude supports its manual OAuth login: the operator pastes the authorization code via `POST /api/accounts/{id}/login/code`, and the worker relays it to the running login workload. Command Code native connections run in Pi: the bundled plugin's login shows its Studio URL, and the operator pastes the resulting API key through the same endpoint. Native import accepts pi's or the Command Code CLI's `auth.json`. Pi automatic headless OAuth setup for other providers is not exposed as a working flow.
- The first lab verifier materializes pinned/local declarative Dockerfile instructions. Executable RUN/remote ADD are rejected explicitly; uploaded originals remain downloadable/unverified.
- The pinned Pi image applies a hash/integrity-verified brace-expansion security repair and audits the patched graph during build. See the runtime patch manifest and tests.
