# Implementation coordination contract

This is the shared contract for the first complete implementation, authorized by the user's “Build it” instruction. Preserve the PRD's outcomes and all three coding-agent choices. Each owner can make reversible local implementation choices within this boundary. Coordinate contract changes with the orchestrator before changing a consumer-facing shape.

## Ownership

- Backend agent: `backend/`, backend tests, migrations, domain services, scheduler/worker, API/security/persistence. Do not edit `runner/`, frontend, or root deployment files.
- Frontend agent: `frontend/`, its tests and package manifests. Do not edit backend, runner, or root deployment files.
- Runtime agent: `runner/`, root Dockerfiles/Compose files, runtime tests, and pinned agent/plugin/skill manifests. Do not edit frontend or backend modules.
- Orchestrator: root Makefile, bootstrap/backup helpers, integration fixtures/journey, documentation, cross-owner integration and final checks. When a correction belongs to another owner's active files, send it back to that owner.

All agents share the workspace. Preserve other owners' edits and adapt to their work. Read the PRD, design, and UI specification as governing context; these instructions settle serialization only.

## API

All paths below begin with `/api`. A session cookie authenticates requests. `GET /auth/session` returns `{authenticated: boolean, username?: string, csrf_token?: string}`. Login accepts `{username: "admin", password: string}` and returns the authenticated session shape. Browser mutations send `X-CSRF-Token` after login. Login allows 10 attempts per client address in 60 seconds, then `login_rate_limited` (429, retryable). An Approval (A15) is a mutation whose body carries `{password}`, checked against the Operator's password hash on that request alone: there is no re-authentication window, and a missing, empty or wrong password is refused with `approval_refused` (403, so the UI keeps the Operator signed in), also straight after a good Approval. Approvals are rate-limited like login in their own bucket (`approval_rate_limited`, 429), the password is stored and logged nowhere, and each granted one records an `actions` row `{action: approved, approved, ...}` on what it approved. Structured errors use `{code, message, fields?: object, retryable?: boolean}` with JSON; lists use `{items: array, next_cursor: string|null}`. Responses expose no secrets. IDs are strings; times use UTC ISO-8601.

### Domain records

Application fields: `id`, `asset_name`, `asset_url`, `product_kind`, `product_name`, `monitor_interval_seconds` (300 to 315,360,000: at least 5 minutes, at most 10 years; shown and entered in minutes, hours or days), `monitor_enabled`, `archived`, `source_generation`, `last_check_at`, `next_check_at` (both set by the scheduler and Check now), `repositories`, `unresolved_dependencies` (the active Own link's, else `[]`), `version` (latest observation or null), and `config`.

A repository is stored once per source URL and linked to each Application that uses it. GitHub URLs are normalized to `https://github.com/{owner}/{repo}` in lower case, without `.git` or a trailing slash; a WordPress.org plugin is `https://plugins.svn.wordpress.org/{slug}`. Its slug, ref and path are fixed when the row is created, so Applications sharing a URL share them. `repositories` lists the Application's links, the Own one first and then in the order they were added, removed ones included: `repository_id`, `role` (`own` or `upstream`), `enabled`, `removed_at`, `locked_version`, `locked_version_source` (`manifest`, `operator` or `deployed`), `release_branch`, `release_branch_status`, `packages` (the packages a derived Upstream link stands for, such as `npm:react`; `[]` for hand-added and Own links), `source_kind`, `source_url`, `plugin_slug`, `source_ref`, `source_path`, `cursor` (GitHub head or SVN revision), `baseline_revision` (the Baseline: the head when the repository was first checked), `last_check_at` (last successful check) and `last_error`. An Application has at most one active Own repository, which must be on GitHub, and may have none. Commits, snapshots, cursors and Triage belong to the repository, so a shared repository is polled and triaged once. Its new commits are triaged with the first linked Application that is not archived, links it enabled, and has Triage on; with none, they are not triaged. A GitHub repository is read only with a token from an Account with provider `github` (fine-grained, read-only: Contents and Metadata). Without one, the scheduler queues nothing for it and sets `last_error` to `github_token_required`; Check now queues the check, which fails with that code before any request. Every GitHub poll sends `If-None-Match` with the ETag of the last commit list; a `304` returns before any compare or commit request, advances neither cursor nor ETag, imports nothing and queues nothing (the check's result has `not_modified: true`). An Upstream GitHub repository also watches the Release branch of each Locked version that an enabled, not removed link of a not archived Application uses. The first branch that exists among `{major}.x`, `{major}.{minor}`, `release-{major}` and `v{major}` (the major and minor of `^v?(\d+)(?:\.(\d+))?`) is the Release branch; a check resolves a Locked version once, with `GET /repos/{repo}/branches/{name}`, and again only after it changes. `release_branch_status` is null for an Own link, a WordPress repository or no Locked version, `pending` until the next check resolves the current Locked version, `matched`, or `unknown` when no candidate exists (the UI says "release branch unknown"); then only the default branch is watched. Each Release branch keeps its own cursor and ETag in the repository's watched branches, is baselined at its head when first watched, and its new commits are imported with `branch` set to its name; a revision already imported from another branch is not imported again. A check is `not_modified` only when every watched branch answers `304`. Own and WordPress repositories watch their default branch only. WordPress.org plugins keep the SVN revision cursor and need no token.

The Application's source repository is its earliest linked repository that is not removed, whatever its role or on/off state; for a migrated Numen Program it stays the former source after an Own repository is added. Version recipes, version checks, audit contexts, CVE analyses and finding artifacts read it and fail with `repository_required` without one. `source_generation` is the Application's generation of that source: it advances only when the source repository's link is removed (the next earliest link then becomes the source), which clears the active recipe and the CVE cursor and marks audit contexts stale. Adding a repository or turning a link on or off changes neither.

Upstream repositories are derived from the Own repository by a `derive_upstreams` job. A check of an Own repository queues one, with idempotency key `derive:{application id}:{head}`, after its Baseline (when the link was never derived) and whenever an imported commit's `dependency_manifest` Pre-filter flag shows that it changed a manifest or lockfile; linking an Own repository that another Application has already checked queues one at once. The job reads `package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `composer.json` and `composer.lock` at that revision under the repository's path (`GET /repos/{repo}/contents/{path}?ref=`, raw). Direct dependencies are `dependencies`, `devDependencies` and `optionalDependencies` in `package.json` and `require` and `require-dev` in `composer.json`, without platform packages (`php`, `ext-*`, `lib-*`, `composer-*`). Versions come from the lockfile: `package-lock.json` v1 `dependencies` or v2/v3 `packages["node_modules/{name}"]`, `pnpm-lock.yaml` `importers["."]` (v6+, with the peer suffix removed) or its top-level maps (v5), `yarn.lock` v1 or Berry (the entry for the direct range, else the first), and `composer.lock` `packages` and `packages-dev`. Each package is mapped to its GitHub repository through `{npm registry}/{name}/{version}` (`latest` without a locked version, scoped names as `@scope%2Fname`) and its `repository` field, or for Composer through the `composer.lock` entry's `source.url`, else `{packagist}/p2/{vendor}/{name}.json` (the entry for the version, else the newest). The registry base URLs are `https://registry.npmjs.org` and `https://repo.packagist.org`; in test mode `NUMEN_NPM_REGISTRY_URL` and `NUMEN_PACKAGIST_URL` replace them. Packages mapped to one URL share one Upstream repository, found or created by URL (a derivation or request that creates it at the same time reads the other's row), and one link per Application. A new link is on at the first derivation and off afterwards, with the first package's Locked version recorded as `manifest`. An existing link gets the new `packages`, a new Locked version unless its source is `operator` or `deployed`, and is restored if it was removed. A derived link whose packages are all gone is marked removed and keeps its commits; hand-added links (no `packages`) and the Own link are never removed by derivation. A removed link that is added again by hand is restored as a hand-added link: its `packages`, `unresolved` and derived revision are cleared. A package with no repository metadata, a repository outside GitHub, a registry `404` or a registry body that is not its JSON object is listed in the Own link's `unresolved` (`unresolved_dependencies`: `{ecosystem, name, version, reason}`). A manifest that is not valid JSON or YAML, or is valid but of the wrong shape, fails the job with `invalid_manifest` and changes nothing; a failed derivation sets the Own repository's `last_error`. A derivation that added repositories sets `next_check_at` to now, so they get their Baseline on the next scheduler tick.

`config` contains `triage_mode` (`disabled`, `jev`, `pi`, `claude`; `codex` is refused with `validation_error` "Triage on Codex is refused until a no-tools restriction has been verified for it", though a configuration stored with it still loads), `profiles` keyed by operation, `cve_selectors` (list of typed selector objects), `cve_min_score`, `cve_versions` (subset of `3.0`, `3.1`, `4.0`), `cve_auto_analyze`, `active_recipe_id`, `monitor_interval_inherited`, `version_scheme`, `version_monitor_enabled`, `asset_origins`, `jev_connection_id`, and `jev_model_id`. Application `latest_version_check` supplies the latest failure independently of the last successful `version`. Agent operations are `commit_triage`, `commit_analysis`, `version_recipe`, `audit_context`, `cve_analysis`, `finding_artifacts`, and `patch_drafting`. A `commit_triage` profile on Codex, whether a default profile, an Application profile or the one an import resolves, is refused with `triage_codex_unsupported` (422); an import blocked that way records the commit as `blocked` with that reason. A `commit_analysis` or `cve_analysis` profile on Codex is refused the same way with `analysis_codex_unsupported` (422, "Analysis and CVE analysis on Codex are refused until a Codex mode without a shell has been verified"), because Codex always has a shell and those operations get only a read-only checkout and a write-only output directory (ADR-0004); a queued job with such a profile fails with that error, and an automatic Analysis is `blocked` with it. A `patch_drafting` profile on Codex is refused with `patch_codex_unsupported` (422, "Patch drafting on Codex is refused until a Codex mode without a shell has been verified") for the same reason.

Profile fields: `agent` (`pi`, `claude`, `codex`), `connection_id`, `model_id`, and nullable `reasoning_effort`. Server resolves defaults and validates every combination. These fields are identical for all operation submissions. Runtime receives a resolved provider/auth mode separately.

Commit fields: `id`, `repository_id`, `application_id` (the first Application that uses the repository: not archived, its link on and not removed; else the first that ever linked it. It is the context of commit pages and owns the commit's one Analysis; the Findings that Analysis opens are per affected Application), `revision`, optional imported `parent_revisions`, `message`, `author`, `committed_at`, `url`, `files`, `diff`, `diff_complete`, `prefilter`, optional `backfill` (true for a commit imported by a Backfill), optional `branch` (the Release branch it was imported from), `triage_status`, `triage_result`, `review_decision`, `verdict` (the newest Analysis's Verdict, null until one completes), `analysis_state` (null, or the latest Analysis job's `{status, job_id}` while `queued`, `{status: completed, analysis_id}`, or `{status: failed|timed_out, job_id, error}`; an automatic Analysis that has not started is `{status: waiting_for_cap, since, cap: application|account}` or `{status: blocked, error}`), and `analyses`. A diff is capped at 60,000 characters per file and 2 MiB in all; a capped diff, or one whose file patch the source omitted, has `diff_complete: false`. `prefilter` is the Pre-filter result recorded at import, `[{rule, paths}]` for the rules the change matches: `dependency_manifest` (`package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `composer.json`, `composer.lock`), `package_scripts` (a changed `package.json` line inside the `scripts` object as the hunk shows it, the `scripts` line itself, or a changed npm lifecycle hook: `install`, `prepare`, `prepublishOnly`, or `pre`/`post` with `install`, `pack`, `publish`, `start`, `test`, `stop`, `restart`, `version` or `shrinkwrap`), `ci_workflow`, `minified_or_obfuscated` (`*.min.js`/`*.min.css`, an added line over 1,000 characters, `_0x…` identifiers, `eval(atob(`, `String.fromCharCode(`) and `auth_or_crypto` (authentication, session, token, cryptography, signing, secret, key, permission and CSRF paths). It never changes `triage_status` or `review_decision`. Triage is one agent run with no tools and a 120-second deadline (`TRIAGE_SECONDS`), never a Herdr session. Its prompt carries the change as `facts.commit` (`message`, `author`, changed `files` paths, `diff` capped at 100,000 characters (`TRIAGE_DIFF_CHARS`) as its JSON in the prompt counts them, escapes included, and `diff_complete`, which is false for an incomplete or truncated diff), with no input files. The facts are appended as JSON with non-ASCII characters unescaped, so no diff pushes the prompt past the runner's 262,144-character bound. The runner returns the agent's raw reply as `{reply}`, and the broker accepts nothing else from a Triage run; application code takes the JSON object in it (from the first `{` to the last `}`, so a code fence or prose around it is tolerated), replaces configured secrets with `[redacted]`, and validates it against the Triage schema: `decision` (`security_candidate`, `unrelated`, `insufficient_context`), `title` (1–300 characters, a potential-issue title) and `reason` (1–2,000 characters), nothing else. Jev triage keeps its typed answer, which adds `change_kind`, `issue_type`, `confidence` and probabilities. Complete unrelated triage sets dismissed; uncertain input stays pending, and an unrelated decision on an incomplete diff becomes `insufficient_context`. A failed Triage run (a reply that fails the schema, a timeout, a provider error) sets `triage_status: failed` and `triage_result: {error, reason, attempt}` with no `decision`, so it is never read as unrelated, and leaves `review_decision` unchanged. Unless it was cancelled, lost its lease or its input changed, the worker queues the same Triage again with `attempt` n+1 and the same profile, not before n minutes, up to three attempts (`TRIAGE_ATTEMPTS`), and records `retry_job_id`. Each Triage run, agent or Jev, is stored as a Transcript: a `transcripts` row (`id`, `job_id`, `kind: triage`, `subject_id` (the commit), `data`, `created_at`) whose `data` holds the `prompt` and `reply` (Jev: the `request` body, which never holds the key, and the `response`) with configured secrets replaced by `[redacted]`, `status` (`completed` or `failed`), the `error` of a failed one, the `profile`, `run_id` and the runtime `execution` provenance. A failed run's Transcript is kept. Analysis (`commit_analysis`) returns exactly one Verdict: `verdict` (`Vulnerability fix`, `Vulnerability introduced`, `Malicious change`, `Security hardening`, `Unrelated`, `Insufficient context`; `schemas.VERDICTS`), `confidence` (`low`, `medium`, `high`), `title` (1–300 characters), `summary`, `evidence`, `open_questions`, `before_after`, `affected_behavior`, `vulnerable_ref` (a full revision, required with at least one evidence item for Vulnerability fix and Vulnerability introduced) and optional `addresses`: up to 50 commit SHAs (7–64 hex characters) or advisory ids (`CVE-…`, `GHSA-xxxx-xxxx-xxxx`, or another database's `PREFIX-id`) that the change addresses, kept in the result for linking to Findings. Nothing is run, so the result has no reproduction. Drafts are output files: report.md always, the Proof bundle (`artifacts.REQUIRED`) for Vulnerability fix and Vulnerability introduced, and `detection-rule.yar` (a YARA Detection rule) for a Malicious change, all saved with the analysis artifacts. A Malicious change also returns `indicators` (`files`, `hosts`, `urls` and `commands`, each up to 100 strings of 1–240, 1–253, 1–2,048 and 1–2,000 characters; no hashes, which application code computes) and `reachable_secrets` (up to 50 names of 1–300 characters, never values); the schema requires both for that Verdict only. Its review decision is `candidate` for Vulnerability fix, Vulnerability introduced and Malicious change, `dismissed` for Security hardening and Unrelated, and `pending` for Insufficient context, which puts the change in the Review queue. The opening Verdicts (`domain.OPENING_VERDICTS`: Vulnerability fix, Vulnerability introduced, Malicious change) open one `commit`-source Finding in each affected Application (`domain.affected_applications`: every Application whose link to the repository is on and not removed, the Application not archived; an Own link always counts, and an Upstream link counts because Exposure is unknown until Phase 7, which counts as exposed). In each such Application the change is linked to the Findings, in any state, that its `addresses` name (see Finding fields): a Vulnerability fix linked that way opens nothing, while a Vulnerability introduced or Malicious change fixes nothing and opens its own Finding as well. Vulnerability fix and Vulnerability introduced publish the drafted bundle to each such Finding that is Open or Confirmed, once per Application; a Dismissed or Remediated one keeps the evidence and bundle it was closed with, and `target_applicability` is never reset. An incomplete bundle is published as a draft (`artifact_state.status: draft`) and the job still succeeds. A drafted `vulnerable_ref` that fails validation (`invalid_finding_revision`) publishes no bundle: the Findings still open and alert, the job succeeds, and the error is kept as `bundle_error` in the Analysis and job results. A Malicious change publishes a static Proof and a cleanup report to each such Open or Confirmed Finding instead (see Finding fields). `workflows.check_verdict(result, served_content)` refuses a served-content Analysis that returns Vulnerability fix or Vulnerability introduced with `verdict_not_allowed` (422), which fails the job; commit Analysis may return all six. Analysis and CVE analysis request a 30-minute deadline (`timeout_seconds` 1800, `ANALYSIS_SECONDS`). A failed or expired Analysis sets `analysis_state` to `failed` or `timed_out` (error `timeout` or `runtime_timeout`) and leaves `verdict` and `review_decision` unchanged, so an expired deadline never reads as Unrelated. Migration `9f7a8ba3c2d7` rewrote Numen's stored commit analysis results (analyses and jobs) from its `category` to a `verdict` by the PRD's AC-A04 table, with `confidence: unknown` and Numen's confidence object kept as `numen_confidence`; Numen's other fields stay as they were, and each commit's `verdict` is its newest analysis's. Late manual review actions take precedence over automatic review-decision updates. The commit pages show `verdict` with its newest analysis's confidence (`unknown` for a migrated one), `analysis_state` as Queued, Waiting for cap (with its cap), Timed out after 30 minutes, Blocked or Failed (with the error message), and `prefilter` beside the Triage result even when Triage rejected the change; a `failed` or `blocked` Triage reads as Triage failed or Triage blocked, never as unrelated. The Review queue is a Show filter of the commit list (`verdict` Insufficient context, `review_decision` pending) and a dashboard panel fed by `review_queue`.

Commit analysis is read-only like CVE analysis: it reads the pinned revision's snapshot at `inputs/source`, writes only to `outputs/`, and builds and runs nothing, so a bundle it writes is a draft that only a Lab run verifies. Its `own_repository` fact tells it whether an Application links the repository as Own, so the bundle leaves the repository itself to the Lab. Each Application has at most one Finding per commit that the Analysis opens; re-analysis reuses it, in whatever state, preserving its operator title, lifecycle status and cause, so a Dismissed or Remediated Finding is never reopened and a different opening Verdict opens no second one. Fix findings must pin a verified parent revision; introductions must pin the analyzed revision. A Git application lock must match that revision. Finding generation reuses this validated vulnerable source instead of the current fixed checkout. Linked immutable analysis output remains separate from the finding's current artifact revision. Vulnerability fix and Vulnerability introduced publish their drafted bundle, an incomplete one as a draft, and the job still succeeds; a Malicious change publishes its static Proof as a draft; the other Verdicts need a report only. Job results expose `commit_id`, `analysis_id`, `finding_ids` (every Finding opened or reused) and `finding_id`, `artifact_revision` and `artifact_state` of the job Application's Finding (`finding_id` null when that Application linked the change or does not use the repository); the analysis `result.finding_id` is the same.

Resolve legacy commit parents and any vulnerable-source snapshot before acquiring the publication fence. Source I/O renews the job lease through a separate connection and must never run while that same job is locked by publication. Invalid revision proposals still retain the analysis/report and fail without creating a finding; publication remains fenced against cancellation and replacement attempts.

CVE fields: `id` (CVE ID), `application_id`, `title`, `description`, `published_at`, `modified_at`, `scores`, `match_status`, `eligible`, `eligibility_reason`, `applicability`, `affected_versions`, `fixed_versions`, `references`, and `analyses`. Score entries contain `version`, `base_score`, `vector`, `source`. Keep per-Application match/eligibility separate from global records.

Finding fields: `id`, `application_id`, `source` (the Finding source: `commit`, `served_content`, `advisory`, or `cve` for a CVE record carried over from Numen; fixed at creation, a change is refused with `immutable_source`), nullable `source_ref` (the source's short SHA, Watched page or advisory id), nullable `cve_id`, `title`, `status` (the A11 lifecycle state: `open`, `confirmed`, `dismissed`, `remediated`), `cause` (who or what set the current status: `{by, at, ...refs}`; `by` is `operator` (with `reason`), `verdict`, `cve_analysis` or `numen` for an opened or carried-over Finding, `proof`, `detection_rule` or `advisory` for a confirmation, and `remediation_pr`, `version_bump`, `baseline_match` or `deployed_version` for a remediation), `deployed_version` (shown apart from the lifecycle; `unknown` until the Deployed version check exists), `affected_versions`, `fixed_versions`, `target_applicability`, `source_commit_id`, `source_analysis_id`, `artifact_state`, `artifacts`, `lab_runs`, `own_repository` (whether the Application has an Own repository; without one the Remediation PR steps show "no Own repository" and are skipped, A06), `remediation_actions` (the drafts `POST /findings/{id}/remediation-prs` accepts: on a commit of the Own repository, `[revert]` for a Malicious change, and `[patch, revert]` for a Vulnerability introduced or a commit with no Verdict yet (a Finding the Operator opened); none for any other Verdict, so a Vulnerability fix is never reverted), `remediation_prs` (the Finding's Remediation PR records, oldest first, each with its record fields and `data` spread: `revision`, `dependency`, `job_id` (the draft's job, then the PR step's once approved), `since` and `cap` while waiting, `summary`, `paths`, `flags`, `error`, and once opened `branch`, `pull_number`, `pull_url`, `head_sha`, then `merge_commit_sha` once merged), `created_at`, `updated_at`. `artifact_state` is `{status: "draft"|"complete", missing: string[], limitations: string[], vulnerable_version: string|null}`; Draft is artifact completeness only (Numen's AC-12), never a lifecycle state. `malicious_change` is true when a Malicious change Verdict opened the Finding or is its source commit's newest Verdict. A Malicious change's Finding (A07) carries `static_proof` and `cleanup_report` in place of a Proof bundle. Commit Analysis publishes to each Open or Confirmed one a revision of `report.md`, `indicators.json` and, when drafted, `detection-rule.yar` (`detection.STATIC_REQUIRED`). `static_proof` is `{analysis_id, indicators, artifact_revision, files, rule, status: pending|failed|validated, checks: [{name, status, message, files?, count?}], job_id}`. Its `indicators` are the agent's as `detection.check_indicators` kept them: `files: [{path, sha256}]`, each a path commit.json lists as added or changed (an SVN path names the snapshot's file by suffix), hashed by application code from the commit's snapshot; `hosts`, `urls` and `commands` that occur in a line the diff adds; and every other value in `rejected: [{kind, value, reason}]`. Each new revision, from Analysis or an upload, sets `status` to `pending` with no checks and queues its validation, a `detection_rule` job with input `{finding_id, artifact_revision}` and idempotency key `detection-rule:{finding id}:{revision}` (`job_id`), or sets it to `failed` with the `rule` check, and queues nothing, when no rule was drafted, it is over 64 KiB or it is not UTF-8. The job reads `detection-rule.yar` from that revision and the trees from stored snapshots, fetching a missing one through the read-only GitHub tarball or SVN export: the files the commit added or changed (`detection.changed_files`), the parent tree (`parent_revisions[0]`, else GitHub's parents, the SVN revision before, or empty for a root commit) and the repository's `baseline_revision` tree, which is skipped for a Backfill commit, when it is the parent, or when the repository has no Baseline. It runs the runtime `detection_rule` kind with no profile, then `detection.checks` turns the result into the checks `rule` (compiles), `changed` (matches at least one file), `parent` and `baseline` (match no file), each tree check with the matched `files` and `count`; a rule that does not compile has only the `rule` check, and a malformed result fails the job with `invalid_rule_result` (422). If the Finding's revision is still that one, every check passing sets `validated` and confirms the Finding with cause `{by: detection_rule, artifact_revision, job_id}`; a failed check sets `failed` and leaves the lifecycle state as it was. A result for a superseded revision is kept on its job only (`current: false`). A job that fails leaves `pending` with its `job_id`, and the Operator retries it. A static Proof's `artifact_state` is `complete` only once `status` is `validated` with every required file present; until then it is `draft`, and its limitations are the failed checks' messages or "The Detection rule has not been validated yet". `cleanup_report` is `{analysis_id, commits: [{revision, commit_id}], commits_truncated, releases, secrets}`: `commits` are the commit, then the stored commits of the same repository, source generation and branch with a later `committed_at`, oldest first, and for a Backfill commit the Baseline (`commit_id` null when it is not stored), at most 100; `releases` are the GitHub tags that point at one of them, or null when unknown (a WordPress plugin, or the tag request failed); `secrets` are the agent's `reachable_secrets`. A later Analysis of the commit with another opening Verdict removes both from an Open or Confirmed Finding. Neither is ever sent: an Alert holds only its fixed template's fields. Every Finding opens `open`. `domain.open_finding(db, application, source, subject, title, ref, cause)` opens the Application's Finding for a subject (the commit by `source_commit_id`, the CVE by `cve_id`, a served-content change or advisory by `data.subject_id`) or returns the existing one unchanged, in any state; an opened one records an `actions` row `{action: opened, cause, source_ref}`. Commit Analysis and CVE analysis use it; the served-content (cause `{by: verdict, verdict: Malicious change, confidence}`, `source_ref` the Watched page) and Advisory check (cause `{by: advisory, advisory_id}`) callers arrive in Phases 9 and 8. `domain.link_change(db, application, addresses, change)` maps an Analysis's `addresses` to that Application's Findings only, in any state (a fix addressing a Dismissed or Remediated Finding is linked to it and opens nothing): a commit SHA (7–64 hex characters) matches the prefix of a Finding's source commit revision, any other id its `cve_id` or an advisory Finding's subject; the change's own Finding is skipped. Each match gets an `actions` row `{action: linked, commit_id, revision, analysis_id, verdict}` in its `events` and keeps its status and cause; a change linked once returns the same Findings on a repeat Analysis and is never opened. A Finding may reference the Analysis of a shared Upstream commit, which belongs to the first Application that uses it: `domain.analysis_reaches` accepts an Analysis of the Application's own or of a commit in a repository it links, for `POST`/`PATCH /findings` and finding generation. `domain.transition_finding(db, finding, state, cause)` is the one lifecycle move: `open` to `confirmed` or `dismissed`, `open` or `confirmed` to `remediated`; it raises for a cause that cannot set that state (only the Operator dismisses), returns false and changes nothing from any other state, and records an `actions` row `{action: transition, from, to, cause}` that appears in the Finding's `events`. A verified Lab run confirms its Finding (`{by: proof, lab_run_id}`); a not-reproduced one changes nothing, and so does a failed one (over a limit, for instance), whose Lab run is `failed` with `{error}`. For a `commit` Finding whose source commit is in a repository the Finding's Application links as Own, the Lab's vulnerable app is that repository at the commit (the Verdict's commit), read from its stored snapshot and placed under `vulnerable-app/` beneath the bundle's own files, which win; the snapshot's `manifest.json` is left out, and so is the repository's `.dockerignore`, which belongs to the Dockerfile the bundle replaces and would keep the fetched `node_modules` out of `COPY . /app/`; the Lab run records `source_ref` (the commit's revision). Completeness is still judged on the bundle alone, so such a bundle carries its Dockerfile and uses `COPY . /app/`. Other Findings' Labs are built from the bundle alone until Phase 7. PATCH edits only `FindingInput` fields and never the status, cause or server-owned keys (those starting with `_`); `source_ref` follows the edit as `POST` sets it: a `cve` Finding's CVE id, a `commit` Finding's source commit short SHA (else its CVE id). CVE analysis refreshes an Open or Confirmed Finding's evidence, versions, applicability and bundle; a Dismissed or Remediated one keeps them. Migration `a08b9cb4d3e8` renamed `kind` to `source` (`0day` to `commit`, `cve` kept), mapped status `fixed` to `remediated`, and added `cause: {by: numen}` and `source_ref` to every Finding, leaving artifacts and other data untouched; its downgrade is refused while any Finding is confirmed or dismissed or has a `served_content` or `advisory` source. Analysis records expose structured output under `result`; CVE `qualifying_score` names the gate witness.

Remediation PR records (A08; table `remediation_prs`, migration `b19c0dd5e4f9`) hold `application_id`, `finding_id`, `repository_id` (the Own repository), `subject` (the Commit's id; a vulnerability for an Advisory check), `action` (`patch`, `revert`, `pin`, `bump`), `status` (`drafting`, `waiting_for_cap`, `draft_failed`, `ready`, `approved`, `failed`, `open`, `merged`, `closed`), nullable `base_ref` (the revision the diff applies to), `diff` and `diff_sha256`, and `data`. (`application_id`, `subject`, `action`) is unique: ADR-0004's idempotency key, so at most one pull request is opened per key. Deleting a Finding deletes its Remediation PRs. `numen/remediation.py` holds the application-code mechanics, run with no network: `apply_diff` validates a diff against a snapshot and applies it in a temporary git checkout, refusing it with `diff_rejected` (422) and the failed check (renames and copies are refused: write them as a deletion and an addition); `tree_diff` writes git's own diff between two file maps (a revert); `dependency_files` edits `package.json` and `package-lock.json`, or `composer.json`, for a pin or a bump (`dependency_not_found`, 422, for a package that is not a direct dependency); `branch_name(revision, action)` is `asset-monitor/<short-sha>-<action>`.

Drafting (A08, the A06 Own column). `domain.draft_remediation(db, application, finding, subject, action, revision, automatic, dependency, submitted)` gets or creates the record for its key (a concurrent draft that creates it first wins) on the Application's Own repository (`domain.own_repository`: its Own link, not removed) and returns None, drafting nothing, without one, or when a patch or revert's commit is not of that repository; a `waiting_for_cap` record of that key then becomes `draft_failed` with `not_own_repository` (its Own link was removed or replaced while it waited), and its `repository_id` is kept. A record that is `drafting`, `approved`, `open`, `merged` or `closed` is left alone (a manual draft gets 409 `remediation_busy`); otherwise the new draft clears `base_ref`, `diff` and `diff_sha256`, sets `status: drafting` and `data: {revision, dependency, job_id}`, and queues its job. A patch is a `patch_drafting` agent run with input `{remediation_pr_id, finding_id, automatic, shared: false}` and the Application's `patch_drafting` profile (an automatic one needs an API-key account, A13); there is no fallback profile, so without one an automatic draft is `draft_failed` with `profile_required` (or `api_key_required`). An automatic patch counts against the Analysis caps (`domain.over_cap`); over a cap it is `waiting_for_cap` with `data.since` and `data.cap`, and `domain.start_waiting` starts it, after the waiting commits and oldest first, once the caps allow. A revert, pin or bump is a `remediation_draft` job (`{remediation_pr_id, finding_id}`, no profile, not capped). An automatic draft never raises into the Analysis that queued it. Commit Analysis drafts automatically for each affected Application whose Own repository is the commit's, once its Finding is Open or Confirmed: a patch after Vulnerability introduced (not for a Finding a Malicious change opened) and a revert (the Cure's) after Malicious change; an Upstream Verdict drafts nothing here (Phase 7). `patch_drafting` snapshots the Own repository at its cursor (its default-branch head; else the commit's revision), gives the agent `source/` (read-only), `commit.json` (and `prior-analyses.json`), and `analysis-report.md` (the Finding's source Analysis report) with a 20-minute deadline (`timeout_seconds` 1200, `workflows.PATCH_SECONDS`), and needs `outputs/patch.diff` (`missing_patch`) and a result `{summary: 1..4000 characters, workflows?: boolean}`; `workflows: true` allows and flags a `.github/workflows` change. `remediation_draft` drafts on the head: a revert is `tree_diff` from the commit's tree to its first parent's (`parent_revisions[0]`, else GitHub's parents; a root commit is `revert_unavailable`), with workflow changes allowed and flagged. A path the commit changed (`data.files`, its `path` and `previous_path`) that neither snapshot holds (binary media, a symlink or another non-regular file) fails the draft with `revert_incomplete` (422) naming it, rather than revert only part; with a `source_path`, the summary says changes outside it are not reverted (a commit's `data.files` holds only the paths under it); a pin or bump reads `data.dependency` `{ecosystem: npm|composer, name, version}`, takes the npm dist from the registry (`Sources.npm_version`, `dependency_version_unknown` when it does not have it) and edits the manifest (and `package-lock.json`) at the repository's `source_path`. Every draft then goes through `apply_diff` against the base tree with the repository's `source_path`, and the stored `diff` is git's own diff of the result (`tree_diff` of the touched files), so what an Approval approves is exactly what is pushed; `diff_sha256` is its SHA-256, and `status: ready` with `base_ref`, `data.summary`, `paths` and `flags`. An empty result is `nothing_to_change`. A draft whose job fails, its diff rejected or anything else, is `draft_failed` with `data.error` and no diff to approve; the Finding is untouched. A result for a superseded draft stays on its job only (`current: false`). Patch drafting gets the same tools as Analysis and Codex is refused for it; the write token is never among its inputs (every stored credential is refused there with `secret_in_input`).

Opening (A08). An approved draft (`POST /findings/{id}/remediation-prs/{remediation_pr_id}/approvals`) queues one `remediation_pr` job `{remediation_pr_id, finding_id, diff_sha256}` with no profile. The job refuses a record whose repository is no longer the Application's Own repository (`not_own_repository`, 409), or that is no longer `approved` with that hash (`input_changed`, 409). It applies the stored diff to the `base_ref` snapshot again before any GitHub request. Only then does it make requests with the write token (`Workflows.write_client`, the only place they are made; `github_write_token_required`, 422, without a `github_write` account). `remediation.open_pull_request` works only on `asset-monitor/<short-sha>-<action>` (`unsafe_branch` otherwise):
- An existing branch is reused when its head commit's message and parent are this change's, else the job fails with `branch_exists` (409).
- A new branch gets one blob per changed file and a tree on the base commit's tree. Each file keeps its mode from GitHub's recursive tree, a new file is 100644, and a deleted one has `sha: null`. A path that is, or sits under, a symlink or submodule there is `diff_rejected`, and a truncated listing is `tree_truncated`. Then a commit whose only parent is `base_ref` and `refs/heads/<branch>`.
- Each touched path must be on GitHub exactly as the snapshot held it: its blob's git object id (`remediation.blob_sha`) equals the listed entry's `sha`, and a path the diff creates is not listed. A tarball applies `.gitattributes` (line endings, `export-subst`, `export-ignore`), so a mismatch is `diff_rejected` before the first write.
- An existing pull request for the branch (`state=all`) is reused, else a `draft: true` one is opened against the repository's `source_ref` (the branch its cursor and merge check follow), else its default branch.

Title, body and commit message are fixed application text: `Asset Monitor <action> of <short-sha>`, the Finding's dashboard link, and `Approved diff SHA-256: <hash>` in the message. Writes are single requests that are never retried (`Sources.send`). A 4xx is `github_write_failed` with GitHub's status and message, bounded to 300 characters; a 5xx is the same but retryable; an unreachable GitHub is `github_unavailable`. A crashed attempt is recovered by lease expiry and finds its branch and pull request by name, so at most one is opened. The record becomes `open` with `data.branch`, `pull_number`, `pull_url` and `head_sha`, and an Action `{action: remediation_pr_opened, remediation, remediation_pr_id, diff_sha256, branch, pull_number, pull_url, head_sha}`. A failed or cancelled job leaves the record `failed` with `data.error`, to approve again; the Finding is untouched. `domain.remediation_job_ended` does this for every draft and PR job: on a failure in the worker, on `POST /jobs/{id}/cancel` of a queued one (`data.error.code: cancelled`), and when `queue.recover` finalizes a `cancelling` one; a draft job leaves its record `draft_failed` the same way. Nothing merges, moves a ref, writes a default branch or writes to any other repository.

Merging (A08). The Operator merges. Every source check, a 304 included, reads each `open` record of that repository with `remediation.pull_state` (`GET pulls/{n}`: `state`, `merged`, `merge_commit_sha`) through `Workflows.write_client`, before its fence: a fine-grained read token cannot read pull requests on a private repository. A failed read (such as `github_write_token_required`) is kept as the record's `data.error` and never fails the check; the next successful read clears it. Inside the fence, after the poll's commits are imported (`Workflows.pull_request_state`):
- `merged` with a `merge_commit_sha` that is a Commit of this repository (a merge commit, the squash commit or the last rebased commit, all on the default branch): the record becomes `merged` with `data.merge_commit_sha`, an Action `{action: remediation_pr_merged, remediation, remediation_pr_id, pull_url, merge_commit_sha}` is recorded, and `domain.transition_finding` moves the Finding to Remediated with cause `{by: remediation_pr, remediation_pr_id, pull_request (its URL), merge_commit}`. A Dismissed or Remediated Finding stays as it is.
- `merged` with a merge commit that no poll has imported yet: nothing changes until the poll that imports it.
- `closed` and not merged: the record becomes `closed`; the Finding is unchanged.

The Finding page's Remediation PRs panel is the Approval screen. Each record shows its `action`, `status`, `summary`, `error` (a failed draft, PR step or pull-request read), a warning for the `workflows` flag, `base_ref`, `branch`, a `pull_url` link (only an `http(s)` URL, `rel=noreferrer`) and its `diff` as React text with its full `diff_sha256`, never as markup. Each bidirectional control or zero-width character in the diff (U+061C, U+200B to U+200F, U+2028 to U+202E, U+2060 to U+2069, U+FEFF) is shown as a visible `⟨U+XXXX⟩` escape under a "Hidden characters" warning; the hash stays that of the stored bytes. Approve, on a `ready` or `failed` record, opens the same password dialog as Start Lab and posts `{password, diff_sha256}`. Draft patch and Draft revert post `{action}` for each of `remediation_actions`, disabled while that action's record is `drafting`, `approved`, `open`, `merged` or `closed`. With `own_repository` false it reads "No Own repository: Remediation PR steps are skipped." The Jobs page offers no Retry for `remediation_pr`, `patch_drafting` or `remediation_draft`.

A `merged` or `closed` record is not read again. An `open` one is read on every check, so a merge commit imported by a poll whose read failed is still seen by a later poll with nothing new.



Finding version arrays accept strings and structured evidence objects. The UI renders their product/range/version labels and preserves structured evidence when an operator edits unrelated fields. `GET /findings?view=summary` returns identity, source, lifecycle status and cause, Deployed version, versions, exposure, source links, artifact revision/completeness, timestamps, and nullable `lab_status` for the latest lab run; it omits artifact inventories, evidence, events, and lab histories. The register, Application counts, and quick search use this projection. The default list and individual finding responses retain their full fields. The register shows each Finding's source (`Commit abc1234`, the CVE id, `Advisory GHSA-…` or `Watched page /path`) and its State with the cause under it. The Finding page has a Lifecycle panel with the state, the cause and its time, and the Operator's Confirm and Dismiss (Open only) and Mark remediated (Open or Confirmed) buttons, each sending a required reason to `POST /findings/{id}/transitions`. Its History lists the opened, linked (the change's short revision, linking to its commit, and Verdict) and transition (from → to and cause) events, and older events by their action name. The Deployed version is a separate row (Unknown until Phase 7) under the hint that a fix in the repository does not mean the Asset serves it. The commit queue and commit page link each Finding a commit opened or was linked to as `{State} finding · {Application}`, prefixed `Linked:` for a linked one. The commit review decision that sets `confirmed` is labelled Confirm revision, so Confirm names only the Finding lifecycle action.

Finding completeness is recorded with the published artifact revision in server-owned finding data. Edits preserve it, public responses omit the private record, and request bodies cannot override it. A missing or older revision summary is derived from published path/size metadata and integrity-checked Dockerfile/lock contents. Reading a finding describes its published bundle; full byte integrity remains enforced on preview, download, upload merge, and lab execution.

Each agent operation's prompt is rendered from its template in `backend/numen/prompt_templates/operations/`, which includes the shared sections it needs from `sections/` (`rules` for all; `attack-path` and `bundle` for commit analysis, CVE analysis and finding artifacts; `detection-rule` for commit analysis; `source-pin` and `audit-context` for CVE analysis and finding artifacts; `audit` for the three audit phases). Templates are Jinja rendered in a sandbox; operator versions saved through `/prompts` override the shipped defaults by name and apply to the next job. Numen appends `Facts:` and the run's facts as JSON after the rendered template, and a job whose prompt used a customized template records a `prompt_customized` event naming them. Finding regeneration sends bounded identity/source facts in the prompt and supplies operator fields and evidence in `finding.json`. Its linked `analysis.json` preserves analysis identity/results without the artifact inventory, alongside the integrity-checked original `analysis-report.md` and pinned source. Generation does not read every saved analysis artifact or inline file inventories and histories into the bounded runner prompt. Public analysis/detail responses retain their full artifact inventories.

CVE analysis drafts the full n-day bundle in its read-only analysis run, which builds and runs nothing, and creates or updates its Application's CVE finding, preserving an existing finding's title and lifecycle status. Analysis `result.finding_id` and job `result.finding_id` link to that finding; earlier analysis files remain immutable. Both CVE analysis and finding generation (unlike commit Analysis) require all paths in `artifacts.REQUIRED` and a valid pinning declaration before the job succeeds. Incomplete bundles are published as drafts, the job retains artifact/finding/analysis identifiers in `result`, and fails with `incomplete_bundle` and `partial_output_retained:true`. Finding generation receives the linked analysis JSON, original report and pinned CVE record as evidence. Generation never verifies reproduction or automatically closes a finding; unsupported lab build steps remain explicit prerequisites.

Job fields: `id`, `kind`, `application_id`, `status`, `progress`, `profile`, `created_at`, `started_at`, `finished_at`, `error`, `result`, `events`. Job submission returns `202 {job_id, status_url}`. Idempotency keys are supported. Profile/input changes create a new job; a retry reuses the recorded profile/input.

## Runtime broker contract

The internal broker is authenticated by `X-Broker-Token` from `NUMEN_BROKER_TOKEN`. URL environment: `NUMEN_BROKER_URL`. Its default port is 8081. Frontend callers never access it.

`POST /internal/runs` accepts `{attempt_token, kind, profile, prompt, output_schema, inputs, limits, target_policy?}`; `build` and `repository` are refused as unknown fields, because no agent run builds anything or receives a repository mirror (ADR-0004, ADR-0005). `profile` extends the public profile with `provider_id`, `auth_type`, and a protected `credential` envelope. Inputs are an array of `{path, content_base64}`. Paths are safe workspace-relative files. Limits and kind map to hardcoded broker-controlled profiles; caller values can lower limits, not exceed configured maxima. Prompt/schema never contain credential values. The broker does not accept arbitrary container flags, host mounts, images, or command strings.

Kinds include `agent`, `probe`, `lab`, `detection_rule`, `capabilities`, and `account_login`. `agent` has an `operation` in the profile. Probe inputs include the recipe/script and JSON target input; lab inputs include the finding bundle; `detection_rule` inputs are `rule.yar` and the `changed`, `parent` and, except for a Backfill commit, `baseline` trees, each one archive input. `target_policy` scopes origins/methods and request budgets.

A `lab` run carries and builds a whole application, so it is bounded like a build rather than like an analysis: its bundle travels as one compressed archive (up to 65536 expanded files and 512MB), its ceiling is `LAB_MAXIMA` (`timeout_seconds` 600 for the run, `build_seconds` 900, `image_bytes` 4 GiB, `memory_mb` 8192, `cpus` 4, `pids` 4096, `output_bytes` 64MB, `input_bytes` 512MB; ADR-0005), callers may only lower them, and the per-run 512-file limit no longer applies to it. The backend's lab defaults are 600 s, 900 s, 4 GiB, 6144 MB, 2 CPUs and 4096 pids, and it waits up to 1800 s for a Lab. `build_lab` accepts an ordinary Dockerfile — `RUN`, multi-stage and continuations included — and builds it with no network, after phase one: only a Node bundle (`vulnerable-app/package.json`) is accepted, otherwise `lab_stack_unsupported`, and a fixed container fetches its dependencies with `npm ci`/`npm install --ignore-scripts`, no credential (a `lab` request with one is refused) and egress only through a gateway allowing the `NUMEN_NPM_REGISTRY_URL` host; the Lab base's global npmrc sets `ignore-scripts=true` for npm in the build and the run too. `FROM` must name the bundled `asset-monitor-lab:0.1.0` (pinned Node 24.9.0 and npm), `scratch` or an earlier stage, `COPY --from` must name an earlier stage, `COPY`/`ADD` sources stay inside the bundle and are never URLs, and build mounts and privileged build flags are refused. The Dockerfile is read as the Engine reads it (`engine.instructions`, mirrored by `artifacts.dockerfile_instructions`): a comment line is dropped before continuations are joined, so a trailing backslash never continues one; a parser directive (`# escape=`, `# syntax=`) and a `$` variable in `FROM`, `COPY` or `ADD` are refused, because they would make the Engine build something other than what was checked. The build context gets exactly those instructions. A `LABEL` with the run's labels follows every `FROM`, so a failed or interrupted build's layers are removed with the run; cleanup also removes the `asset-monitor-lab-job:<run>` tag by name. A watchdog stops a build at `build_seconds` even through a silent step (`timeout`), and a built image over `image_bytes` fails with `lab_image_too_large`; either way no image is left. The application container then runs with a writable root filesystem, its image's own user and an ordinary capability set, on the internal job network only, with no route out and none to the application or control network. The run's `timeout_seconds` starts after the build. The container that runs `poc.py` keeps the bounded, nonroot, network-isolated profile, so an observed proof comes from the application and not from the network. A failing PoC's error stream is returned with its result.

A `detection_rule` run validates a Detection rule (A07) and never runs what it scans. It uses the probe image, which carries the pinned yara 4.2.3, with `network_mode none`, no credential (a request with one is refused) and no Docker socket; its ceiling is `RULE_MAXIMA` (`timeout_seconds` 600, `memory_mb` 1024, `cpus` 2, `pids` 64, `output_bytes` 8MB, `input_bytes` 256MB), which callers may only lower. The backend requests 1 CPU and the ceiling otherwise. A rule using `include` or the `console` module is refused before compiling. The result is `{compiled: false, error}` for a rule that does not compile, otherwise `{compiled: true, error: null, matches: {changed|parent|baseline: {files, count}}}` for each tree sent, with paths relative to the tree, at most 1000 files listed and `count` the full number. A scan error fails the run with `Detection rule scan failed`; it is never read as no match. It writes no outputs. See `runner/README.md`, Detection rules.

Every agent run is read-only. Its inputs, including `inputs/source`, the pinned revision's source snapshot without git history, are staged read-only, only `outputs/` is collected from it (Pi and Claude can write nowhere else; where Codex runs, its sandbox can write elsewhere in the `/workspace` tmpfs), and it has no Docker daemon, socket or client. Its tools are fixed per operation in `runner/numen_runner/adapters.py` by the flags that decide which tools exist, never by `--allowedTools`: Triage (`commit_triage`) gets no tools at all: Claude runs `claude -p --output-format json --tools '' --setting-sources '' --strict-mcp-config --mcp-config '{"mcpServers":{}}' --no-session-persistence` (plus `--bare` for an API key), Pi runs `--print --mode json --no-tools` with every discovery switched off, and Codex is refused because it has no flag that removes its shell. Every other operation writes under `outputs/`: Pi gets only its bundled read/list tools, `numen_write` under `outputs/`, and `target_fetch` for `version_recipe`; Claude gets `Read,Grep,Glob,Write,Edit` under `--restricted` and `--permission-mode dontAsk`, with `--settings` approving file edits under `//workspace/outputs/**` and, for `version_recipe`, the target MCP tool; Codex is refused for Analysis, CVE analysis and patch drafting too, and for the operations it still runs keeps its shell in its native `:workspace` sandbox with network off except for `version_recipe`; neither Pi nor Claude gets a shell tool. The credential-free gateway allows CONNECT only to the selected provider's hosts, plus `herdr.dev` for an agent run that hosts a Herdr session (`engine.gateway_config`; Triage never does); every other host, package and source registries included, is refused before any DNS lookup.

A commit analysis on an incomplete upstream diff (a merge or an oversized change) never stands as Unrelated or Security hardening: the snapshot has no history, so the whole change cannot be reviewed, and either Verdict is recorded as Insufficient context, so the commit stays pending in the Review queue. Analysis prompts require the attacker, least privilege, source, propagation, sink and trust boundary to be established before drafting a bundle, and a reproduction to deliver the payload only through that source as the least-privileged attacker and observe it at the sink, never by writing the payload into storage directly; a shortcut reports `not_reproduced`. Analysis itself reproduces nothing: its bundle is a draft for a Lab. A commit's `commit.json` input describes the revision only; earlier analyses travel separately as `prior-analyses.json`, labeled untrusted prior analysis to be used only as a checklist and never as a verdict, without their artifacts or finding links.

`ExecutionContext.progress` records runtime lifecycle events as job events, once per run and type. The recognised types are `lab_started`, `lab_application_exited`, `lab_dependencies`, `lab_build`, `lab_built` and `result_repair`, sourced from `RUNTIME_EVENTS` in `backend/numen/queue.py`. A runtime event only selects which row is written: the application substitutes its own fixed message and discards the runtime's, and runtime-reported provenance values are bounded before they become a row, because a workload reports both on a log its agent's own process shares. A milestone is therefore not evidence of what ran; the pinned provenance and the attempt record are. Runtime output, prompts, and credentials still never reach the timeline.

Submission returns `{run_id, status}`. `GET /internal/runs/{id}` returns `{run_id, status, progress, events, error?, result?, outputs?}`. Outputs are `{path, content_base64, sha256, size}`. `POST /internal/runs/{id}/cancel` stops/reconciles the run. `GET /internal/runs/{id}/outputs` retrieves validated outputs. Standard statuses are `queued`, `running`, `succeeded`, `failed`, `cancelling`, `cancelled`.

Implement real Pi, Claude, and Codex argv/protocol adapters, isolated container jobs, and capabilities/native login flows. Fixture modes may exist only in explicit test configuration. Unsupported credentials or unavailable engines fail truthfully. Sensitive credentials are never included in ordinary run responses or logs. Trusted native-login credential ingress requires a separate authenticated retrieval channel, deleted after successful vault ingestion; coordinate the exact minimal channel with backend owner.

## Verified implementation adjustments

- A repository's first check sets its Baseline at the head (`cursor` and `baseline_revision`) and imports no history, on GitHub (one commit-list request) and over SVN (`svn info`). Later checks import every revision after the cursor, which can trigger optional triage; earlier commits are imported only by a Backfill. Commit jobs pin immutable revisions; a later head advance does not invalidate historical evidence.
- CPE selectors query NVD by product identity (`virtualMatchString` with wildcard version fields), because `cpeName` rejects wildcard versions. Deployed-version applicability is evaluated separately.
- Source snapshots omit binary media (images, fonts, audio, video) and hold up to 65,536 files, 64 MiB per file and 512 MiB in all (`artifacts.MAX_SOURCE_FILES`, `MAX_FILE`, `MAX_SET`), so CMS-sized sources fit. Agent runs receive `source/` as one compressed archive input that the runner validates (regular files, safe paths, the same expanded bounds) and expands into the read-only input volume; other inputs keep the per-run input limit.
- Version recipes receive the release fingerprint map as `release-corpus.json` and only a coverage summary in the prompt. Numen writes `fingerprints.json` from the corpus unless the agent supplies an identical map. The corpus takes one installable package per release (an updater or patch package is skipped), drops the package's versioned top folder, and fingerprints only front-end files a site publishes as-is (`.js`, `.mjs`, `.css`, `.svg`, `.html`, readme/changelog/VERSION files); manifests, lock files, dependency metadata and hidden files are never fingerprinted or requested. It adds `probes` (files whose bytes differ between releases) and `resolution` (release groups the published files cannot separate). After a recipe's observe run, a version check runs Numen's own fingerprint stage (`fingerprint_probe.py`, budget 10, base URL from the recipe's `asset_base` on an allowed origin, a WordPress plugin directory, or the asset URL), fetching the probe that best splits the remaining releases until one group is left. The result narrows the observation: a single unmatched-free release becomes `detected` with medium confidence, several become `ambiguous` candidates, and a disclosure that contradicts the fingerprints becomes `unknown`.
- Automatic CVE analysis is held while an Application has no successful source check; the baseline check dispatches held analyses.
- Automatic Analysis (A04): a Triage decision of `security_candidate` or `insufficient_context` (agent or Jev; an incomplete diff's `unrelated` becomes `insufficient_context`) starts one automatic `commit_analysis` per commit through `domain.start_analysis`, with idempotency key `analysis:{commit id}`, so a second flag, or the same shared Upstream commit flagged again, starts nothing more. It runs in the context of the first Application that uses the repository (not archived, link on and not removed), with that Application's `commit_analysis` profile, and its job input adds `automatic: true` and `shared` (true when more than one Application uses the repository). Caps (`domain.ANALYSIS_CAPS`): 10 automatic Analyses per Application and 30 per Provider account per UTC day, counted from `commit_analysis` and automatic `patch_drafting` jobs (A08) with `input.automatic` created since 00:00 UTC (`domain.over_cap`), per `application_id` (only `shared: false` jobs) and per `profile.connection_id`, so a shared Upstream Analysis counts only against the account. Failed and cancelled jobs count. Job rows are durable, so the counts survive restarts and reset at midnight with no other state. A change over a cap gets `analysis_state: {status: waiting_for_cap, since, cap}` and records one `actions` row per scope and UTC day (`resource_type` `application` or `account`, `resource_id` the Application or account id, `data: {action: analysis_cap_reached, day, limit}`) and sends one Alert. Every scheduler tick re-checks waiting changes, oldest `since` first (`domain.start_waiting`), so after the reset they start in that order and only as many as the caps allow. A Triage flag runs the same pass before it starts its own change, so a change flagged just after midnight never takes a freed slot ahead of one already waiting. Manual Analyses (`POST /commits/{id}/analyses`, `POST /commits/analyses`) are neither capped nor counted, and a Retry of an automatic job keeps its input, so it counts but is not held at a cap. Concurrency stays bounded by `NUMEN_WORKER_CONCURRENCY` and `NUMEN_RUNNER_CONCURRENCY`.
- Automated runs use API keys only (A13): `domain.automated_profile` resolves the saved or default profile of a run nobody started by hand and refuses an account whose `auth_type` is not `api_key` with `api_key_required` (422, "Automated runs use only Provider accounts that hold an API key; {label} uses a subscription sign-in. Start this run by hand or select an API-key account."). It covers an imported commit's Triage (`triage_status: blocked`, `triage_result.error` and `reason`), automatic Analysis (`analysis_state: {status: blocked, error}`), automatic CVE analysis (`analysis_blocked`) and audit refresh (an `audit_refresh_blocked` event). Jev triage uses its Jev API key. Runs the Operator starts by hand may still use subscription sign-ins.
- Findings and Alerts (A11, A12): only Findings the application opens (`domain.open_finding`) send an Alert, so a Finding the Operator creates by hand (`POST /findings`) sends none. A CVE-analysis (`cve`-source) Finding alerts as `Advisory` with its CVE id as the source, and an account-cap Alert carries the Provider account's label in place of an Application name, because an account cap belongs to no Application. A legacy Numen outbox row, if retried, sends only `Asset Monitor: Alert` and its link, never its stored title or detail. Upstream Exposure is not computed until Phase 7, so every Upstream link counts as unknown, which counts as exposed, and AC-A12's not-exposed case is untested until then.
- A shared Upstream Analysis row keeps the first Application's `application_id`. The Findings it opens in the other Applications reference it through `domain.analysis_reaches`, which relaxes Numen's same-Application rule for commit Analyses only, and its drafted bundle is published once per affected Application. The opening de-duplication is application code (`SELECT … FOR UPDATE` on the Application's Finding for that subject), not a database constraint, because carried-over data holds duplicate manual Findings, so two concurrent Analyses of one commit can still race to a duplicate, as in Numen. Linking matches a short SHA (7 or more hex characters) as a prefix within one Application, and a change linked once is never opened later, even after that Finding is Remediated.
- Numen's commit review decisions (`candidate`, `confirmed`, `dismissed`) stay separate from the Finding lifecycle. The Open findings counts on the dashboard (`open_findings`) and the Application page count `open` Findings only, not Confirmed ones.
- Audit context takes `max_functions` (1–100, default 24) per request: orientation lists significant functions most significant first, and Numen analyzes at most that many, each in its own agent run; any beyond the limit are recorded in coverage as `deferred`/`deferred_units` instead of failing the audit. A function analysis runs with a 1800-second deadline and is analysed once more (`:retry` phase) when it fails on its own (a timeout, invalid output, no document); broker, lease and cancellation failures still stop the audit. A selected path that is off by leading folders resolves to the one snapshot file it matches on a directory boundary; otherwise the function is recorded as failed. Function analyses run in parallel (`NUMEN_AUDIT_CONCURRENCY`, default 3), and the job's progress reports the stage and how many functions are analysed. An interrupted, failed, or cancelled audit continues instead of starting over: lease recovery, Retry, or an identical request (same source and skill revisions, focus, max functions, and agent profile) reuses the latest interrupted checkpoint's function selection and analysed functions (checkpoints store their records as `audit-functions.json`) and re-runs only unfinished or failed functions. A continued checkpoint is marked `continued_by` and never reused twice; `fresh` starts over. Synthesis receives the per-function records as `audit-functions.json` with only an index in its prompt, so record size does not reach the prompt bound. When synthesis follows the skill's `audit-context/DOSSIER.md` layout, Numen writes the `audit-context-building.md` entry document linking it.
- `POST /applications/{id}/audit-contexts` with `{refresh_from: <context id>, profile?}` refreshes that context for the current source head: the job keeps the base's focus and `max_functions`, reuses its orientation, keeps the documents of functions whose own file is byte-identical between the two snapshots, analyses functions in changed files again, records functions whose file was deleted as `removed`, and runs synthesis with the changed-file list (`coverage.refresh`: `from`, `from_revision`, `changed_files` (first 200), `changed_files_total`, `removed_units`). A base from another source generation or skill revision, or one with no analysed functions, is refused with `refresh_unavailable`; one already at the head with `context_current`. Finished contexts keep `audit-functions.json` for refreshes; an older context without it is rebuilt from its orientation and function documents. With Application config `audit_auto_refresh` (default false), every source check queues such a refresh (idempotency key `audit-refresh:{application}:{head}`) when the newest context lags the head and no audit-context job is queued, running or cancelling; a refresh it cannot queue is recorded as an `audit_refresh_blocked` event and never fails the check.
- CVE analysis and finding artifacts start from the Application's audit context (commit analysis judges the change on its own and never receives it): a complete one built at the analysed revision, else the newest complete one of the current source generation, else one with analysed functions at that revision, else the newest such. Its files arrive under `context/` (without `audit-functions.json`); above 4 MB the function documents are left out, and above that again the context is skipped with an `audit_context_skipped` event. Facts carry `audit_context: {id, source_ref, matches_revision, complete, functions_analysed, function_documents}` (null without one), the `audit-context` prompt section explains it as untrusted orientation to verify against the pinned source — at another revision possibly describing fixed code, so never evidence that a vulnerability is absent — and the job records `audit_context_supplied`.
- Jobs run concurrently. The worker runs `NUMEN_WORKER_CONCURRENCY` job slots (default 3) plus one slot that never claims long agent, lab, or login work, so source checks, CVE syncs, version checks, and notifications proceed during long audits. Claims stay row-locked (`SKIP LOCKED`) and attempts fenced. The broker runs up to `NUMEN_RUNNER_CONCURRENCY` workloads at once (default 4); each run has its own containers, networks, and gateway, and an agent run may use up to its 1 GiB memory limit. An attempt records every runtime phase it starts (`runtime_phases`), so failure handling and lease recovery cancel all of its runs and treat it as stopped only when each is terminal; once an operation is stopping, no new phase starts, and a phase that finds its attempt cancelled or lost cancels its own run.
- Agent runs have no execution deadline unless one is requested: the backend omits `timeout_seconds` and waits until the run ends, and requested agent limits refine the broker's defaults instead of replacing them. Triage requests 120 seconds, and Analysis, CVE analysis and audit function analyses 1800 seconds; audit context has no cumulative time budget. Operators stop long runs by cancelling the job. Probe, lab, and login runs keep their time limits.
- A broker run is terminal only after owned workload cleanup is proved. Lost submission acknowledgement is resolved by authenticated attempt-token lookup; an unavailable broker/engine preserves cancelling/pending recovery instead of allowing overlapping replacement.
- API database transactions finish before an HTTP success is emitted, so a returned Application/job/artifact identifier is immediately readable and a late constraint failure cannot follow a false success.
- Native connection setup supports protected cache import. Codex also supports device login, and Claude supports its manual OAuth login: the operator pastes the authorization code via `POST /api/accounts/{id}/login/code`, and the worker relays it to the running login workload. Command Code native connections run in Pi: the bundled plugin's login shows its Studio URL, and the operator pastes the resulting API key through the same endpoint. Native import accepts pi's or the Command Code CLI's `auth.json`. Pi automatic headless OAuth setup for other providers is not exposed as a working flow.
- The Lab builds offline on the bundled Lab base. `RUN` is accepted and runs with no network; URL `ADD`/`COPY` sources and other bases are refused; uploaded originals remain downloadable/unverified.
- Labs behind Approval (A07 Labs, A15): Numen's digest-pinned Lab bases, their Engine pull and the retained base cache are removed, because the Engine would fetch a base outside `--network none` and a retained base contradicts ADR-0005's removal of every Lab's images; a carried-over bundle with a digest base reads as Draft (a Finding's cached artifact state carries `artifacts.RULES` and is recomputed when the rules change) and is refused at Lab start, and a Node app that needs another Node version cannot get one in this release. Install scripts are disabled for npm (`--ignore-scripts` in phase one, `ignore-scripts=true` in the Lab base's global npmrc), not for a bundle that runs a dependency's script directly, which still runs offline. Completeness does not check the Node-only rule, so a non-Node bundle reads as complete and is refused (`lab_stack_unsupported`) only at Lab start, after its Approval. The image limit is checked after the build, so a step that fills the disk is stopped only by the build deadline. The Approval's rate limit, like login's, is in memory per app process and keyed by client address, and a refused Approval records no Action. A `lab_run` job cannot be retried; the worker's crash recovery may still run an approved job again, which is the approved action. Own-repository Labs use the stored snapshot (binary media omitted, at most 65,536 files, 64 MiB per file and 512 MiB in all, `package.json` at the repository root), and finding generation gets no `own_repository` fact. The run's 10 minutes now start after the build and include the app's startup. `LabRun.data` gains `source_ref`; no migration was needed.
- Malicious change static Proofs (A07, ADR-0004 point 6): the agent drafts no hashes, and application code hashes each file it keeps from the commit's snapshot. It keeps only files commit.json lists as added or changed and hosts, URLs and commands that occur literally in a line the diff adds, so an encoded or obfuscated value, or one in the uncaptured part of an incomplete diff, is listed as rejected. Snapshots omit binary media and are bounded (65,536 files, 64 MiB per file, 512 MiB in all), so a payload in an image or font, or in a repository over the bounds, never satisfies the `changed` check and its Finding stays Draft. For the same reason, and because the repository's own root `manifest.json` is never sent (the snapshot's artifact manifest takes that path), the `parent` and `baseline` checks do not scan media files or the root `manifest.json`: a rule that matches only those passes, although it would match them on the server. The indicators have no count or length bounds in the result schema, so a long payload line or a large change never fails the Verdict; application code keeps only what it finds in the commit. A commit's Finding that a Malicious change opened, or whose source commit's newest Verdict is one, takes the static Proof path on every new revision even without a stored `static_proof` (one opened before Phase 5 starts it on its first upload), and a later Verdict on a Finding a Malicious change opened publishes no Lab bundle over it. Queued Finding generation is refused when it runs too. Releases that no stored commit carried show as "None found among the stored commits; not ruled out", never as none. The cleanup report is data on the Finding (`static_proof.indicators` and `cleanup_report`), not a drafted `cleanup-report.md`: the agent drafts the indicators and `reachable_secrets`, and application code adds the commits, the releases and the Detection rule. Containment is approximate until Phase 7's tag containment: later stored commits on the same branch by `committed_at`, the Baseline for a Backfill commit, and the tags that point at those, so tags on unwatched branches, backports and later reverts are missed. A Release-branch commit is checked against the repository's default-branch `baseline_revision`, because a watched branch stores no Baseline of its own. Validation runs once per Finding revision, so a shared Upstream commit in N Applications runs N identical yara jobs (its parent and Baseline snapshots are stored once). Finding generation is refused for a Malicious change (`generation_not_available`). A validation job that fails (broker down, a snapshot fetch error) leaves `status: pending` with its `job_id` and no failed check, and the Operator retries the job. An Operator-customized `commit_analysis` template lacks the `detection-rule` include; the appended result schema still names the fields, but such a run may fail `invalid_agent_output` until the template is reset (`GET /prompts` flags `default_changed`). Upstream static Proofs stay downloadable until Phase 7 implements A15's refusal, and the Findings list still shows "Lab unverified" on a Malicious change row, because the summary view carries no `malicious_change`. A Lab for another Finding is not refused when its tree contains a known Malicious change (an Own-repository Proof at a later commit, or an Upstream version that shipped it): install scripts stay disabled, but a payload in runtime code would run in that Lab; Phase 7's tag containment is needed to refuse it. No migration: `static_proof` and `cleanup_report` live in `findings.data`, and job kinds are strings.
- Remediation PRs (A08, A15, decision 7): the patch run's "scratch worktree" is its write-only `outputs/` with the Own checkout as read-only input, and Codex is refused for it as for Analysis. Only an Own Vulnerability introduced Verdict drafts a patch automatically, because A06's Own column gives a Vulnerability fix no Remediation PR. `POST /findings/{id}/remediation-prs` (manual drafting, uncapped) is an addition the PRD does not name. Validation runs at draft time, so a rejected diff never reaches an Approval or a write-token request, and the PR step applies the diff again locally before its first GitHub request. The write token is also used by the merge check, which reads pull requests with it because a fine-grained read token cannot read them on a private repository, and by its connection check (`GET /user`); it is never used to list commits or snapshot a repository. A pull request targets the Own repository's `source_ref` when one is set, the branch the diff was drafted on and the merge check polls, which the PRD calls the default branch. A Finding the Operator opened on an Own commit with no Verdict may get a patch or a revert by hand; A06 names only Verdicts. Pin and bump rewrite only the package's own `package-lock.json` entry (no transitive entries, `composer.lock`, `pnpm-lock.yaml` or `yarn.lock`), and nothing triggers them before Phases 7 and 8. `branch_exists`, `tree_truncated` and `unsafe_branch` are additions.
