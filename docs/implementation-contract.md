# Implementation coordination contract

This is the shared contract for the first complete implementation, authorized by the user's “Build it” instruction. Preserve the PRD's outcomes and all three coding-agent choices. Each owner can make reversible local implementation choices within this boundary. Coordinate contract changes with the orchestrator before changing a consumer-facing shape.

## Ownership

- Backend agent: `backend/`, backend tests, migrations, domain services, scheduler/worker, API/security/persistence. Do not edit `runner/`, frontend, or root deployment files.
- Frontend agent: `frontend/`, its tests and package manifests. Do not edit backend, runner, or root deployment files.
- Runtime agent: `runner/`, root Dockerfiles/Compose files, runtime tests, and pinned agent/plugin/skill manifests. Do not edit frontend or backend modules.
- Orchestrator: root Makefile, bootstrap/backup helpers, integration fixtures/journey, documentation, cross-owner integration and final checks. When a correction belongs to another owner's active files, send it back to that owner.

All agents share the workspace. Preserve other owners' edits and adapt to their work. Read the PRD, design, and UI specification as governing context; these instructions settle serialization only.

## API

All paths below begin with `/api`. A session cookie authenticates requests. `GET /auth/session` returns `{authenticated: boolean, username?: string, csrf_token?: string}`. Login accepts `{username: "admin", password: string}` and returns the authenticated session shape. Browser mutations send `X-CSRF-Token` after login. Structured errors use `{code, message, fields?: object, retryable?: boolean}` with JSON; lists use `{items: array, next_cursor: string|null}`. Responses expose no secrets. IDs are strings; times use UTC ISO-8601.

### Domain records

Application fields: `id`, `asset_name`, `asset_url`, `product_kind`, `product_name`, `monitor_interval_seconds` (300 to 315,360,000: at least 5 minutes, at most 10 years; shown and entered in minutes, hours or days), `monitor_enabled`, `archived`, `source_generation`, `last_check_at`, `next_check_at` (both set by the scheduler and Check now), `repositories`, `unresolved_dependencies` (the active Own link's, else `[]`), `version` (latest observation or null), and `config`.

A repository is stored once per source URL and linked to each Application that uses it. GitHub URLs are normalized to `https://github.com/{owner}/{repo}` in lower case, without `.git` or a trailing slash; a WordPress.org plugin is `https://plugins.svn.wordpress.org/{slug}`. Its slug, ref and path are fixed when the row is created, so Applications sharing a URL share them. `repositories` lists the Application's links, the Own one first and then in the order they were added, removed ones included: `repository_id`, `role` (`own` or `upstream`), `enabled`, `removed_at`, `locked_version`, `locked_version_source` (`manifest`, `operator` or `deployed`), `release_branch`, `release_branch_status`, `packages` (the packages a derived Upstream link stands for, such as `npm:react`; `[]` for hand-added and Own links), `source_kind`, `source_url`, `plugin_slug`, `source_ref`, `source_path`, `cursor` (GitHub head or SVN revision), `baseline_revision` (the Baseline: the head when the repository was first checked), `last_check_at` (last successful check) and `last_error`. An Application has at most one active Own repository, which must be on GitHub, and may have none. Commits, snapshots, cursors and Triage belong to the repository, so a shared repository is polled and triaged once. Its new commits are triaged with the first linked Application that is not archived, links it enabled, and has Triage on; with none, they are not triaged. A GitHub repository is read only with a token from an Account with provider `github` (fine-grained, read-only: Contents and Metadata). Without one, the scheduler queues nothing for it and sets `last_error` to `github_token_required`; Check now queues the check, which fails with that code before any request. Every GitHub poll sends `If-None-Match` with the ETag of the last commit list; a `304` returns before any compare or commit request, advances neither cursor nor ETag, imports nothing and queues nothing (the check's result has `not_modified: true`). An Upstream GitHub repository also watches the Release branch of each Locked version that an enabled, not removed link of a not archived Application uses. The first branch that exists among `{major}.x`, `{major}.{minor}`, `release-{major}` and `v{major}` (the major and minor of `^v?(\d+)(?:\.(\d+))?`) is the Release branch; a check resolves a Locked version once, with `GET /repos/{repo}/branches/{name}`, and again only after it changes. `release_branch_status` is null for an Own link, a WordPress repository or no Locked version, `pending` until the next check resolves the current Locked version, `matched`, or `unknown` when no candidate exists (the UI says "release branch unknown"); then only the default branch is watched. Each Release branch keeps its own cursor and ETag in the repository's watched branches, is baselined at its head when first watched, and its new commits are imported with `branch` set to its name; a revision already imported from another branch is not imported again. A check is `not_modified` only when every watched branch answers `304`. Own and WordPress repositories watch their default branch only. WordPress.org plugins keep the SVN revision cursor and need no token.

The Application's source repository is its earliest linked repository that is not removed, whatever its role or on/off state; for a migrated Numen Program it stays the former source after an Own repository is added. Version recipes, version checks, audit contexts, CVE analyses and finding artifacts read it and fail with `repository_required` without one. `source_generation` is the Application's generation of that source: it advances only when the source repository's link is removed (the next earliest link then becomes the source), which clears the active recipe and the CVE cursor and marks audit contexts stale. Adding a repository or turning a link on or off changes neither.

Upstream repositories are derived from the Own repository by a `derive_upstreams` job. A check of an Own repository queues one, with idempotency key `derive:{application id}:{head}`, after its Baseline (when the link was never derived) and whenever an imported commit's `dependency_manifest` Pre-filter flag shows that it changed a manifest or lockfile; linking an Own repository that another Application has already checked queues one at once. The job reads `package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `composer.json` and `composer.lock` at that revision under the repository's path (`GET /repos/{repo}/contents/{path}?ref=`, raw). Direct dependencies are `dependencies`, `devDependencies` and `optionalDependencies` in `package.json` and `require` and `require-dev` in `composer.json`, without platform packages (`php`, `ext-*`, `lib-*`, `composer-*`). Versions come from the lockfile: `package-lock.json` v1 `dependencies` or v2/v3 `packages["node_modules/{name}"]`, `pnpm-lock.yaml` `importers["."]` (v6+, with the peer suffix removed) or its top-level maps (v5), `yarn.lock` v1 or Berry (the entry for the direct range, else the first), and `composer.lock` `packages` and `packages-dev`. Each package is mapped to its GitHub repository through `{npm registry}/{name}/{version}` (`latest` without a locked version, scoped names as `@scope%2Fname`) and its `repository` field, or for Composer through the `composer.lock` entry's `source.url`, else `{packagist}/p2/{vendor}/{name}.json` (the entry for the version, else the newest). The registry base URLs are `https://registry.npmjs.org` and `https://repo.packagist.org`; in test mode `NUMEN_NPM_REGISTRY_URL` and `NUMEN_PACKAGIST_URL` replace them. Packages mapped to one URL share one Upstream repository, found or created by URL (a derivation or request that creates it at the same time reads the other's row), and one link per Application. A new link is on at the first derivation and off afterwards, with the first package's Locked version recorded as `manifest`. An existing link gets the new `packages`, a new Locked version unless its source is `operator` or `deployed`, and is restored if it was removed. A derived link whose packages are all gone is marked removed and keeps its commits; hand-added links (no `packages`) and the Own link are never removed by derivation. A removed link that is added again by hand is restored as a hand-added link: its `packages`, `unresolved` and derived revision are cleared. A package with no repository metadata, a repository outside GitHub, a registry `404` or a registry body that is not its JSON object is listed in the Own link's `unresolved` (`unresolved_dependencies`: `{ecosystem, name, version, reason}`). A manifest that is not valid JSON or YAML, or is valid but of the wrong shape, fails the job with `invalid_manifest` and changes nothing; a failed derivation sets the Own repository's `last_error`. A derivation that added repositories sets `next_check_at` to now, so they get their Baseline on the next scheduler tick.

`config` contains `triage_mode` (`disabled`, `jev`, `pi`, `claude`; `codex` is refused with `validation_error` "Triage on Codex is refused until a no-tools restriction has been verified for it", though a configuration stored with it still loads), `profiles` keyed by operation, `cve_selectors` (list of typed selector objects), `cve_min_score`, `cve_versions` (subset of `3.0`, `3.1`, `4.0`), `cve_auto_analyze`, `active_recipe_id`, `monitor_interval_inherited`, `version_scheme`, `version_monitor_enabled`, `asset_origins`, `jev_connection_id`, and `jev_model_id`. Application `latest_version_check` supplies the latest failure independently of the last successful `version`. Agent operations are `commit_triage`, `commit_analysis`, `version_recipe`, `audit_context`, `cve_analysis`, and `finding_artifacts`. A `commit_triage` profile on Codex, whether a default profile, an Application profile or the one an import resolves, is refused with `triage_codex_unsupported` (422); an import blocked that way records the commit as `blocked` with that reason. A `commit_analysis` or `cve_analysis` profile on Codex is refused the same way with `analysis_codex_unsupported` (422, "Analysis and CVE analysis on Codex are refused until a Codex mode without a shell has been verified"), because Codex always has a shell and those operations get only a read-only checkout and a write-only output directory (ADR-0004); a queued job with such a profile fails with that error, and an automatic Analysis is `blocked` with it.

Profile fields: `agent` (`pi`, `claude`, `codex`), `connection_id`, `model_id`, and nullable `reasoning_effort`. Server resolves defaults and validates every combination. These fields are identical for all operation submissions. Runtime receives a resolved provider/auth mode separately.

Commit fields: `id`, `repository_id`, `application_id` (the first Application that uses the repository: not archived, its link on and not removed; else the first that ever linked it. It is the context of commit pages and owns the commit's one Analysis; the Findings that Analysis opens are per affected Application), `revision`, optional imported `parent_revisions`, `message`, `author`, `committed_at`, `url`, `files`, `diff`, `diff_complete`, `prefilter`, optional `backfill` (true for a commit imported by a Backfill), optional `branch` (the Release branch it was imported from), `triage_status`, `triage_result`, `review_decision`, `verdict` (the newest Analysis's Verdict, null until one completes), `analysis_state` (null, or the latest Analysis job's `{status, job_id}` while `queued`, `{status: completed, analysis_id}`, or `{status: failed|timed_out, job_id, error}`; an automatic Analysis that has not started is `{status: waiting_for_cap, since, cap: application|account}` or `{status: blocked, error}`), and `analyses`. A diff is capped at 60,000 characters per file and 2 MiB in all; a capped diff, or one whose file patch the source omitted, has `diff_complete: false`. `prefilter` is the Pre-filter result recorded at import, `[{rule, paths}]` for the rules the change matches: `dependency_manifest` (`package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `composer.json`, `composer.lock`), `package_scripts` (a changed `package.json` line inside the `scripts` object as the hunk shows it, the `scripts` line itself, or a changed npm lifecycle hook: `install`, `prepare`, `prepublishOnly`, or `pre`/`post` with `install`, `pack`, `publish`, `start`, `test`, `stop`, `restart`, `version` or `shrinkwrap`), `ci_workflow`, `minified_or_obfuscated` (`*.min.js`/`*.min.css`, an added line over 1,000 characters, `_0x…` identifiers, `eval(atob(`, `String.fromCharCode(`) and `auth_or_crypto` (authentication, session, token, cryptography, signing, secret, key, permission and CSRF paths). It never changes `triage_status` or `review_decision`. Triage is one agent run with no tools and a 120-second deadline (`TRIAGE_SECONDS`), never a Herdr session. Its prompt carries the change as `facts.commit` (`message`, `author`, changed `files` paths, `diff` capped at 100,000 characters (`TRIAGE_DIFF_CHARS`) as its JSON in the prompt counts them, escapes included, and `diff_complete`, which is false for an incomplete or truncated diff), with no input files. The facts are appended as JSON with non-ASCII characters unescaped, so no diff pushes the prompt past the runner's 262,144-character bound. The runner returns the agent's raw reply as `{reply}`, and the broker accepts nothing else from a Triage run; application code takes the JSON object in it (from the first `{` to the last `}`, so a code fence or prose around it is tolerated), replaces configured secrets with `[redacted]`, and validates it against the Triage schema: `decision` (`security_candidate`, `unrelated`, `insufficient_context`), `title` (1–300 characters, a potential-issue title) and `reason` (1–2,000 characters), nothing else. Jev triage keeps its typed answer, which adds `change_kind`, `issue_type`, `confidence` and probabilities. Complete unrelated triage sets dismissed; uncertain input stays pending, and an unrelated decision on an incomplete diff becomes `insufficient_context`. A failed Triage run (a reply that fails the schema, a timeout, a provider error) sets `triage_status: failed` and `triage_result: {error, reason, attempt}` with no `decision`, so it is never read as unrelated, and leaves `review_decision` unchanged. Unless it was cancelled, lost its lease or its input changed, the worker queues the same Triage again with `attempt` n+1 and the same profile, not before n minutes, up to three attempts (`TRIAGE_ATTEMPTS`), and records `retry_job_id`. Each Triage run, agent or Jev, is stored as a Transcript: a `transcripts` row (`id`, `job_id`, `kind: triage`, `subject_id` (the commit), `data`, `created_at`) whose `data` holds the `prompt` and `reply` (Jev: the `request` body, which never holds the key, and the `response`) with configured secrets replaced by `[redacted]`, `status` (`completed` or `failed`), the `error` of a failed one, the `profile`, `run_id` and the runtime `execution` provenance. A failed run's Transcript is kept. Analysis (`commit_analysis`) returns exactly one Verdict: `verdict` (`Vulnerability fix`, `Vulnerability introduced`, `Malicious change`, `Security hardening`, `Unrelated`, `Insufficient context`; `schemas.VERDICTS`), `confidence` (`low`, `medium`, `high`), `title` (1–300 characters), `summary`, `evidence`, `open_questions`, `before_after`, `affected_behavior`, `vulnerable_ref` (a full revision, required with at least one evidence item for Vulnerability fix and Vulnerability introduced) and optional `addresses`: up to 50 commit SHAs (7–64 hex characters) or advisory ids (`CVE-…`, `GHSA-xxxx-xxxx-xxxx`, or another database's `PREFIX-id`) that the change addresses, kept in the result for linking to Findings. Nothing is run, so the result has no reproduction. Drafts are output files: report.md always, the Proof bundle (`artifacts.REQUIRED`) for Vulnerability fix and Vulnerability introduced, and `detection-rule.yar` and `cleanup-report.md` for a Malicious change, all saved with the analysis artifacts. Its review decision is `candidate` for Vulnerability fix, Vulnerability introduced and Malicious change, `dismissed` for Security hardening and Unrelated, and `pending` for Insufficient context, which puts the change in the Review queue. The opening Verdicts (`domain.OPENING_VERDICTS`: Vulnerability fix, Vulnerability introduced, Malicious change) open one `commit`-source Finding in each affected Application (`domain.affected_applications`: every Application whose link to the repository is on and not removed, the Application not archived; an Own link always counts, and an Upstream link counts because Exposure is unknown until Phase 7, which counts as exposed). In each such Application the change is linked to the Findings, in any state, that its `addresses` name (see Finding fields): a Vulnerability fix linked that way opens nothing, while a Vulnerability introduced or Malicious change fixes nothing and opens its own Finding as well. Vulnerability fix and Vulnerability introduced publish the drafted bundle to each such Finding that is Open or Confirmed, once per Application; a Dismissed or Remediated one keeps the evidence and bundle it was closed with, and `target_applicability` is never reset. An incomplete bundle is published as a draft (`artifact_state.status: draft`) and the job still succeeds. A drafted `vulnerable_ref` that fails validation (`invalid_finding_revision`) publishes no bundle: the Findings still open and alert, the job succeeds, and the error is kept as `bundle_error` in the Analysis and job results. A Malicious change's Finding gets no bundle: its drafts stay with the Analysis. `workflows.check_verdict(result, served_content)` refuses a served-content Analysis that returns Vulnerability fix or Vulnerability introduced with `verdict_not_allowed` (422), which fails the job; commit Analysis may return all six. Analysis and CVE analysis request a 30-minute deadline (`timeout_seconds` 1800, `ANALYSIS_SECONDS`). A failed or expired Analysis sets `analysis_state` to `failed` or `timed_out` (error `timeout` or `runtime_timeout`) and leaves `verdict` and `review_decision` unchanged, so an expired deadline never reads as Unrelated. Migration `9f7a8ba3c2d7` rewrote Numen's stored commit analysis results (analyses and jobs) from its `category` to a `verdict` by the PRD's AC-A04 table, with `confidence: unknown` and Numen's confidence object kept as `numen_confidence`; Numen's other fields stay as they were, and each commit's `verdict` is its newest analysis's. Late manual review actions take precedence over automatic review-decision updates. The commit pages show `verdict` with its newest analysis's confidence (`unknown` for a migrated one), `analysis_state` as Queued, Waiting for cap (with its cap), Timed out after 30 minutes, Blocked or Failed (with the error message), and `prefilter` beside the Triage result even when Triage rejected the change; a `failed` or `blocked` Triage reads as Triage failed or Triage blocked, never as unrelated. The Review queue is a Show filter of the commit list (`verdict` Insufficient context, `review_decision` pending) and a dashboard panel fed by `review_queue`.

Commit analysis is read-only like CVE analysis: it reads the pinned revision's snapshot at `inputs/source`, writes only to `outputs/`, and builds and runs nothing, so a bundle it writes is a draft that only a Lab run verifies. Each Application has at most one Finding per commit that the Analysis opens; re-analysis reuses it, in whatever state, preserving its operator title, lifecycle status and cause, so a Dismissed or Remediated Finding is never reopened and a different opening Verdict opens no second one. Fix findings must pin a verified parent revision; introductions must pin the analyzed revision. A Git application lock must match that revision. Finding generation reuses this validated vulnerable source instead of the current fixed checkout. Linked immutable analysis output remains separate from the finding's current artifact revision. Vulnerability fix and Vulnerability introduced publish their drafted bundle, an incomplete one as a draft, and the job still succeeds; the other Verdicts need a report only. Job results expose `commit_id`, `analysis_id`, `finding_ids` (every Finding opened or reused) and `finding_id`, `artifact_revision` and `artifact_state` of the job Application's Finding (`finding_id` null when that Application linked the change or does not use the repository); the analysis `result.finding_id` is the same.

Resolve legacy commit parents and any vulnerable-source snapshot before acquiring the publication fence. Source I/O renews the job lease through a separate connection and must never run while that same job is locked by publication. Invalid revision proposals still retain the analysis/report and fail without creating a finding; publication remains fenced against cancellation and replacement attempts.

CVE fields: `id` (CVE ID), `application_id`, `title`, `description`, `published_at`, `modified_at`, `scores`, `match_status`, `eligible`, `eligibility_reason`, `applicability`, `affected_versions`, `fixed_versions`, `references`, and `analyses`. Score entries contain `version`, `base_score`, `vector`, `source`. Keep per-Application match/eligibility separate from global records.

Finding fields: `id`, `application_id`, `source` (the Finding source: `commit`, `served_content`, `advisory`, or `cve` for a CVE record carried over from Numen; fixed at creation, a change is refused with `immutable_source`), nullable `source_ref` (the source's short SHA, Watched page or advisory id), nullable `cve_id`, `title`, `status` (the A11 lifecycle state: `open`, `confirmed`, `dismissed`, `remediated`), `cause` (who or what set the current status: `{by, at, ...refs}`; `by` is `operator` (with `reason`), `verdict`, `cve_analysis` or `numen` for an opened or carried-over Finding, `proof`, `detection_rule` or `advisory` for a confirmation, and `remediation_pr`, `version_bump`, `baseline_match` or `deployed_version` for a remediation), `deployed_version` (shown apart from the lifecycle; `unknown` until the Deployed version check exists), `affected_versions`, `fixed_versions`, `target_applicability`, `source_commit_id`, `source_analysis_id`, `artifact_state`, `artifacts`, `lab_runs`, `created_at`, `updated_at`. `artifact_state` is `{status: "draft"|"complete", missing: string[], limitations: string[], vulnerable_version: string|null}`; Draft is artifact completeness only (Numen's AC-12), never a lifecycle state. Every Finding opens `open`. `domain.open_finding(db, application, source, subject, title, ref, cause)` opens the Application's Finding for a subject (the commit by `source_commit_id`, the CVE by `cve_id`, a served-content change or advisory by `data.subject_id`) or returns the existing one unchanged, in any state; an opened one records an `actions` row `{action: opened, cause, source_ref}`. Commit Analysis and CVE analysis use it; the served-content (cause `{by: verdict, verdict: Malicious change, confidence}`, `source_ref` the Watched page) and Advisory check (cause `{by: advisory, advisory_id}`) callers arrive in Phases 9 and 8. `domain.link_change(db, application, addresses, change)` maps an Analysis's `addresses` to that Application's Findings only, in any state (a fix addressing a Dismissed or Remediated Finding is linked to it and opens nothing): a commit SHA (7–64 hex characters) matches the prefix of a Finding's source commit revision, any other id its `cve_id` or an advisory Finding's subject; the change's own Finding is skipped. Each match gets an `actions` row `{action: linked, commit_id, revision, analysis_id, verdict}` in its `events` and keeps its status and cause; a change linked once returns the same Findings on a repeat Analysis and is never opened. A Finding may reference the Analysis of a shared Upstream commit, which belongs to the first Application that uses it: `domain.analysis_reaches` accepts an Analysis of the Application's own or of a commit in a repository it links, for `POST`/`PATCH /findings` and finding generation. `domain.transition_finding(db, finding, state, cause)` is the one lifecycle move: `open` to `confirmed` or `dismissed`, `open` or `confirmed` to `remediated`; it raises for a cause that cannot set that state (only the Operator dismisses), returns false and changes nothing from any other state, and records an `actions` row `{action: transition, from, to, cause}` that appears in the Finding's `events`. A verified Lab run confirms its Finding (`{by: proof, lab_run_id}`); a not-reproduced one changes nothing. PATCH edits only `FindingInput` fields and never the status, cause or server-owned keys (those starting with `_`); `source_ref` follows the edit as `POST` sets it: a `cve` Finding's CVE id, a `commit` Finding's source commit short SHA (else its CVE id). CVE analysis refreshes an Open or Confirmed Finding's evidence, versions, applicability and bundle; a Dismissed or Remediated one keeps them. Migration `a08b9cb4d3e8` renamed `kind` to `source` (`0day` to `commit`, `cve` kept), mapped status `fixed` to `remediated`, and added `cause: {by: numen}` and `source_ref` to every Finding, leaving artifacts and other data untouched; its downgrade is refused while any Finding is confirmed or dismissed or has a `served_content` or `advisory` source. Analysis records expose structured output under `result`; CVE `qualifying_score` names the gate witness.

Finding version arrays accept strings and structured evidence objects. The UI renders their product/range/version labels and preserves structured evidence when an operator edits unrelated fields. `GET /findings?view=summary` returns identity, source, lifecycle status and cause, Deployed version, versions, exposure, source links, artifact revision/completeness, timestamps, and nullable `lab_status` for the latest lab run; it omits artifact inventories, evidence, events, and lab histories. The register, Application counts, and quick search use this projection. The default list and individual finding responses retain their full fields. The register shows each Finding's source (`Commit abc1234`, the CVE id, `Advisory GHSA-…` or `Watched page /path`) and its State with the cause under it. The Finding page has a Lifecycle panel with the state, the cause and its time, and the Operator's Confirm and Dismiss (Open only) and Mark remediated (Open or Confirmed) buttons, each sending a required reason to `POST /findings/{id}/transitions`. Its History lists the opened, linked (the change's short revision, linking to its commit, and Verdict) and transition (from → to and cause) events, and older events by their action name. The Deployed version is a separate row (Unknown until Phase 7) under the hint that a fix in the repository does not mean the Asset serves it. The commit queue and commit page link each Finding a commit opened or was linked to as `{State} finding · {Application}`, prefixed `Linked:` for a linked one. The commit review decision that sets `confirmed` is labelled Confirm revision, so Confirm names only the Finding lifecycle action.

Finding completeness is recorded with the published artifact revision in server-owned finding data. Edits preserve it, public responses omit the private record, and request bodies cannot override it. A missing or older revision summary is derived from published path/size metadata and integrity-checked Dockerfile/lock contents. Reading a finding describes its published bundle; full byte integrity remains enforced on preview, download, upload merge, and lab execution.

Each agent operation's prompt is rendered from its template in `backend/numen/prompt_templates/operations/`, which includes the shared sections it needs from `sections/` (`rules` for all; `attack-path` and `bundle` for commit analysis, CVE analysis and finding artifacts; `source-pin` and `audit-context` for CVE analysis and finding artifacts; `audit` for the three audit phases). Templates are Jinja rendered in a sandbox; operator versions saved through `/prompts` override the shipped defaults by name and apply to the next job. Numen appends `Facts:` and the run's facts as JSON after the rendered template, and a job whose prompt used a customized template records a `prompt_customized` event naming them. Finding regeneration sends bounded identity/source facts in the prompt and supplies operator fields and evidence in `finding.json`. Its linked `analysis.json` preserves analysis identity/results without the artifact inventory, alongside the integrity-checked original `analysis-report.md` and pinned source. Generation does not read every saved analysis artifact or inline file inventories and histories into the bounded runner prompt. Public analysis/detail responses retain their full artifact inventories.

CVE analysis drafts the full n-day bundle in its read-only analysis run, which builds and runs nothing, and creates or updates its Application's CVE finding, preserving an existing finding's title and lifecycle status. Analysis `result.finding_id` and job `result.finding_id` link to that finding; earlier analysis files remain immutable. Both CVE analysis and finding generation (unlike commit Analysis) require all paths in `artifacts.REQUIRED` and a valid pinning declaration before the job succeeds. Incomplete bundles are published as drafts, the job retains artifact/finding/analysis identifiers in `result`, and fails with `incomplete_bundle` and `partial_output_retained:true`. Finding generation receives the linked analysis JSON, original report and pinned CVE record as evidence. Generation never verifies reproduction or automatically closes a finding; unsupported lab build steps remain explicit prerequisites.

Job fields: `id`, `kind`, `application_id`, `status`, `progress`, `profile`, `created_at`, `started_at`, `finished_at`, `error`, `result`, `events`. Job submission returns `202 {job_id, status_url}`. Idempotency keys are supported. Profile/input changes create a new job; a retry reuses the recorded profile/input.

### Routes

- `GET /dashboard`: `{applications, security_reviews, eligible_cves, open_findings, running_jobs, failed_jobs, recent_events, due_applications, review_queue, review_queue_count}`; counts are numeric, lists are real data. `review_queue` is the Review queue: up to 20 commits whose `verdict` is Insufficient context and whose `review_decision` is still `pending`, newest `committed_at` first, each `{id, title, revision, application_id, committed_at}` (`title` is the Triage title, else the message's first line); `review_queue_count` counts them all. `open_findings` counts Findings in state `open`, and `security_reviews` commits whose review decision is `candidate`. Any review decision by the Operator takes a change out of it.
- `GET/POST /applications` (`q` also matches linked repository URLs and plugin slugs); `GET/PATCH /applications/{id}`.
- `POST /applications/{id}/repositories` with `{role?: "own"|"upstream", source_kind, source_url?, plugin_slug?, source_ref?, source_path?, locked_version?}` finds or creates the repository by URL and returns 201 with the link. It is refused with `own_repository_exists` while an Own repository is active and `repository_linked` when the repository is already linked; a removed link is restored. ## Runtime broker contract

The internal broker is authenticated by `X-Broker-Token` from `NUMEN_BROKER_TOKEN`. URL environment: `NUMEN_BROKER_URL`. Its default port is 8081. Frontend callers never access it.

`POST /internal/runs` accepts `{attempt_token, kind, profile, prompt, output_schema, inputs, limits, target_policy?}`; `build` and `repository` are refused as unknown fields, because no agent run builds anything or receives a repository mirror (ADR-0004, ADR-0005). `profile` extends the public profile with `provider_id`, `auth_type`, and a protected `credential` envelope. Inputs are an array of `{path, content_base64}`. Paths are safe workspace-relative files. Limits and kind map to hardcoded broker-controlled profiles; caller values can lower limits, not exceed configured maxima. Prompt/schema never contain credential values. The broker does not accept arbitrary container flags, host mounts, images, or command strings.

Kinds include `agent`, `probe`, `lab`, `capabilities`, and `account_login`. `agent` has an `operation` in the profile. Probe inputs include the recipe/script and JSON target input; lab inputs include the finding bundle. `target_policy` scopes origins/methods and request budgets.

A `lab` run carries and builds a whole application, so it is bounded like a build rather than like an analysis: its bundle travels as one compressed archive (up to 65536 expanded files and 512MB), its ceiling is `LAB_MAXIMA` (`timeout_seconds` 10800, `memory_mb` 8192, `cpus` 4, `pids` 4096, `output_bytes` 512MB, `input_bytes` 512MB), and the per-run 512-file limit no longer applies to it. `build_lab` accepts an ordinary Dockerfile — `RUN`, multi-stage and continuations included — and builds it on a per-run bridge with network, because a vulnerable application installs its dependencies and initialises a database. What a bundle still may not do is float its base or reach the host: `FROM` must name the bundled lab image, `scratch`, an earlier stage or a `@sha256` digest, `COPY`/`ADD` sources stay inside the bundle unless they carry a valid `--from`, and build mounts and privileged build flags are refused. The application container then runs with a writable root filesystem, its image's own user and an ordinary capability set on that same per-run bridge, so it has internet; Docker keeps bridges apart, so it reaches neither the application nor the control network. The container that runs `poc.py` keeps the bounded, nonroot, network-isolated profile, so an observed proof comes from the application and not from the network. A failing PoC's error stream is returned with its result.

Every agent run is read-only. Its inputs, including `inputs/source`, the pinned revision's source snapshot without git history, are staged read-only, only `outputs/` is collected from it (Pi and Claude can write nowhere else; where Codex runs, its sandbox can write elsewhere in the `/workspace` tmpfs), and it has no Docker daemon, socket or client. Its tools are fixed per operation in `runner/numen_runner/adapters.py` by the flags that decide which tools exist, never by `--allowedTools`: Triage (`commit_triage`) gets no tools at all: Claude runs `claude -p --output-format json --tools '' --setting-sources '' --strict-mcp-config --mcp-config '{"mcpServers":{}}' --no-session-persistence` (plus `--bare` for an API key), Pi runs `--print --mode json --no-tools` with every discovery switched off, and Codex is refused because it has no flag that removes its shell. Every other operation writes under `outputs/`: Pi gets only its bundled read/list tools, `numen_write` under `outputs/`, and `target_fetch` for `version_recipe`; Claude gets `Read,Grep,Glob,Write,Edit` under `--restricted` and `--permission-mode dontAsk`, with `--settings` approving file edits under `//workspace/outputs/**` and, for `version_recipe`, the target MCP tool; Codex is refused for Analysis and CVE analysis too, and for the operations it still runs keeps its shell in its native `:workspace` sandbox with network off except for `version_recipe`; neither Pi nor Claude gets a shell tool. The credential-free gateway allows CONNECT only to the selected provider's hosts, plus `herdr.dev` for an agent run that hosts a Herdr session (`engine.gateway_config`; Triage never does); every other host, package and source registries included, is refused before any DNS lookup.

A commit analysis on an incomplete upstream diff (a merge or an oversized change) never stands as Unrelated or Security hardening: the snapshot has no history, so the whole change cannot be reviewed, and either Verdict is recorded as Insufficient context, so the commit stays pending in the Review queue. Analysis prompts require the attacker, least privilege, source, propagation, sink and trust boundary to be established before drafting a bundle, and a reproduction to deliver the payload only through that source as the least-privileged attacker and observe it at the sink, never by writing the payload into storage directly; a shortcut reports `not_reproduced`. Analysis itself reproduces nothing: its bundle is a draft for a Lab. A commit's `commit.json` input describes the revision only; earlier analyses travel separately as `prior-analyses.json`, labeled untrusted prior analysis to be used only as a checklist and never as a verdict, without their artifacts or finding links.

`build_lab` fetches a bundle's validated digest-pinned base when the host store lacks it. That base is an immutable approved reference and is deliberately retained in the host store as a cache for later verifications rather than removed with the run, so repeated lab runs neither refetch it nor race each other's cleanup.

`ExecutionContext.progress` records runtime lifecycle events as job events, once per run and type. The recognised types are `lab_started`, `lab_application_exited`, `lab_base_fetch`, `lab_build`, `lab_built` and `result_repair`, sourced from `RUNTIME_EVENTS` in `backend/numen/queue.py`. A runtime event only selects which row is written: the application substitutes its own fixed message and discards the runtime's, and runtime-reported provenance values are bounded before they become a row, because a workload reports both on a log its agent's own process shares. A milestone is therefore not evidence of what ran; the pinned provenance and the attempt record are. Runtime output, prompts, and credentials still never reach the timeline.

Submission returns `{run_id, status}`. `GET /internal/runs/{id}` returns `{run_id, status, progress, events, error?, result?, outputs?}`. Outputs are `{path, content_base64, sha256, size}`. `POST /internal/runs/{id}/cancel` stops/reconciles the run. `GET /internal/runs/{id}/outputs` retrieves validated outputs. Standard statuses are `queued`, `running`, `succeeded`, `failed`, `cancelling`, `cancelled`.

Implement real Pi, Claude, and Codex argv/protocol adapters, isolated container jobs, and capabilities/native login flows. Fixture modes may exist only in explicit test configuration. Unsupported credentials or unavailable engines fail truthfully. Sensitive credentials are never included in ordinary run responses or logs. Trusted native-login credential ingress requires a separate authenticated retrieval channel, deleted after successful vault ingestion; coordinate the exact minimal channel with backend owner.

## Verified implementation adjustments

- A repository's first check sets its Baseline at the head (`cursor` and `baseline_revision`) and imports no history, on GitHub (one commit-list request) and over SVN (`svn info`). Later checks import every revision after the cursor, which can trigger optional triage; earlier commits are imported only by a Backfill. Commit jobs pin immutable revisions; a later head advance does not invalidate historical evidence.
- CPE selectors query NVD by product identity (`virtualMatchString` with wildcard version fields), because `cpeName` rejects wildcard versions. Deployed-version applicability is evaluated separately.
- Source snapshots omit binary media (images, fonts, audio, video) and hold up to 20,000 files / 64 MiB, so CMS-sized sources fit. Agent runs receive `source/` as one compressed archive input that the runner validates (regular files, safe paths, the same expanded bounds) and expands into the read-only input volume; other inputs keep the per-run input limit.
- Version recipes receive the release fingerprint map as `release-corpus.json` and only a coverage summary in the prompt. Numen writes `fingerprints.json` from the corpus unless the agent supplies an identical map. The corpus takes one installable package per release (an updater or patch package is skipped), drops the package's versioned top folder, and fingerprints only front-end files a site publishes as-is (`.js`, `.mjs`, `.css`, `.svg`, `.html`, readme/changelog/VERSION files); manifests, lock files, dependency metadata and hidden files are never fingerprinted or requested. It adds `probes` (files whose bytes differ between releases) and `resolution` (release groups the published files cannot separate). After a recipe's observe run, a version check runs Numen's own fingerprint stage (`fingerprint_probe.py`, budget 10, base URL from the recipe's `asset_base` on an allowed origin, a WordPress plugin directory, or the asset URL), fetching the probe that best splits the remaining releases until one group is left. The result narrows the observation: a single unmatched-free release becomes `detected` with medium confidence, several become `ambiguous` candidates, and a disclosure that contradicts the fingerprints becomes `unknown`.
- Automatic CVE analysis is held while an Application has no successful source check; the baseline check dispatches held analyses.
- Automatic Analysis (A04): a Triage decision of `security_candidate` or `insufficient_context` (agent or Jev; an incomplete diff's `unrelated` becomes `insufficient_context`) starts one automatic `commit_analysis` per commit through `domain.start_analysis`, with idempotency key `analysis:{commit id}`, so a second flag, or the same shared Upstream commit flagged again, starts nothing more. It runs in the context of the first Application that uses the repository (not archived, link on and not removed), with that Application's `commit_analysis` profile, and its job input adds `automatic: true` and `shared` (true when more than one Application uses the repository). Caps (`domain.ANALYSIS_CAPS`): 10 automatic Analyses per Application and 30 per Provider account per UTC day, counted from `commit_analysis` jobs with `input.automatic` created since 00:00 UTC, per `application_id` (only `shared: false` jobs) and per `profile.connection_id`, so a shared Upstream Analysis counts only against the account. Failed and cancelled jobs count. Job rows are durable, so the counts survive restarts and reset at midnight with no other state. A change over a cap gets `analysis_state: {status: waiting_for_cap, since, cap}` and records one `actions` row per scope and UTC day (`resource_type` `application` or `account`, `resource_id` the Application or account id, `data: {action: analysis_cap_reached, day, limit}`) and sends one Alert. Every scheduler tick re-checks waiting changes, oldest `since` first (`domain.start_waiting`), so after the reset they start in that order and only as many as the caps allow. A Triage flag runs the same pass before it starts its own change, so a change flagged just after midnight never takes a freed slot ahead of one already waiting. Manual Analyses (`POST /commits/{id}/analyses`, `POST /commits/analyses`) are neither capped nor counted, and a Retry of an automatic job keeps its input, so it counts but is not held at a cap. Concurrency stays bounded by `NUMEN_WORKER_CONCURRENCY` and `NUMEN_RUNNER_CONCURRENCY`.
- Automated runs use API keys only (A13): `domain.automated_profile` resolves the saved or default profile of a run nobody started by hand and refuses an account whose `auth_type` is not `api_key` with `api_key_required` (422, "Automated runs use only Provider accounts that hold an API key; {label} uses a subscription sign-in. Start this run by hand or select an API-key account."). It covers an imported commit's Triage (`triage_status: blocked`, `triage_result.error` and `reason`), automatic Analysis (`analysis_state: {status: blocked, error}`), automatic CVE analysis (`analysis_blocked`) and audit refresh (an `audit_refresh_blocked` event). Jev triage uses its Jev API key. Runs the Operator starts by hand may still use subscription sign-ins.
- Findings and Alerts (A11, A12): only Findings the application opens (`domain.open_finding`) send an Alert, so a Finding the Operator creates by hand (`POST /findings`) sends none. A CVE-analysis (`cve`-source) Finding alerts as `Advisory` with its CVE id as the source, and an account-cap Alert carries the Provider account's label in place of an Application name, because an account cap belongs to no Application. A legacy Numen outbox row, if retried, sends only `Asset Monitor: Alert` and its link, never its stored title or detail. Upstream Exposure is not computed until Phase 7, so every Upstream link counts as unknown, which counts as exposed, and AC-A12's not-exposed case is untested until then.
- A shared Upstream Analysis row keeps the first Application's `application_id`. The Findings it opens in the other Applications reference it through `domain.analysis_reaches`, which relaxes Numen's same-Application rule for commit Analyses only, and its drafted bundle is published once per affected Application. The opening de-duplication is application code (`SELECT … FOR UPDATE` on the Application's Finding for that subject), not a database constraint, because carried-over data holds duplicate manual Findings, so two concurrent Analyses of one commit can still race to a duplicate, as in Numen. Linking matches a short SHA (7 or more hex characters) as a prefix within one Application, and a change linked once is never opened later, even after that Finding is Remediated.
- Numen's commit review decisions (`candidate`, `confirmed`, `dismissed`) stay separate from the Finding lifecycle. The Open findings counts on the dashboard (`open_findings`) and the Application page count `open` Findings only, not Confirmed ones.
- Audit context takes `max_functions` (1–100, default 24) per request: orientation lists significant functions most significant first, and Numen analyzes at most that many, each in its own agent run; any beyond the limit are recorded in coverage as `deferred`/`deferred_units` instead of failing the audit. A function analysis runs with a 1800-second deadline and is analysed once more (`:retry` phase) when it fails on its own (a timeout, invalid output, no document); broker, lease and cancellation failures still stop the audit. A selected path that is off by leading folders resolves to the one snapshot file it matches on a directory boundary; otherwise the function is recorded as failed. Function analyses run in parallel (`NUMEN_AUDIT_CONCURRENCY`, default 3), and the job's progress reports the stage and how many functions are analysed. An interrupted, failed, or cancelled audit continues instead of starting over: lease recovery, Retry, or an identical request (same source and skill revisions, focus, max functions, and agent profile) reuses the latest interrupted checkpoint's function selection and analysed functions (checkpoints store their records as `audit-functions.json`) and re-runs only unfinished or failed functions. A continued checkpoint is marked `continued_by` and never reused twice; `fresh` starts over. Synthesis receives the per-function records as `audit-functions.json` with only an index in its prompt, so record size does not reach the prompt bound. When synthesis follows the skill's `audit-context/DOSSIER.md` layout, Numen writes the `audit-context-building.md` entry document linking it.
- `POST /applications/{id}/audit-contexts` with `{refresh_from: <context id>, profile?}` refreshes that context for the current source head: the job keeps the base's focus and `max_functions`, reuses its orientation, keeps the documents of functions whose own file is byte-identical between the two snapshots, analyses functions in changed files again, records functions whose file was deleted as `removed`, and runs synthesis with the changed-file list (`coverage.refresh`: `from`, `from_revision`, `changed_files` (first 200), `changed_files_total`, `removed_units`). A base from another source generation or skill revision, or one with no analysed functions, is refused with `refresh_unavailable`; one already at the head with `context_current`. Finished contexts keep `audit-functions.json` for refreshes; an older context without it is rebuilt from its orientation and function documents. With Application config `audit_auto_refresh` (default false), every source check queues such a refresh (idempotency key `audit-refresh:{application}:{head}`) when the newest context lags the head and no audit-context job is queued, running or cancelling; a refresh it cannot queue is recorded as an `audit_refresh_blocked` event and never fails the check.
- CVE analysis and finding artifacts start from the Application's audit context (commit analysis judges the change on its own and never receives it): a complete one built at the analysed revision, else the newest complete one of the current source generation, else one with analysed functions at that revision, else the newest such. Its files arrive under `context/` (without `audit-functions.json`); above 4 MB the function documents are left out, and above that again the context is skipped with an `audit_context_skipped` event. Facts carry `audit_context: {id, source_ref, matches_revision, complete, functions_analysed, function_documents}` (null without one), the `audit-context` prompt section explains it as untrusted orientation to verify against the pinned source — at another revision possibly describing fixed code, so never evidence that a vulnerability is absent — and the job records `audit_context_supplied`.
- Jobs run concurrently. The worker runs `NUMEN_WORKER_CONCURRENCY` job slots (default 3) plus one slot that never claims long agent, lab, or login work, so source checks, CVE syncs, version checks, and notifications proceed during long audits. Claims stay row-locked (`SKIP LOCKED`) and attempts fenced. The broker runs up to `NUMEN_RUNNER_CONCURRENCY` workloads at once (default 4); each run has its own containers, networks, and gateway, and an agent run may use up to its 1 GiB memory limit. An attempt records every runtime phase it starts (`runtime_phases`), so failure handling and lease recovery cancel all of its runs and treat it as stopped only when each is terminal; once an operation is stopping, no new phase starts, and a phase that finds its attempt cancelled or lost cancels its own run.
- Agent runs have no execution deadline unless one is requested: the backend omits `timeout_seconds` and waits until the run ends, and requested agent limits refine the broker's defaults instead of replacing them. Triage requests 120 seconds, and Analysis, CVE analysis and audit function analyses 1800 seconds; audit context has no cumulative time budget. Operators stop long runs by cancelling the job. Probe, lab, and login runs keep their time limits.
- A broker run is terminal only after owned workload cleanup is proved. Lost submission acknowledgement is resolved by authenticated attempt-token lookup; an unavailable broker/engine preserves cancelling/pending recovery instead of allowing overlapping replacement.
- API database transactions finish before an HTTP success is emitted, so a returned Application/job/artifact identifier is immediately readable and a late constraint failure cannot follow a false success.
- Native connection setup supports protected cache import. Codex also supports device login, and Claude supports its manual OAuth login: the operator pastes the authorization code via `POST /api/accounts/{id}/login/code`, and the worker relays it to the running login workload. Command Code native connections run in Pi: the bundled plugin's login shows its Studio URL, and the operator pastes the resulting API key through the same endpoint. Native import accepts pi's or the Command Code CLI's `auth.json`. Pi automatic headless OAuth setup for other providers is not exposed as a working flow.
- The first lab verifier materializes pinned/local declarative Dockerfile instructions. Executable RUN/remote ADD are rejected explicitly; uploaded originals remain downloadable/unverified.
- The pinned Pi image applies a hash/integrity-verified brace-expansion security repair and audits the patched graph during build. See the runtime patch manifest and tests.
