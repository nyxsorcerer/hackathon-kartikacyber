## Intake: token, ETag, Baseline, Backfill and Pre-filter (2026-11-13)

Deviations and limits recorded for this phase:
- **Migration merge.** Programs sharing one source URL become one Upstream repository. The Program with the newest `last_check_at` is canonical. The others' commits and snapshots move to earlier generations: they stay visible, and their analyses and findings stay intact, but they are `historical_source` and can no longer be analysed. Programs that share a URL but differ in `source_ref` or `source_path` stop the upgrade with a message naming them, so no Program's branch or subpath is dropped. `downgrade()` of `4a2b3c5d6e72` moves each repository back onto its Application when every Application links exactly one repository that no other Application links, and refuses otherwise.
- **Findings per Application (A01).** Until Phase 3, a commit analysis of a shared repository's commit runs in the context of the first Application that still uses the repository (not archived, link on and not removed; else the first that ever linked it: `commit_application`), and its Finding lands there.
- **Source repository (not in the PRD).** Numen's per-Application operations read a "source repository": the earliest linked repository that is not removed, whatever its role or on/off state. These are version recipe, version check, audit context, CVE analysis and finding artifacts. Adding an Own repository to a migrated Application, or turning a link on or off, keeps it, with the recipe and CVE cursor. Removing its link moves the source to the next earliest link and bumps the source generation, which clears the active recipe and marks audit contexts stale.
- **Fixed ref and path.** A repository's ref and path are fixed when its row is created. Applications that need different branches or subpaths of one URL share the first one's settings.
- **Lower-cased URLs.** GitHub URLs are lower-cased for identity, and the UI shows the lower-cased form.
- **No history import.** The first check no longer imports history, where Numen imported GitHub's newest page and the whole SVN history. Numen tests and the journey changed accordingly.
- **Incomplete diffs.** An incomplete diff whose analysis says `Unrelated change` is recorded as `Insufficient context`, even when the agent reported `diff_review` over a cloned repository. Numen dismissed it.
- **Mandatory GitHub token.** An existing deployment with GitHub sources and no `github` Account stops polling them, and they show `github_token_required`.
- **Short intervals.** With 5-minute intervals, `schedule()` also queues `cve_sync` (NVD rate limits) and `version_check` (which probes the live Asset) on every tick, as in Numen. A separate cadence is left for a later phase.
- **PyYAML.** PyYAML is now declared for `pnpm-lock.yaml`. Refreshing `uv.lock` reaches PyPI at build time, never from tests.
- **Release-branch cost.** Resolving a Release branch costs up to 4 GitHub branch lookups per new Locked version. Every watched Release branch adds one conditional request per poll.
- **npm metadata.** npm metadata is read from `/{name}/{version}`, or `/latest` without a lockfile version, because the full package document can be megabytes.
- **Migration drift.** `alembic check` reports no drift at the head, so its assertion stayed in.
- **Derivation.** Each derivation makes 7 GitHub contents requests plus one registry request per direct dependency, with nothing cached. Two derivations of one Application running at once apply in the order they finish (marked `ponytail:` in `Workflows.derive_upstreams`).
- **Force pushes.** A force push, where GitHub's compare fails, still makes `github_commits` page through up to 1000 list pages and import and triage them.
- **Fractional intervals.** `formatInterval` and `IntervalInput` handle whole minutes, hours or days only. A value such as 301 s set through the API shows as fractional minutes.
- **Image names (outside Phase 1).** Compose still names the `asset-monitor-backend-test`, `asset-monitor-frontend-test` and `asset-monitor-broker` images, so these runs rebuilt `asset-monitor-backend-test:0.1.0` and `asset-monitor-frontend-test:0.1.0`, which the Numen project also uses.

## Phase 2 T2: Triage (2026-11-13)

A03. Triage is now a one-shot agent run with no tools and a 120-second deadline. It is never a Herdr session, so it never reaches `herdr.dev`. The prompt carries the change as `facts.commit` (message, author, changed paths, a diff capped at 100,000 characters, and `diff_complete`), with no input files.

- **No tools.** Claude runs `claude -p --output-format json --model M --tools '' --setting-sources '' --strict-mcp-config --mcp-config '{"mcpServers":{}}' --no-session-persistence`, with `--bare` for an API key and `--effort`. It gets no `--json-schema`, because structured output relies on a tool. Pi runs `pi_no_tools_argv`: `PI_BASE` plus `--print --mode json --provider P --model M --no-tools` and `--thinking`. In the pinned Pi 1.0.0, `--no-tools` disables every built-in and extension tool. `--no-extensions` stops discovery, though an explicit `-e` still loads, so only the Command Code provider extension loads, and only for that provider. `test_triage_is_offered_no_tools` checks the argv. `test_pinned_claude_triage_is_offered_no_tools_with_loopback_provider` runs the pinned Claude CLI against a loopback Messages API with no network: no request offers tools, the envelope is `subtype: success` with the reply in `result`, and `final_text` returns it. In `test_pinned_pi_cli_runs_commandcode_plugin_against_its_provider_api` the provider API receives `tools: []`, and in the native-protocol test the Triage case has no active tools.
- **Codex refused.** `RunRequest`, `agent_argv`, `resolve_profile` (default profiles, Application profiles and the profile an import resolves) and `ApplicationConfig.triage_mode` all refuse Codex Triage. The API error is `triage_codex_unsupported`, or `validation_error` for the mode. A stored Codex mode blocks import with that reason (`test_triage_on_codex_is_refused_with_a_clear_error`, `test_codex_triage_is_refused`). The Application form no longer offers Codex for Triage.
- **Application code validates the reply.** The runner returns `{reply}` without schema validation or a Pi restatement, and the credential scan still applies (`test_triage_returns_the_raw_reply_without_schema_validation`). The backend first replaces configured secrets with `[redacted]`. It then takes the JSON from the first `{` to the last `}` and validates it against the reduced schema: `decision`, `title` (1–300 characters) and `reason` (1–2,000 characters). `change_kind` and `confidence` are gone from agent Triage, and Jev keeps them.
- **Failure and retry.** A reply that fails the schema fails the job with `invalid_agent_output`. The commit's `triage_status` becomes `failed`, and its `triage_result` holds `{error, reason, attempt, retry_job_id?}` with no `decision`. `review_decision` is unchanged. The worker treats every failed `commit_triage` or `jev_triage` the same way: unless it was cancelled, lost its lease or its input changed, it queues the same kind with `attempt` n+1 and the same profile, not before n minutes, up to three attempts (`test_a_reply_that_fails_the_schema_is_recorded_failed_and_retried`). This replaces Numen's failure record, which wrote `decision: insufficient_context`.
- **Transcripts.** Migration `8e6f7a92b1c6` adds the `transcripts` table (`id`, `job_id`, `kind`, `subject_id`, `data`, `created_at`), and the downgrade drops it (`test_postgres_migration_adds_triage_transcripts`). Each Triage run that returns a reply, valid or not, stores a row: `kind: triage`, `subject_id` the commit, and `data` with `prompt`, `reply`, `status`, `error`, `profile`, `run_id` and `execution`. A failed run's row is committed before the failure is raised. Jev stores its `request` body, which never holds the key, and the raw `response` (`test_each_triage_run_stores_its_transcript`, `test_jev_official_model_discovery_and_typed_triage_keeps_uncertainty`).
- **Kept.** Jev triage, Triage turned off per Application (`test_triage_can_be_turned_off_per_application`) and the shared repository triaged once all still work. So does a Pre-filter hit that Triage rejects: it stays in the commit list with both its `prefilter` and its `triage_result` (`test_prefilter_hit_rejected_by_triage_stays_listed_with_both_results`). A diff over 100,000 characters is truncated and counts as incomplete, so it is never Unrelated (`test_long_diff_is_truncated_and_never_unrelated`).

Deviations and limits:

- **Dead code removed.** With Triage off the tool-profile path, every remaining operation writes under `outputs/`. This removes `adapters.WRITE_OPERATIONS`, `agent_argv`'s `session` parameter and Codex's `:read-only` profile. `pi_repair_argv` is renamed `pi_no_tools_argv`.
- **Runs without a reply.** A run that times out or fails in the runner has no reply. It gets no Transcript; its job error and the commit's `triage_result` record it, and it is retried.
- **Configuration errors are retried too.** A configuration error such as `triage_codex_unsupported` for an already-queued job is attempted three times before it stays failed.
- **Stored Codex mode.** An Application stored with Codex Triage cannot be saved, for any field, until its Triage mode is changed, because PATCH validates the whole configuration.
- **Prompt text.** The runner's shared preamble and the `rules` section still mention writing to `/workspace/outputs`. The Triage task text says there is nothing to write.
- **Prompt size.** The diff is capped at 100,000 characters before JSON encoding. A diff of mostly non-ASCII text can therefore exceed the runner's 262,144-character prompt bound. That run is refused and retried, and it then stays failed (never Unrelated).
- **Engine flag untested.** No unit test covers `engine`'s Triage-is-not-interactive condition, because it is inline in `DockerEngine.run`.

## Phase 2 T4: Automatic Analysis, caps and API keys for automated runs (2026-11-13)

A04 (automatic start, caps) and the first bullet of AC-A13.

- **Automatic start.** A Triage decision of `security_candidate` or `insufficient_context`, agent or Jev, calls `domain.start_analysis`. It queues one `commit_analysis` per commit (idempotency key `analysis:{commit id}`) with job input `automatic: true` and `shared`, and sets `analysis_state: {status: queued, job_id}`. `unrelated` starts nothing, and a second flag starts nothing more (`test_triage_flag_starts_one_automatic_analysis`).
- **Shared Upstream commit.** A commit of a repository that more than one Application uses is analysed once, in the first such Application's context, with `shared: true`. It starts even when that Application's cap is full, and it counts against the Provider account cap (`test_shared_upstream_commit_is_analysed_once_and_counts_only_against_the_account_cap`, `test_shared_upstream_repository_is_polled_and_triaged_once`).
- **Caps.** 10 per Application (only `shared: false` jobs) and 30 per Provider account (`profile.connection_id`) per UTC day. They are counted from today's automatic `commit_analysis` job rows, so they survive a restart with no extra state (`test_caps_persist_across_restarts`). Over a cap the change gets `{status: waiting_for_cap, since, cap}` and one `actions` row per scope and day (`analysis_cap_reached`, `day`, `limit`) is recorded (`test_application_cap_makes_new_automatic_analyses_wait_and_records_one_cap_event`, `test_account_cap_of_thirty_makes_new_automatic_analyses_wait`). Another API-key account still starts the change, because the account cap is per account.
- **Reset.** `domain.schedule()` re-checks waiting changes oldest `since` first. After 00:00 UTC they start in that order and only as many as the caps allow, and a change that still waits keeps its `since` (`test_caps_reset_at_midnight_utc_and_waiting_changes_start_oldest_first`). The count, cap-event and `FOR UPDATE SKIP LOCKED` waiting queries are also run against PostgreSQL (`test_postgres_automatic_analysis_caps_count_todays_automatic_jobs`).
- **Manual Analysis.** It is neither capped nor counted, so it starts while both caps are full (`test_manual_analysis_still_works_at_a_cap`).
- **API keys only.** `domain.automated_profile` refuses an account whose `auth_type` is not `api_key` with `api_key_required` and says why. An imported commit's Triage is then `blocked`, an automatic Analysis is `{status: blocked, error}`, an automatic CVE analysis lands in `analysis_blocked`, and an audit refresh records `audit_refresh_blocked`. No job is queued, and a manual Analysis on the same subscription sign-in is queued (`test_automated_runs_refuse_accounts_without_an_api_key`).
- **Existing tests.** The Triage tests that drain the queue now leave the automatic Analysis unrun (`exclude=("commit_analysis",)`) or assert it is queued, because without a stored snapshot it would fetch from GitHub. The whole backend suite also passed with `NUMEN_GITHUB_API_URL` and `NUMEN_NVD_API_URL` pointed at a closed loopback port, so no test reached a real host. The only failure was `test_parent_lookup_checks_the_requested_commit_and_immutable_hashes`, which asserts the default URL against its mocked transport.

Deviations and limits:

- **Blocked stays blocked.** A change blocked for want of an API key is not retried when the profile is fixed. A later Triage flag, or Analyze by hand, starts it.
- **Retry counts but is not held.** A Retry of an automatic job keeps `automatic: true`, so it counts toward the day's caps, but it is queued even at a cap.
- **Soft caps under concurrency.** Two workers flagging changes at the same moment can each see the last free place, so a cap can be overrun by the number of concurrent Triage jobs.
- **Scheduler cost.** Each 15-second scheduler tick re-checks every waiting change with two or three count queries. That is fine at current volumes; it needs an index on `analysis_state` or a stop on the first full cap if the waiting list grows large.
- **No Alert yet.** The cap-reached event is an `actions` row; Phase 3 turns it into an Alert. The UI does not show `waiting_for_cap` or `blocked` yet (T5).

Deviations from the plan, PRD and ADRs:
- **Lab bases.** Numen's bundle contract allowed digest-pinned bases. Lab bases are now only `asset-monitor-lab:0.1.0` (pinned Node 24.9.0), `scratch` and earlier stages, and URL `ADD`/`COPY` sources are refused, because the Engine would fetch these outside `--network none` and a retained base contradicts ADR-0005's "images removed after every run". A carried-over bundle with a digest base reads as Draft and is refused at Lab start. A Node app that needs another Node version cannot get one in this release.
- **Install scripts.** AC-A07's "cannot run a dependency install script" is enforced for npm: `--ignore-scripts` in phase one and `ignore-scripts=true` in the Lab base's global npmrc, which covers `npm install`, `ci` and `rebuild` in `RUN` or `CMD`. `RUN` stays accepted and runs offline. A bundle that runs a dependency's script directly (`node node_modules/x/install.js`) still runs it, with no network. `composer --no-scripts` is not implemented, because Node is the only first-release stack.
- **Node only, checked late.** `artifacts.completeness` does not check the Node-only rule, so a non-Node bundle reads as complete and is refused with `lab_stack_unsupported` only at Lab start, after its Approval.
- **Image limit.** The 4 GB is checked after the build and covers the whole image, the Lab base layers included. A step that writes more than the host disk holds is stopped only by the 15-minute build deadline; the phase-one dependency volume is bounded only by the disk and that deadline.
- **Registry egress untested against a registry.** No test reaches a registry: runtime fixtures vendor `file:` dependencies and the gateway's allowlist is unit-tested. With a real registry, the gateway's 64 MiB-per-tunnel bound could cut a large install over one keep-alive connection; lockfiles that resolve from other registries or git URLs fail visibly; the registry must be https on port 443.
- **Approval rate limit.** Like login's, it is in memory per app process: it resets on restart and is keyed by client address, so behind the Operator's tunnel every request shares one address. Refused Approvals are rate-limited but not recorded as Actions; only granted ones are.
- **No Lab retry.** Retrying a `lab_run` job is refused; a new Lab needs a new Approval. The worker's crash recovery still re-runs an approved job at least once, which is the approved action, not a new one.
- **Own-repository Labs.** They use the stored snapshot, which omits binary media and is bounded (20,000 files / 64 MiB), and `package.json` must sit at the repository root. Completeness is judged on the bundle alone, so an Own-repository Dockerfile must `COPY . /app/`. Finding generation (regenerating a bundle) gets no `own_repository` fact, so its agent may bundle a minimal app, which still runs because the bundle's files win. A repository that is Own for one Application and Upstream for another gets one drafted bundle published to both Findings, and a Dockerfile-only bundle written for the Own case fails the Upstream Application's bundle-only Lab with `lab_stack_unsupported`. - **Reproduces after Approval.** No single automated test covers the Own-repository overlay and the real Engine together; the Done-when row above names the three pieces that do.
- **Run deadline.** The Lab's 10 minutes now start after the build and include the app's startup, where Numen gave one shared budget, so a slowly booting app may time out. The backend's per-container memory default (6144 MB) is unchanged; runtime tests pass small limits.
- **No migration.** The Approval is an `actions` row and `LabRun.data` (JSON) gains `source_ref`.

Deviations from the plan, PRD and ADRs:
- **Hashes computed by application code.** The PRD's extracted indicators include hashes. The agent drafts none (the schema refuses a `hashes` field); application code hashes each file it keeps from the commit's snapshot.
- **Indicators must be literal.** A file is kept only if commit.json lists it as added or changed, and a host, URL or command only if it occurs literally in a line the diff adds. An encoded or obfuscated value, or one in the uncaptured part of an incomplete diff, is listed as rejected with its reason, not kept.
- **Snapshot bounds.** Snapshots omit binary media and hold up to 65,536 files, 64 MiB per file and 512 MiB in all (`artifacts.MAX_SOURCE_FILES`, `MAX_FILE`, `MAX_SET`), so a payload hidden in an image or font, or in a repository over the bounds, can never satisfy the `changed` check, and its Finding stays Draft. The `parent` and `baseline` checks scan the same snapshots, so they cover no media file and not the repository's own root `manifest.json` (the snapshot's artifact manifest takes that path and is never sent): a rule that would match only those files on the server still passes.
- **No prose `cleanup-report.md`.** The cleanup report is structured data on the Finding (`static_proof.indicators` and `cleanup_report`). The agent drafts only the indicators and `reachable_secrets`; application code adds the commits, the releases and the Detection rule, and the UI renders them.
- **Generation refused.** Lab bundle generation does not apply to a static Proof, so `artifact-generations` refuses a Malicious change Finding with 409 `generation_not_available`; it is re-drafted by analysing the commit again or uploading a corrected `detection-rule.yar`.
- **Approximate containment.** The commits that contained the change are the later stored commits on the same branch by `committed_at`, plus the Baseline for a Backfill commit, and the releases are the tags pointing at those. Tags on unwatched branches, backports and later reverts are missed. Phase 7's tag containment replaces this (marked `ponytail:` in `detection.containing_commits`).
- **Release-branch Baseline.** A commit on a Release branch is checked against the repository's default-branch `baseline_revision`, because a watched branch stores no Baseline revision of its own.
- **Validation per Finding.** Validation runs once per Finding revision, so a shared Upstream commit in N Applications runs N identical yara jobs; the parent and Baseline snapshots are stored once.
- **Done-when on the real Engine.** No single test runs the backend and the real Engine together, and the journey has no agent, so it cannot produce a Malicious change Verdict. As in Phase 4, the Done-when row names the two pieces that prove it on one fixture: the backend `FixtureBroker` test and the runtime test.
- **Failed validation jobs.** A validation job that fails (broker down, a snapshot fetch error) leaves `static_proof.status` `pending` with its job link and no failed check; the Operator retries the job.
- **Customized templates.** An Operator-customized `commit_analysis` template lacks the new `detection-rule` include. The appended result schema still names the fields, but such runs may fail `invalid_agent_output` until the template is reset; `GET /prompts` already flags `default_changed`, and no migration resets it.

A Lab for another Finding is not refused when its tree contains a known Malicious change, such as an Own-repository Proof at a later commit or an Upstream version that shipped it: install scripts stay disabled, but a payload in runtime code (a required module, `server.js`) would run during that Lab's run phase. Refusing it needs Phase 7's tag containment.
- **No migration.** `static_proof` and `cleanup_report` live in `findings.data` (JSON), and job kinds are strings.
