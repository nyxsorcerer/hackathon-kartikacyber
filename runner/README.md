# Numen execution runtime

The broker is the trusted Engine control plane. Production application and generated workloads do not receive its Docker socket. It accepts only the fixed API in `docs/implementation-contract.md`; unknown launch fields, unsupported profiles, unsafe paths, remote JSON-schema references, excessive limits and invalid outputs are rejected. `X-Broker-Token` authenticates every control and credential route.

## Images and checks

Agent packages are npm-locked: Pi 1.0.0, Claude Code 2.1.288 and Codex 0.160.0. Command Code provider 0.7.3 is loaded only when the resolved profile explicitly enables it. The Pi image repairs upstream brace-expansion5.0.9 to the integrity-verified compatible5.0.12 tarball, repairs its actual nested shrinkwrap/locks, and routes the exact hash-verified compiled CLI entry point to the fixed module; details and advisories are in `dependency-patches.lock.json`. Post-repair npm audit must pass during image build. Python dependencies use `uv.lock`; base images use immutable multi-platform digests. Trail of Bits audit-context-building 2.0.2 is vendored with attribution, CC-BY-SA-4.0 license and a content hash manifest. The separate workload image tags are `asset-monitor-pi`, `asset-monitor-claude`, `asset-monitor-codex`, `asset-monitor-probe`, and `asset-monitor-lab`, and the per-run sidecars are `asset-monitor-gateway` and `asset-monitor-dind`, all `:0.1.0`. A build run needs `asset-monitor-dind` and, for the base it streams in, `asset-monitor-lab`, so the build-sandbox Engine tests require the `images` profile to have been built.

```sh
scripts/compose.sh --profile images build
scripts/compose.sh --profile test run --build --rm runner-tests
scripts/compose.sh --profile test run --build --rm runner-runtime-tests
```

The last command explicitly enables real Engine tests with `NUMEN_DOCKER_TESTS=1`; it does not silently substitute fixtures. Its trusted test driver receives Engine control and uses the `runtime-tests` instance label. Production broker cleanup is scoped to `NUMEN_RUNNER_INSTANCE`, normally the Compose project name. Only integration tests make a credential-free CONNECT to `api.openai.com`; no authenticated inference or production target is used.

## Boundary

Each workload runs as UID/GID10001 with a read-only image, dropped capabilities, no-new-privileges, bounded memory/CPU/PIDs/filesystems/outputs and an execution deadline. Validated inputs are copied by a fixed, credential-free staging container into a job volume mounted read-only. Workspaces, caches and temporary files are bounded tmpfs mounts. Outputs are regular files without links, with normalized relative paths, validated JSON results, integrity hashes and aggregate byte limits. A disk-backed workspace's outputs are collected from its volume by a fixed credential-free container instead of through the completion envelope, since a log rotates at its bound and would truncate an application-sized bundle; they are validated identically. Credentials and arbitrary child stderr are not returned in ordinary status/errors/logs.

A `cve_analysis` or `commit_analysis` agent run requests `build`. It then receives a private per-run rootless Docker daemon on its job network at `tcp://docker:2375`, a disk-backed writable workspace, raised process/memory/output limits, a shell (Codex workspace policy, Claude `Bash`, Pi `numen_shell`), `git`, and proxy access to source, package and image registries. The daemon has its own egress network so builds can install dependencies, and the run's workspace volume is mounted into it at the same `/workspace` path so bind mounts resolve; paths outside `/workspace` are not mountable, and `/workspace/share` is world-writable because containers the daemon starts cannot map back to the workload's user. Files those containers create stay owned by the daemon's own mapped user, so the workload can read and unlink them but never change their ownership, and anything bound for `/workspace/outputs` has to be copied there by the workload itself. `asset-monitor-lab:0.1.0` (Debian bookworm with Python 3.12, `curl`, `git`, `unzip` and CA certificates, root by default so a bundle's Dockerfile can `apt-get` its runtime; the engine still starts the PoC workload on it as the unprivileged job user) is streamed into the daemon's empty store at startup because it cannot be pulled, so the agent can iterate on the same offline base the verifier uses. Build rejections the daemon records in its own log (an unavailable image, a bind mount it does not have, exhausted disk) are reported to the operator as fixed messages; for anything else the daemon's log stays on the host under its run label. Before preparing a build run, the engine reads the Docker disk's free space with a throwaway `df` container and refuses with `build_disk_low` below `NUMEN_BUILD_MIN_FREE_GB` (default 10), because every concurrent build daemon stores its images on that disk; an unreadable report never blocks a run. Numen images carry the label `org.pruferva.asset-monitor.image=true`, and `make build` ends with `make prune`, which removes only dangling images with that label so rebuilds do not accumulate. When the run carries a `repository`, Numen first updates a shared, lock-protected git mirror (volume `numen-git-cache-<instance>`, never mounted by an agent and kept across runs) through the run's gateway and clones it with full history into `/workspace/repo` at the pinned revision, so the agent does not clone again; a failure is reported and the run continues. In a build run Pi's `numen_write` may write scratch files anywhere under `/workspace` except `inputs/`; only `outputs/` is collected. The host Engine socket is still never shared with any workload, the agent container stays nonroot with a read-only image and dropped capabilities, and the daemon container holds no credential. The daemon container is privileged because nested containers require it on Engine 20.10 without cgroup delegation; treat a build run as code execution with internet access on the operator's behalf, and note that its daemon, images, containers and workspace are destroyed with the run.

Workloads join only an internal job network. A credential-free per-job proxy has separate egress and allows CONNECT only to the selected provider's fixed TLS hosts on443. Disregarding proxy configuration does not grant direct egress. Target reads use GET/HEAD through an expiring token, explicit origins, `request_budget`/`max_requests`, response/aggregate byte budgets, redirect validation and DNS-pinned sockets. Private/link-local destinations are denied unless the exact asset network is explicitly authorized; application/control networks remain denied.

Pi uses bundled source-read/list and output-write tools, with ambient resources/built-in execution tools disabled. Claude uses restricted file tools, explicit settings/MCP sources and a scoped target MCP tool. Codex derives native permission profiles from `:read-only` for triage and `:workspace` for report/artifact generation, denies tool reads of `/home/job` and excludes provider credentials from shell inheritance. Input mounts remain read-only in both policies. Codex alone uses a narrow Moby20.10.22-derived seccomp adjustment for nested native namespaces; other profiles use Engine default seccomp. Native-policy failures are explicit failures. Codex/Claude structured CLI output uses a fixed `result_json` string envelope, then validates the decoded object against the application schema; this supports application evidence objects without weakening validation or relying on a provider's unrestricted-object schema dialect.

## Interactive agent sessions (Herdr)

With `NUMEN_AGENT_BACKEND=herdr` (the Compose default on this branch) an agent workload starts a private [Herdr](https://herdr.dev/docs/) 0.9.3 server inside its own container and runs the agent's interactive TUI in a Herdr pane instead of its print mode. Onboarding, workspace trust and API-key approval are pre-answered so startup is unattended. Every agent runs on the terminal's main screen so its conversation reaches scrollback: Claude Code with `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` (its default fullscreen renderer uses the alternate screen, which keeps no scrollback), Codex with `--no-alt-screen`, and Pi with `--tui-mode regular`. The agent writes its result to `/workspace/outputs/result.json`; the workload validates it against the application schema and finishes once the agent is quiet with a valid result. A quiet agent without one is reminded with the validation error up to three times, then the run fails. Every session operation can therefore write `outputs/`; input mounts stay read-only.

The operator reaches a session only through the broker: `GET /internal/runs/{id}/session` returns agent status, hold state, `live`, and the full saved native conversation/tool output plus the latest terminal view. The terminal view is read from Herdr with `format: "ansi"`, so it keeps the agent's own colors (SGR codes only). Herdr returns at most 1,000 lines per read and its visible screen is one viewport, so each 2-second session poll appends the lines that scrolled off screen to a saved scrollback (`.numen-scrollback.json`, matched by overlap so nothing repeats). The terminal view is that scrollback plus the current screen, up to 10,000 lines (the oldest 1,000 are dropped together, with a note); output that outruns one read between polls is marked as a gap. The Transcript keeps the full conversation regardless; settling compares the text without them, and credential redaction tolerates whitespace or escape sequences between a secret's characters. History has no dashboard row/byte cap. Pi session persistence is enabled for Herdr; Claude/Pi tool-output files use private fixed directories. A private per-run home volume survives workload exit and cancellation until the broker archives the redacted transcript under `NUMEN_RUNNER_STATE/sessions/`. Checkpoints are saved independently of browser polling. Reads after completion or broker restart use that retained archive; late live reads cannot overwrite the finalized history. An abrupt broker restart retains the last redacted checkpoint, and native tool truncation markers remain visible.

`POST /internal/runs/{id}/session` accepts `{action: "prompt", text}`, `{action: "keys", keys}`, `{action: "hold"}` or `{action: "release"}` for live sessions. Operations execute fixed commands as the unprivileged workload user. Post-exit history reads use a silent, network-isolated helper with only that run's home mounted read-only; raw transcript bytes travel through private exec stdout, never Docker logs. A held session never finishes on its own, including after a failure, until released or cancelled. `NUMEN_AGENT_BACKEND=native` restores one-shot print mode. Earlier output already discarded by an old session or by the native CLI cannot be reconstructed.

## Connections and native cache ingress

Pi catalogs come from the pinned SDK/provider extension and are intersected with the account's authenticated provider model list. Codex uses paginated native app-server `model/list`, plus API account model access for API-key mode. Claude uses the authenticated model endpoint. Effort values are retained from the runtime/provider metadata; unsupported selected models/efforts fail before inference. Missing usage is `null`.

Codex native setup uses `login --device-auth`. Claude native setup uses `claude auth login --claudeai` in its manual flow: the workload emits only the authorization URL, then waits for the operator's code. The worker relays the code to `POST /internal/runs/{id}/login-input`, which keeps it in broker memory only. The engine writes it into the workload's private home through exec stdin (never argv or environment), and the workload forwards it to the CLI's stdin. Command Code native setup runs the pinned plugin's `/login` through pi's `ModelRuntime.login` (`pi-commandcode-login.mjs`): it emits only the Studio URL, skips the localhost callback that cannot reach the container, and reads the pasted API key over the same login-input channel. The plugin validates the key with `/alpha/whoami`, pi stores it in its private `auth.json`, and later jobs pass it to the plugin as `COMMAND_CODE_API_KEY`. Login events contain only the native verification URI/device code and code-submission state. Pi native OAuth for other providers is explicitly unsupported by this runtime. Claude API keys and protected imported Claude native caches have separate execution paths. Actual account eligibility, OAuth model-endpoint access and native provider/proxy inference compatibility require operator credentials and remain unverified without them.

New/refreshed native caches use private ephemeral files and a fixed Engine exec transport inside the workload's mount namespace. The transport validates a bounded regular file and keeps its private response separate from Docker's main stdout/stderr logs. The broker retains the cache in memory for ten minutes after authoritative completion (kept available while cleanup is pending). A changed cache sets `credential_updated:true` in the ordinary run response, including failed native runs when refresh completed. The vault consumer fetches it with authenticated `GET /internal/runs/{id}/credential`, revision-fences encrypted ingestion, then deletes it with `DELETE` after commit. Ordinary `result`, outputs and events omit cache values. Plaintext temporary state is removed with the workload; broker restart never restores plaintext caches.

## Lab bundles

Artifact upload does not build anything. Explicit verification requires `poc.py`, `report.md` and `vulnerable-app/Dockerfile` plus the application's own files, which may be a whole tree: the bundle travels as one compressed archive and is bounded by the expanded archive limits, not by a per-file count. The verifier builds that Dockerfile as its own project, with `RUN`, multi-stage, continuations and the network its dependencies need, on a per-run bridge. It still refuses a floating base, a `COPY`/`ADD` source outside the bundle, a `--from` naming neither a stage nor a digest, and build mounts or privileged build flags. `FROM` may name the bundled `asset-monitor-lab:0.1.0`, `scratch`, an earlier stage, or any image pinned by digest, which is fetched once if the host store lacks it. Uploaded originals are preserved; unsupported bundles remain downloadable and unverified.

The application then starts at `http://application:8080` with a writable root filesystem, its image's own user and an ordinary capability set, so it can initialise a database and complete an install, and its per-run bridge reaches the internet while Docker's bridge isolation keeps it away from the application and control networks. Its PoC verifier shares only the internal job network and has no egress, so an observed proof comes from the application rather than the network. Neither receives a provider or application credential. Observed results retain the built image digest, exit code and bounded log. A nonzero PoC is `status:not_reproduced, verified:false`; successful recording of that result never means successful reproduction. Cancel/timeouts/restarts remove owned containers, volumes, networks and job images. A failed cleanup keeps the run nonterminal (`cancelling`, `cleanup_pending`), preserves its pending result/error privately, retries reconciliation, and blocks new execution with503. A terminal status is published only after actual owned-resource cleanup succeeds. Interrupted work cannot falsely succeed or claim it stopped while Engine availability is unknown. Authenticated `GET /internal/attempts/{attempt_token}` resolves lost submit acknowledgements; explicit `{run_id:null,status:"absent",reconciled:true}` is returned only after reconciliation, while503/404 cannot prove absence.
