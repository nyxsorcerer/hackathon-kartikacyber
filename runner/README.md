# Numen execution runtime

The broker is the trusted Engine control plane. Production application and generated workloads do not receive its Docker socket. It accepts only the fixed API in `docs/implementation-contract.md`; unknown launch fields, unsupported profiles, unsafe paths, remote JSON-schema references, excessive limits and invalid outputs are rejected. `X-Broker-Token` authenticates every control and credential route.

## Images and checks

Agent packages are npm-locked: Pi 1.3.0 (with `@earendil-works/pi-ai` 1.3.0), Claude Code 2.1.288 and Codex 0.160.0. The Command Code provider `pi-commandcode-provider` 0.7.8 is pinned in `plugins.lock.json` by version and its registry sha512 integrity, which equals its `package-lock.json` entry, and is loaded only when the resolved profile explicitly enables it. Adding or changing a plugin means editing that file and the Pi lock and rebuilding the image. Pi 1.3.0 pins the fixed brace-expansion 5.0.12 itself, publishes no shrinkwrap and bundles the fixed `expand` (with `maxDepth` and `maxRewrites`) into its CLI, so the image applies no dependency patch. Pi 1.0.0 needed one (`patch-pi-dependency.py`, for the brace-expansion 5.0.9 it shrinkwrapped and bundled), and it was removed with the upgrade. `undici` stays overridden to 8.12.4, and `npm audit --omit=dev --audit-level=high` must pass during the image build. Python dependencies use `uv.lock`; base images use immutable multi-platform digests. Trail of Bits audit-context-building 2.0.2 is vendored with attribution, CC-BY-SA-4.0 license and a content hash manifest. The separate workload image tags are `asset-monitor-pi`, `asset-monitor-claude`, `asset-monitor-codex`, `asset-monitor-probe`, and `asset-monitor-lab`, and the per-run sidecar is `asset-monitor-gateway`, all `:0.1.0`. No agent image carries a Docker client, and there is no build daemon image (ADR-0005). Broker reconciliation also removes the instance's git mirror volume (label `org.pruferva.asset-monitor.cache=git`), which build runs shared before ADR-0005 and nothing mounts any more. Numen images carry the label `org.pruferva.asset-monitor.image=true`, and `make build` ends with `make prune`, which removes only dangling images with that label so rebuilds do not accumulate.

```sh
scripts/compose.sh --profile images build
scripts/compose.sh --profile test run --build --rm runner-tests
scripts/compose.sh --profile test run --build --rm runner-runtime-tests
```

The last command explicitly enables real Engine tests with `NUMEN_DOCKER_TESTS=1`; it does not silently substitute fixtures. Its trusted test driver receives Engine control and uses the `runtime-tests` instance label. Production broker cleanup is scoped to `NUMEN_RUNNER_INSTANCE`, normally the Compose project name. Only integration tests make a credential-free CONNECT to `api.openai.com`; no authenticated inference or production target is used.

## Boundary

Each workload runs as UID/GID10001 with a read-only image, dropped capabilities, no-new-privileges, bounded memory/CPU/PIDs/filesystems/outputs and an execution deadline. Validated inputs are copied by a fixed, credential-free staging container into a job volume mounted read-only. Workspaces, caches and temporary files are bounded tmpfs mounts. Outputs are regular files without links, with normalized relative paths, validated JSON results, integrity hashes and aggregate byte limits. Credentials and arbitrary child stderr are not returned in ordinary status/errors/logs.

No agent run builds anything (ADR-0004, ADR-0005). `commit_analysis` and `cve_analysis` read the pinned revision's source snapshot, staged read-only at `/workspace/inputs/source` as one compressed archive input (no git history; binary media is skipped and the snapshot is bounded by the source and archive limits), and write only to `/workspace/outputs`. They have no Docker daemon, socket or client, no shell tool on Pi or Claude, and no egress beyond the gateway below; `RunRequest` refuses `build` and `repository` as unknown fields and agent runs keep the ordinary `MAXIMA` ceiling. A bundle such a run writes is a draft: only a `lab` run, which the Operator starts after an Approval, builds it (see Labs). `patch_drafting` (A08) has the same boundary: it reads the Own repository's snapshot at its default-branch head read-only under `inputs/source` and writes only `outputs/patch.diff`, which the application validates with `git apply` before an Approval can see it. The application gives it a 20-minute deadline (`limits.timeout_seconds` 1200), and the GitHub write token is never among its inputs: like every stored credential, the application refuses it in agent inputs.

Workloads join only an internal job network. A credential-free per-job proxy has separate egress and allows CONNECT only to the selected provider's fixed TLS hosts on443, plus `herdr.dev` for an agent run that hosts a Herdr session, because Herdr fetches its agent-detection manifests there at start and every 30 minutes (`engine.gateway_config`). Every other host is refused with 403 before any DNS lookup, so package and source registries are unreachable. Disregarding proxy configuration does not grant direct egress. Target reads use GET/HEAD through an expiring token, explicit origins, `request_budget`/`max_requests`, response/aggregate byte budgets, redirect validation and DNS-pinned sockets. Private/link-local destinations are denied unless the exact asset network is explicitly authorized; application/control networks remain denied.

A Served-content check (A10) runs as a `probe` whose `target_policy` sets `served_content: true`. That policy has no origin list: any http(s) origin is allowed, and `gateway.origin()` still refuses other schemes, credentials in the URL and fragments, while the method stays GET or HEAD. Each request may name `user_agent` from the fixed pair `gateway.USER_AGENTS`, `browser` (a desktop Chrome) or `googlebot`, sent on every redirect hop; any other name is refused, and a request that names none keeps the version recipe's `Numen-version-fetch/1`. Every address, on every redirect hop and for each script, is resolved and must be public: an IPv4 address inside IPv6 is unwrapped, and anything that is not `is_global`, or is multicast, is refused, which covers private, loopback, link-local, multicast, reserved, unspecified and shared addresses. The socket is pinned to the checked address and TLS is verified against the hostname, so DNS rebinding finds nothing to rebind. The request's own `allowed_private_cidrs` is ignored for served content: the only private range is the demo fixture's, set on the demo VM by the broker's `NUMEN_SERVED_CONTENT_FIXTURE_NETWORK`, which names a Docker network. Its subnets become `allowed_private_cidrs` and the run's gateway joins that network (`engine.served_fixture_cidrs`). The setting is empty by default, and the application and control subnets stay blocked whatever it names. The test override `compose.test.yaml` names `asset-monitor-test-served`, an internal network that the fixture service joins with the extra alias `cdn.clickfix-fixture.test`, so the journey's Served-content checks reach the fixture's judol and ClickFix pages through the real gateway and nothing else. The demo overlay `compose.demo.yaml` (docs/demo.md) sets `NUMEN_SERVED_CONTENT_FIXTURE_NETWORK` to its own project's `<project>_served` network, and points Lab phase one's `NUMEN_NPM_REGISTRY_URL` at `https://registry.invalid`, because the demo Own repository vendors its stand-in `react-server-dom-webpack` as a `file:` tarball and needs no registry.

Tool profiles are fixed per operation in `adapters.agent_argv` by the flags that decide which tools exist, never by `--allowedTools`, which permission bypass ignores (ADR-0004). Triage (`commit_triage`) is one print-mode call with no tools at all, never a Herdr session (so it gets no `herdr.dev` either). Claude runs `claude -p --output-format json --model M --tools '' --setting-sources '' --strict-mcp-config --mcp-config '{"mcpServers":{}}' --no-session-persistence`, plus `--bare` for an API key (with no tools its minimal mode drops nothing and skips hooks, plugins and `CLAUDE.md`) and `--effort`; it has no `--json-schema`, because structured output needs a tool, and no `--permission-mode` or `--settings`. Pi runs `adapters.pi_no_tools_argv`: the fixed `PI_BASE` (`--no-session --no-extensions --no-skills --no-prompt-templates --no-themes --no-context-files --no-approve`) plus `--print --mode json --provider P --model M --no-tools` and `--thinking`. In the pinned Pi 1.3.0, `--no-tools` disables every built-in and extension tool and `--no-extensions` disables extension discovery and the built-in extensions while an explicit `-e` path still loads, so only the Command Code provider extension loads, and only when that provider is selected; the `pi-tools.ts` extension is not loaded. The prompt ends with "You have no tools. Reply with only one JSON object matching the schema." and the workload returns `{reply}`, the final text (`adapters.final_text`: Claude's `result` from a `subtype: success`, non-error envelope; Pi's final assistant text), without schema validation or a Pi restatement; the credential scan still applies, and the application validates the reply. The broker checks that a Triage result is exactly `{reply}` (a string) and does not validate it against the Triage schema it was sent, so a reply that fails that schema reaches the application, which records it as failed. Codex has no flag that removes its shell, so it is refused for Triage, Analysis, CVE analysis and patch drafting (ADR-0004: Analysis and patch drafting get a read-only checkout and a write-only output directory and run nothing). `RunRequest` and `agent_argv` both raise "Triage on Codex is refused until a no-tools restriction is verified for it", "Analysis and CVE analysis on Codex are refused until a Codex mode without a shell is verified", or "Patch drafting on Codex is refused until a Codex mode without a shell is verified". `test_pinned_claude_triage_is_offered_no_tools_with_loopback_provider` runs the pinned Claude CLI against a loopback Messages API and sees no tools in any request, and the Pi runtime tests see `tools: []` at the Command Code provider API and no active tools in the CLI. Every other operation writes under `outputs/`. Pi runs with `--no-builtin-tools` and only its bundled tools: `numen_read` and `numen_list` over `inputs/`, `outputs/` and `/opt/resources`, `numen_write` under `outputs/`, and `target_fetch` only for `version_recipe`; there is no shell tool. Claude gets `--tools Read,Grep,Glob,Write,Edit`, `--restricted` (file tools confined to `/workspace` and `/opt/resources`, no Bash or WebFetch), `--setting-sources ''`, `--strict-mcp-config` with only the target MCP server for `version_recipe`, and `--permission-mode dontAsk`, which denies whatever is not approved. `--settings '{"permissions":{"allow":["Edit(//workspace/outputs/**)"]}}'` approves file writes under `outputs/` only (an `Edit` rule covers every file-editing tool), plus `mcp__numen_target__target_fetch` for `version_recipe`. The pinned Claude Code 2.1.288 honours `--settings` under `--setting-sources ''` both in print mode and in the interactive TUI a Herdr session runs. Outside Triage, Claude never runs with `--bare`, for an API key as for a native sign-in: `--bare` sets `CLAUDE_CODE_SIMPLE`, whose built-in set would offer only `Read` and `Edit` of the profile and leave an API-key run no way to find files. Without it, `--setting-sources ''` with `--restricted` still loads no `CLAUDE.md` from the workspace or the inputs. `test_pinned_claude_restricted_tools_and_structured_result_with_loopback_provider` proves all of this in print mode and in the TUI: the offered tools equal the profile, `Glob` lists `inputs/`, a write under `outputs/` succeeds, a write outside it and a read of `/home/job` are denied, and no `CLAUDE.md` text reaches the provider. For the operations it still runs (`version_recipe`, `audit_context`, `finding_artifacts`), Codex keeps its shell. It derives its native permission profile from `:workspace`, keeps sandbox network off except for `version_recipe`, denies tool reads of `/home/job`, and passes its shell only `PATH`, `HOME`, `NUMEN_FETCH_URL` and `NUMEN_FETCH_TOKEN`. Its `:workspace` sandbox can write anywhere under the `/workspace` tmpfs, though only `outputs/` is collected. Input mounts remain read-only in all policies. Codex alone uses a narrow Moby20.10.22-derived seccomp adjustment for nested native namespaces; other profiles use Engine default seccomp. Native-policy failures are explicit failures. Codex/Claude structured CLI output uses a fixed `result_json` string envelope, then validates the decoded object against the application schema; this supports application evidence objects without weakening validation or relying on a provider's unrestricted-object schema dialect.

## Interactive agent sessions (Herdr)

With `NUMEN_AGENT_BACKEND=herdr` (the Compose default on this branch) an agent workload other than Triage starts a private [Herdr](https://herdr.dev/docs/) 0.9.3 server inside its own container and runs the agent's interactive TUI in a Herdr pane instead of its print mode. Onboarding, workspace trust and API-key approval are pre-answered so startup is unattended. Every agent runs on the terminal's main screen so its conversation reaches scrollback: Claude Code with `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` (its default fullscreen renderer uses the alternate screen, which keeps no scrollback), Codex with `--no-alt-screen`, and Pi with `--tui-mode regular`. The agent writes its result to `/workspace/outputs/result.json`; the workload validates it against the application schema and finishes once the agent is quiet with a valid result. A quiet agent without one is reminded with the validation error up to three times, then the run fails. Every session operation can therefore write `outputs/`; input mounts stay read-only.

The operator reaches a session only through the broker: `GET /internal/runs/{id}/session` returns agent status, hold state, `live`, and the full saved native conversation/tool output plus the latest terminal view. The terminal view is read from Herdr with `format: "ansi"`, so it keeps the agent's own colors (SGR codes only). Herdr returns at most 1,000 lines per read and its visible screen is one viewport, so each 2-second session poll appends the lines that scrolled off screen to a saved scrollback (`.numen-scrollback.json`, matched by overlap so nothing repeats). The terminal view is that scrollback plus the current screen, up to 10,000 lines (the oldest 1,000 are dropped together, with a note); output that outruns one read between polls is marked as a gap. The Transcript keeps the full conversation regardless; settling compares the text without them, and credential redaction tolerates whitespace or escape sequences between a secret's characters. History has no dashboard row/byte cap. Pi session persistence is enabled for Herdr; Claude/Pi tool-output files use private fixed directories. A private per-run home volume survives workload exit and cancellation until the broker archives the redacted transcript under `NUMEN_RUNNER_STATE/sessions/`. Checkpoints are saved independently of browser polling. Reads after completion or broker restart use that retained archive; late live reads cannot overwrite the finalized history. An abrupt broker restart retains the last redacted checkpoint, and native tool truncation markers remain visible.

`POST /internal/runs/{id}/session` accepts `{action: "prompt", text}`, `{action: "keys", keys}`, `{action: "hold"}` or `{action: "release"}` for live sessions. Operations execute fixed commands as the unprivileged workload user. Post-exit history reads use a silent, network-isolated helper with only that run's home mounted read-only; raw transcript bytes travel through private exec stdout, never Docker logs. A held session never finishes on its own, including after a failure, until released or cancelled. `NUMEN_AGENT_BACKEND=native` restores one-shot print mode. Earlier output already discarded by an old session or by the native CLI cannot be reconstructed.

## Connections and native cache ingress

Pi catalogs come from the pinned SDK/provider extension and are intersected with the account's authenticated provider model list. Codex uses paginated native app-server `model/list`, plus API account model access for API-key mode. Claude uses the authenticated model endpoint. Effort values are retained from the runtime/provider metadata; unsupported selected models/efforts fail before inference. Missing usage is `null`.

Codex native setup uses `login --device-auth`. Claude native setup uses `claude auth login --claudeai` in its manual flow: the workload emits only the authorization URL, then waits for the operator's code. The worker relays the code to `POST /internal/runs/{id}/login-input`, which keeps it in broker memory only. The engine writes it into the workload's private home through exec stdin (never argv or environment), and the workload forwards it to the CLI's stdin. Command Code native setup runs the pinned plugin's `/login` through pi's `ModelRuntime.login` (`pi-commandcode-login.mjs`): it emits only the Studio URL, skips the localhost callback that cannot reach the container, and reads the pasted API key over the same login-input channel. The plugin validates the key with `/alpha/whoami`, pi stores it in its private `auth.json`, and later jobs pass it to the plugin as `COMMAND_CODE_API_KEY`. Login events contain only the native verification URI/device code and code-submission state. Pi native OAuth for other providers is explicitly unsupported by this runtime. Claude API keys and protected imported Claude native caches have separate execution paths. Actual account eligibility, OAuth model-endpoint access and native provider/proxy inference compatibility require operator credentials and remain unverified without them.

New/refreshed native caches use private ephemeral files and a fixed Engine exec transport inside the workload's mount namespace. The transport validates a bounded regular file and keeps its private response separate from Docker's main stdout/stderr logs. The broker retains the cache in memory for ten minutes after authoritative completion (kept available while cleanup is pending). A changed cache sets `credential_updated:true` in the ordinary run response, including failed native runs when refresh completed. The vault consumer fetches it with authenticated `GET /internal/runs/{id}/credential`, revision-fences encrypted ingestion, then deletes it with `DELETE` after commit. Ordinary `result`, outputs and events omit cache values. Plaintext temporary state is removed with the workload; broker restart never restores plaintext caches.

## Labs

Artifact upload does not build anything. The backend submits a `lab` run only after an Approval (the Operator's password, checked on that request), and the runner builds it through the broker on the host Engine (ADR-0005). The run needs `poc.py`, `report.md` and `vulnerable-app/Dockerfile` plus the application's own files, which may be a whole tree: the bundle travels as one compressed archive and is bounded by the expanded archive limits, not by a per-file count. For an Own-repository Proof the backend sends the Own repository at the Verdict's commit, read from its stored snapshot, under `vulnerable-app/` beneath the bundle's own files, which win, and without the repository's `.dockerignore`; the runner builds it like any other bundle. For an Upstream Proof whose link stands for npm packages at a Locked version (A07), the backend sends the Own repository at its default-branch head the same way, or, with no Own repository, a minimal `vulnerable-app/package.json` whose dependencies are those packages. It downloads each package's Locked version from `NUMEN_NPM_REGISTRY_URL` (only a tarball under that registry, at most 64 MiB, matching its sha512 `dist.integrity`), adds it as `vulnerable-app/.asset-monitor/<name>-<version>.tgz`, and points `package.json`, and `package-lock.json` when there is one, at it as `file:.asset-monitor/<name>-<version>.tgz`, the lock entry keeping the version and that integrity. Phase one then installs exactly those bytes with install scripts disabled, without fetching them, while the application's other dependencies still come from the registry. Without a package or a Locked version the Upstream bundle is sent alone. The backend sends no `lab` run whose tree holds a known Malicious change: an Upstream one its Application is exposed to, or an Own-repository Malicious change commit that the built revision reaches without its merged Cure revert. This is backend behaviour only; the runner builds the bundle it receives. Uploaded originals are preserved; unsupported bundles remain downloadable and unverified.

**Node only.** The only Lab stack in the first release is Node: a bundle without `vulnerable-app/package.json` fails with `lab_stack_unsupported` before any Engine call. The backend keeps such a bundle a Draft and refuses its Lab before an Approval, unless the Lab supplies that file.

**Phase one: dependencies** (`lab_dependencies` event). It runs before the build and inside its `build_seconds`. A fixed command, never the bundle's, runs in `asset-monitor-lab:0.1.0` with the bounded nonroot profile and the run's read-only inputs. It copies `vulnerable-app/`, drops any bundled `node_modules`, and runs `npm ci --ignore-scripts --no-audit --no-fund` when `package-lock.json` exists, otherwise `npm install --ignore-scripts --no-audit --no-fund`. The container sits on an internal `asset-monitor-lab-fetch-<run>` network. Its only way out is a per-run gateway whose CONNECT allowlist is the host of `NUMEN_NPM_REGISTRY_URL` (default `https://registry.npmjs.org`, https on port 443 only), whatever the Profile names. Its environment holds no credential, and `RunRequest` refuses a `lab` request whose Profile carries one. A nonzero exit fails with `lab_dependencies_failed`. The fetched `node_modules` (regular files, directories and symlinks only) joins the build context, bounded by `image_bytes`; the gateway, the fetch container and its volume are removed before the build. Runtime tests set the registry to `https://registry.invalid` and vendor `file:` tarballs, so no test reaches a registry.

**Phase two: offline build.** The Dockerfile is built as its own project, with `RUN`, multi-stage and continuations, and with no network (`network_mode none`): `RUN` steps run, but reach nothing. `FROM` may name only the bundled Lab base `asset-monitor-lab:0.1.0` (Debian bookworm, Python 3.12, pinned Node 24.9.0 and npm), `scratch` or an earlier stage, and `COPY --from` only an earlier stage: the Engine would fetch any other base outside the offline build and keep it after the run. A `COPY`/`ADD` source outside the bundle or given as a URL is refused, and so are build mounts and privileged build flags. The Dockerfile is read as the Engine reads it: a comment line is dropped before continuations are joined, so `# note \` never hides the next line, and parser directives (`# escape=`, `# syntax=`) and `$` variables in `FROM`, `COPY` and `ADD` are refused; the build gets exactly the instructions that were checked. The Lab base's global npmrc (`/usr/local/etc/npmrc`) sets `ignore-scripts=true`, so an `npm install`, `ci` or `rebuild` in a bundle's `RUN` or `CMD` skips dependency lifecycle scripts too, while `npm start` and `npm run` still work. A bundle that runs a dependency's script directly, `node node_modules/x/install.js` for example, still runs it, though with no network.

**Limits** (`LAB_MAXIMA`, ADR-0005). A build gets `build_seconds` (900, phase one included) even through a silent step: at the deadline or on cancel a watchdog kills the run's build-step containers and the build fails with `timeout`. A built image larger than `image_bytes` (4 GB, the Lab base layers included) fails with `lab_image_too_large`. The run gets `timeout_seconds` (600), which starts after the build and covers the application's startup and the PoC. The sent Dockerfile carries a `LABEL` with the run's labels after every `FROM`, so every layer and build-step container of the build carries them, and the run's cleanup removes a failed or interrupted build's intermediate layers as well as its image. A Lab over any limit therefore fails visibly and leaves no image behind.

**Run.** The application then starts at `http://application:8080` with a writable root filesystem, its image's own user and an ordinary capability set, on the run's internal Lab network (`numen-job-<run>`) only: like its PoC verifier, it has no route out, no DNS beyond the run's own containers, and no route to the application or control networks. Neither receives a provider or application credential. The PoC reads `TARGET_URL`. Observed results retain the built image digest, exit code and bounded log. A nonzero PoC is `status:not_reproduced, verified:false`; successful recording of that result never means successful reproduction. Every run, and every cancel, timeout or restart, removes owned containers, volumes, networks and job images, intermediate layers included. A failed cleanup keeps the run nonterminal (`cancelling`, `cleanup_pending`), preserves its pending result/error privately, retries reconciliation, and blocks new execution with503. A terminal status is published only after actual owned-resource cleanup succeeds. Interrupted work cannot falsely succeed or claim it stopped while Engine availability is unknown. Authenticated `GET /internal/attempts/{attempt_token}` resolves lost submit acknowledgements; explicit `{run_id:null,status:"absent",reconciled:true}` is returned only after reconciliation, while503/404 cannot prove absence.

## Detection rules

A Malicious change is never run: its Proof is static (A07). The `detection_rule` kind validates its Detection rule with yara 4.2.3 (Debian bookworm package `yara=4.2.3-4`, pinned in `Dockerfile.runner` and checked with `yara --version` at build). Only the probe image, in which the kind runs, and the runner test image carry yara; the Lab, broker, gateway and agent images do not. The backend sends `rule.yar` and up to three trees, each as one archive input: `changed` (the commit's changed files), `parent` (the parent tree) and `baseline` (the Baseline tree, left out for a Backfill commit). The trees are staged read-only like any other input.

The job container has `network_mode none` (no gateway, no proxy variables, no job network), no credential (`RunRequest` refuses one) and no Docker socket. Its ceiling is `RULE_MAXIMA`: 600 s, 1024 MB, 2 CPUs, 64 pids, 8 MB of output and 256 MB of input; callers may only lower it. Only `yarac` and `yara` run: yara reads the scanned files as bytes, and nothing in a tree is executed, installed, imported or rendered. A rule that uses `include` (it reads other files) or imports the `console` module (it prints lines a match would print, even through a comment or `\xHH` escapes) is refused before compiling. A rule that does not compile returns `{compiled: false, error}` with yarac's first 500 characters of error. Otherwise each tree sent is scanned with `yara --compiled-rules --recursive --no-follow-symlinks --no-warnings --threads=4 --timeout=60`, and the result is `{compiled: true, error: null, matches: {<tree>: {files, count}}}`, with paths relative to their tree, at most 1000 files listed and `count` the full number. A tree that was not sent has no entry. A scan error fails the run with `Detection rule scan failed`: yara reports a file it could not read or that timed out on stderr and still exits 0, and that must never read as "no match". The broker cleans up the run's containers, volume and network like any other run's.
