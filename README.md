# Numen

An authenticated, Docker-hosted dashboard for monitoring deployed software, upstream security changes, CVEs, and reproducible findings.

The application includes a React/TypeScript UI, FastAPI backend, PostgreSQL persistence and job queue, a scheduler/worker, and isolated Pi, Claude Code, Codex, Python probe, and lab containers.

## Start

Install Docker Engine/Desktop with Compose. No host Python, Node, or agent installation is required.

```sh
./scripts/init.sh
./scripts/compose.sh --profile images build
./scripts/compose.sh up -d --wait app worker scheduler runner-broker fetch-gateway
./scripts/compose.sh --profile setup run --rm bootstrap-operator
```

`make up` runs those steps together when Make is available.

Open **http://localhost:8788**. The operator is **admin**. Read the generated password locally:

```sh
cat .numen/bootstrap-password
```

Setup creates random credentials in protected `.env` and `.numen/bootstrap-password` files. It preserves existing configuration. Docker Desktop on macOS is detected even when its CLI and credential helper are absent from PATH. Ports are bound to loopback; database and broker ports are internal.

To reset the operator password interactively and revoke existing sessions:

```sh
make reset-password
```

## Use

1. **Settings → Accounts:** connect the providers you use. Pi supports DeepSeek, Command Code through the bundled provider plugin (API key, native login, or auth.json import), OpenAI, and Claude API connections. Codex supports OpenAI API-key access, eligible device login, or protected native-session import. Claude supports API keys, subscription native login, or protected native-session import. Run the connection check to discover account-compatible models and supported effort levels. Add a `github` account with a fine-grained, read-only token (Contents and Metadata): GitHub repositories are not polled without it, and show `github_token_required` until one is added. To let Asset Monitor open Remediation PRs, add a separate `github_write` account (Settings → Integrations, "GitHub write token (Remediation PRs)") with a fine-grained token (`github_pat_…`; a classic token is refused) limited to the Own repositories, with Contents and Pull requests: read and write. It is used by the step that opens Remediation PRs, by the poll that reads an open Remediation PR's state (a read-only token cannot read pull requests), and by its connection check; it never lists commits or snapshots a repository, and never reaches an agent run.
2. **Settings → Defaults:** choose the global monitoring interval (in minutes, hours or days, at least 5 minutes; `NUMEN_MONITOR_INTERVAL_DAYS` seeds it in days on a new database) and agent/account/model/effort profiles for audit context, version recipes, commit/CVE analysis, finding generation, and patch drafting (Remediation PRs; Pi or Claude Code, never Codex, and an API-key account for automatic drafts: there is no fallback, so without one an automatic patch draft fails with the reason). Model catalogs are separate for each runtime. Jev has its own optional typed-triage connection.
3. **Applications → Insert application:** enter the asset URL and software identity, polling interval (at least 5 minutes), and optional CVE selectors/score criteria. The default interval is seven days and can be changed. Then open the Application's **Repositories** tab and link its repositories: at most one Own repository on GitHub (remove it to replace it; an Application may have none), and any number of Upstream repositories added by hand, a GitHub URL or a WordPress.org plugin slug, each with an optional Locked version. The tab lists each Upstream repository with its packages, its on/off switch, its Locked version (editable, with where it came from: Manifest, Operator or Deployed), its status (Watching, Off, Removed or Error, plus its Release branch, "Release branch pending" or "release branch unknown"), its last check and a Backfill action, and it lists the packages that could not be resolved. The API is `POST/PATCH/DELETE /api/applications/{id}/repositories` (see `docs/implementation-contract.md`). An Upstream GitHub repository also watches the Release branch of its Locked version (`{major}.x`, `{major}.{minor}`, `release-{major}` or `v{major}`, the first that exists); with none it watches the default branch only and reports `release_branch_status: "unknown"` (release branch unknown). A repository is stored once per URL, so Applications that share one are polled and triaged once. With an Own repository, its direct dependencies (`package.json` and `composer.json`, versions from `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock` or `composer.lock`) are mapped to their GitHub repositories through npm or Packagist metadata and linked as Upstream repositories after its Baseline: all on the first time, later additions off. A commit that changes a manifest or lockfile derives them again; a dependency that is gone is marked removed and keeps its history, and a package with no GitHub source is listed in `unresolved_dependencies`. WordPress release monitoring works without GitHub.
4. **Application detail:** Check now checks every linked repository that is on, generate/reuse version recipes, build audit context with the pinned Trail of Bits skill, and inspect CVEs/findings. A repository's first check sets its Baseline at the head and imports no history; later checks import the revisions after it, and an unchanged GitHub repository answers `304` and creates nothing. To triage earlier commits, use Backfill on the Repositories tab to import and triage the last N (1–100, default 20) up to the Baseline (`POST /api/applications/{id}/repositories/{repository_id}/backfills`). Each imported commit records its Pre-filter flags (dependency manifests, `package.json` scripts, CI workflows, minified or obfuscated code, authentication and cryptography paths). Manual checks work while scheduled monitoring is paused.
5. **Commit review:** choose an Application to review its security queue. Triage (Jev, Pi or Claude Code; never Codex, which has no way to run without a shell) is one call with no tools and a 120-second deadline that decides whether a change deserves Analysis and gives a short reason and a potential-issue title. Application code checks the reply; a reply that fails the check is recorded as failed and retried twice, never read as unrelated, and each run is kept as a Transcript. Complete non-security changes are dismissed. A change Triage flags (security candidate or insufficient context) is analysed automatically, once per commit, so a commit of an Upstream repository several Applications share is analysed once. Automatic Analysis is capped at 10 runs per Application and 30 per Provider account each UTC day (a shared Upstream commit counts only against the account); a change over a cap waits as "waiting for cap" and starts, oldest first, after the caps reset at 00:00 UTC. Automated runs (Triage, automatic Analysis and CVE analysis, audit refresh) use only Provider accounts that hold an API key and are refused with the reason otherwise; Analyze by hand works at a cap and with a subscription sign-in. Analysis runs are read-only (Pi or Claude Code; Codex is refused for Analysis and CVE analysis, because it always has a shell): the agent reads the pinned revision's source snapshot and the diff, writes only its outputs, builds and runs nothing, and returns one Verdict with a confidence (low, medium or high): Vulnerability fix, Vulnerability introduced, Malicious change, Security hardening, Unrelated, or Insufficient context, which puts the change in the dashboard's Review queue. A Vulnerability fix, Vulnerability introduced or Malicious change Verdict opens one Finding in each Application that uses the repository as its Own repository, and in each that uses it as an Upstream repository and is exposed: its Locked version's release tag contains the commit (or a backport of it with the same patch-id on a watched branch), or, for a Vulnerability fix, does not, or no release contains the fix yet. A Locked version with no matching tag (`v{version}`, `{version}` or `{package}@{version}`), or tags that cannot be read, is unknown and counts as exposed; a not-exposed Application gets no Finding or Alert until a Locked version change (a lockfile re-derivation or an Operator edit), a new link, turning its link on or restoring the archived Application exposes it, which opens its Finding then (a change to not exposed leaves its Findings as they are), and the commit page lists each Application's Exposure with its reason, and a change is linked to that Application's Findings it addresses (a Vulnerability fix linked that way opens no Finding of its own); a repeat Analysis never opens a second Finding or reopens a Dismissed one. A Vulnerability fix or Vulnerability introduced Finding gets a report, Python PoC, and draft vulnerable application bundle that only a Lab run builds; a Malicious change Finding gets a static Proof instead, never run and a draft until its Detection rule validates: the drafted Detection rule, the indicators application code found in the change (each file with its hash), and a cleanup report listing the commits and releases that contained the change (from tag containment, as for Exposure) and the secrets to rotate, which is never sent anywhere. Analysis has a 30-minute deadline: one that expires leaves the change pending with a visible timeout, never Unrelated. The commit list shows each change's Verdict with its confidence (unknown for Verdicts carried over from Numen) or where its Analysis stands (queued, waiting for cap, timed out after 30 minutes, blocked or failed with the reason), and its Pre-filter flags beside the Triage result, also when Triage rejected the change; filter by Verdict, or choose Show → Review queue. Each change links to the Findings it opened or was linked to, in every Application; Confirm revision records the commit review decision and leaves the Finding lifecycle alone. Saved runs, job links and immutable downloads remain available; independent lab verification is tracked on the finding. When the Application has an Own repository and the change is one of its commits, the Verdict also drafts a Remediation PR on it: a Vulnerability introduced gets a patch, drafted by a one-shot agent run (20-minute deadline, the same read-only tools as Analysis, writing only its diff) that counts against the same caps and waits over one; a Malicious change gets a revert (the Cure's), written by application code, which fails rather than revert only part of a commit that also changed binary media or symlinks; a Vulnerability fix gets none, since reverting it would bring the vulnerability back. An exposed Upstream Verdict drafts a dependency pin or bump in application code, once Exposure knows the release to move to: a Vulnerability introduced or Malicious change pins the newest release tag that does not contain the change (by tag containment and tag date, never semantic version), and a Vulnerability fix bumps to the first release tag that contains it, waiting ("Waiting for a release that contains the fix") until one is tagged and a source check sees a new commit. It edits the Own repository's `package.json` and `package-lock.json` (or `composer.json`) for each package the Upstream link stands for, so a hand-added link, which names none, gets no pin or bump. Each Finding's Playbook panel lists the steps of its Verdict's cell (A06) and where each stands; a step that needs your Approval reads "Waiting for your Approval" and blocks no other. On an Own repository, a Vulnerability introduced gets a Proof, a report and a patch; a Malicious change the static Proof, Detection rule, cleanup report and revert (the Cure); a Vulnerability fix a report and the Deployed version check. On an exposed Upstream repository, a Vulnerability introduced gets a Proof, a Disclosure report and a pin; a Malicious change the static Proof, Detection rule, cleanup report and a pin to a release without it; a Vulnerability fix an n-day Proof and a bump once a release contains it. A Finding you open by hand on a commit with no Verdict keeps every step. An Own-repository Vulnerability fix gets a report and a Deployed version check, and no Lab: each version check, and the Analysis that opens the Finding, compares the detected version's release tag in the Own repository with the fix and reports "Still serving code from before the fix", "Serving the fix" (which moves the Finding to Remediated) or "Unknown" with its reason, never a guess. An Upstream Vulnerability introduced Finding shows the Disclosure report the Analysis drafted for the Upstream repository's maintainers, as text with a copy button and a link to the repository's GitHub private vulnerability reporting form; Asset Monitor never sends it. Application code checks every drafted diff with `git apply` against the default-branch head and refuses one that does not apply or touches a path outside the repository, `.git`, or `.github/workflows` (unless the revert or a flagged patch is that fix); a refused draft shows why, with no diff to approve. The draft kept is git's own diff of the result, with its SHA-256; the Approval screen shows any bidirectional or zero-width character in it as a visible `⟨U+…⟩` escape. Approving a ready draft takes your password and the SHA-256 of the diff you reviewed (a draft that changed since is refused). Asset Monitor then opens one **draft** pull request on the Own repository (against its configured branch, else its default branch), refusing a file GitHub holds differently from the snapshot the diff was checked against (a `.gitattributes` export rule), on the branch `asset-monitor/<short-sha>-<action>`, from exactly that diff, with the write token. Approving twice, or a worker that crashed halfway, still opens one pull request. Without the write token the step fails visibly on that draft and nothing else on the Finding changes. Asset Monitor never merges, never pushes to a default branch and never writes to an Upstream repository. You merge it: when a check of the Own repository imports the pull request's merge commit (or its squash or last rebased commit) from the default branch, the Finding becomes Remediated with the pull request as its cause. Closing it without merging changes nothing on the Finding. Checks read the pull request's state with the write token; without it the check still runs and the draft shows the error. Without an Own repository the Remediation PR steps show "no Own repository" and are skipped.
6. **CVEs:** configure selected CVSS versions and an inclusive minimum Base score. Product matches, score eligibility, and deployed-version applicability are separate. Unscored, v2-only, below-threshold, and unconfirmed records cannot bypass the analysis gate. Analysis reads the newest release the record still reports as affected, resolved to that release tag's commit, because the monitored checkout already contains the fix; ranking releases requires an Application version scheme, and the launch dialog accepts an explicit revision when a record cannot be ranked. CVE analysis is read-only like commit Analysis: it reads the pinned source snapshot, has no Docker daemon or package-registry access, and drafts its bundle without building it. Analysis generates a linked finding with a report, Python PoC, and pinned vulnerable Docker bundle draft; success requires a complete bundle. Incomplete generation fails with its report and draft files retained. Jobs and analysis history link to the report and finding artifacts.
7. **Findings:** each Finding has a source (commit, served content, advisory, or a CVE carried over from Numen) and moves from Open to Confirmed or Dismissed, and from Open or Confirmed to Remediated, recording what moved it; the Operator can Confirm, Dismiss or Mark remediated with a reason, and a reproduced Lab Proof or a validated Detection rule confirms it. Upload or generate `poc.py`, `report.md`, and a pinned `vulnerable-app/` Docker bundle. Download the integrity manifest and artifacts, except for an Upstream Finding: its Proof (its bundle, Analysis, PoC, Lab output and every other file but `report.md` and `disclosure-report.md`) is never exported (A15), so its page offers no download and previews only its reports. **Start Lab** is an Approval: it asks for your password and checks it on that request alone, with no re-authentication window, so a missing or wrong password is refused even straight after another Approval. It then builds the bundle in an offline Node Lab (below): a Proof that reproduces confirms the Finding, and one that does not stays visible as Not reproduced and changes nothing. A Lab is never retried; start a new one, with a new Approval. A Malicious change Finding is never run, so it has no Lab and no Generate. Its page shows, as text, the static Proof (the Detection rule, the indicators with each file's hash, the values application code rejected, and each validation check with the files it matched) and the cleanup report (the files and indicators the change added, the commits and releases that contained it, the secrets to rotate and the Detection rule to run on the server). Each new static Proof revision is validated by a `detection_rule` job (below): the rule must match at least one file the commit added or changed and no file in its parent tree, nor, for a commit after the Baseline, in the Baseline tree; a Backfill commit is checked against its parent tree only. A validated rule confirms the Finding. One that fails keeps the artifacts Draft, names the failed check and leaves the state as it was; re-draft it by analysing the commit again or uploading a corrected `detection-rule.yar`, which is validated in turn. The Finding page's **Remediation PRs** panel is the Approval screen (A08): each draft shows its action, status, summary and, when a step failed, the reason (such as a missing write token or a failed pull-request read); a warning when it changes `.github/workflows`; its base revision, branch and pull request link; and its diff as plain text with its full SHA-256, exactly as it will be pushed. **Approve** (on a ready draft, or again after a failed PR step) opens the same password dialog as Start Lab and sends that SHA-256 with your password, so a draft that changed since is refused. **Draft patch** and **Draft revert** draft one by hand, for example again after a failed draft; neither drafts nor PR steps are retried from Jobs. Without an Own repository the panel reads "No Own repository: Remediation PR steps are skipped." The Finding page lists its history (opened, linked changes, state changes each with its cause, Approvals, and Remediation PRs opened and merged) and shows the Deployed version apart from the state: a linked fix does not by itself make a Finding Remediated, and Draft only means its artifacts are incomplete. Opening a Finding, and reaching a cap, sends an Alert to the Discord webhook (Settings → Discord; Send test Alert checks it). An Alert carries only the Application or Provider account, the source (short SHA, Watched page or advisory id), the Verdict and confidence (or Advisory, or Cap reached) and a dashboard link, with mentions disabled; nothing else sends one, including a Finding you create by hand.

Secrets are write-only. Native session import accepts a bounded JSON file without previewing credentials. Native login availability depends on the runtime/account. Codex uses its device flow. Claude login shows the sign-in link, then you paste the authorization code from the page into the login dialog. Command Code login runs the bundled plugin's own login: open the Studio link, then paste the API key Studio shows. Pasted input is relayed to the isolated login process and is never shown in job events. Pi native login for other providers is not implemented. No host credential directory is mounted automatically.

Version recipes preserve ambiguous/unknown results and reuse Python without another generation call. Audit context retains its source/skill revisions, supporting function documents, partial coverage, and stale state. Jobs expose progress, errors, cancellation, and fenced recovery. Markdown reports and relative supporting-document links open inside the application.

## Runtime and reproduction

Only the trusted broker receives Docker Engine control. Workloads run non-root with resource limits, isolated networks, time limits for probe, Lab, Detection rule and login runs, Triage (120 seconds), and Analysis, CVE analysis and audit function analyses (30 minutes; other agent runs continue until finished or cancelled), read-only inputs, and scoped provider/target access: an agent run reaches only its provider's hosts, plus `herdr.dev` when it hosts a Herdr session. Tool access is fixed per operation and never includes Docker. Native Codex sandboxing is retained, with a narrow namespace policy required by Docker's default syscall restrictions. See [runtime details](runner/README.md).

A Lab builds a Proof bundle as its own project on the host Engine, in two phases. Phase one fetches the Node app's dependencies from `package.json` and `package-lock.json` with install scripts disabled, no credential, and egress only to the npm registry. Phase two builds the ordinary Dockerfile (`RUN` and multi-stage included) with no network, on the bundled Lab base `asset-monitor-lab:0.1.0` only (pinned Node 24.9.0, npm set to skip install scripts), and runs the app and the PoC on an internal Lab network with no route out and none to the application network. For an Own-repository Proof the app is the Own repository at the Verdict's commit. For an Upstream Proof it is the Own repository at its default-branch head, or, with no Own repository, a minimal app, with the Locked version installed: Asset Monitor downloads each package the Upstream link stands for at its Locked version from the npm registry it reads, checks the tarball's origin and sha512 integrity, and pins exactly those bytes as a `file:` dependency, so a tarball that does not match fails the Lab before it starts; an Upstream link with no package or no Locked version keeps a bundle-only Lab. The Analysis drafts one bundle, for the Own repository at its commit or for a minimal app, and only the Applications whose Lab builds that app get it; another one, such as an Application with an Own repository whose Upstream Proof builds its head, gets the reports and a Draft, and an automatic bundle draft for its own app, which counts against the Analysis caps (over a cap, or without an API-key profile, **Generate** drafts it); a regenerated bundle keeps the Disclosure report. Node is the only Lab stack: a bundle without `vulnerable-app/package.json` that its Lab does not supply stays a Draft and its Lab is refused before any Approval. A Lab is refused while its tree would hold a known Malicious change: an Upstream one the Application is exposed to (or whose Exposure is unknown or not computed yet), or a Malicious change commit the Own repository's tree reaches, until the Cure's revert Remediation PR is merged into that tree (a revert by hand keeps Labs refused). Each Lab image is at most 4 GB, a build gets 15 minutes and a run 10, and every Lab's images and containers are removed after its run, so a Lab over a limit fails visibly and leaves no image behind. Original unsupported bundles remain downloadable (an Upstream Proof never is) and unverified; they are never silently changed or reported as reproduced.

A Malicious change is never run. Its Detection rule is validated by a `detection_rule` job in the probe image, which carries a pinned yara 4.2.3: no network, no credential and no Docker socket, the commit's changed files, parent tree and Baseline tree mounted read-only, and only `yarac` and `yara` run, reading every file as bytes. A rule that uses `include` or the `console` module is refused, and a scan error fails the job instead of reading as no match.

Configure your own accounts before running paid agent work. Development verification uses controlled fixtures and credential-free native CLI checks; authenticated provider inference and account-specific entitlements require connection checks with your credentials.

## Checks

All normal check entrypoints run inside Docker:

```sh
make check
make test-unit
make test-integration
make test-runtime
make test-ui
make test-journey
```

`test-runtime` explicitly enables actual Docker Engine cases. `test-integration` includes PostgreSQL claims, fencing, persistence, source/CVE workflows, and native-cache handling. Named `CASE` values are validated; unknown cases and empty pytest selections fail.

The journey uses an isolated `asset-monitor-test` project at http://localhost:18788, with real HTTP/SVN source fixtures, a fixture npm registry and captured webhook delivery. It makes no authenticated inference or production-target requests. Its React2Shell case links an Own Node app that locks a harmless stand-in of `react-server-dom-webpack@19.0.0` (a crafted field returns a marker; nothing runs), shows the Upstream Finding's Disclosure report, refuses its downloads, reproduces it in a Lab on the real Engine after an Approval, and shows the fixed 19.0.1 stand-in as Not reproduced. Stop that test stack afterward:

```sh
./scripts/compose.sh -p asset-monitor-test -f compose.yaml -f compose.test.yaml down
```

## Backup and restore

`make backup` briefly pauses application writers and creates a consistent database/artifact/credential-key set under `.numen/backups/`. Preserve the full private set, including `deployment.env`.

```sh
make backup
make restore BACKUP=.numen/backups/<timestamp>
```

Restore replaces the application database and artifacts with the chosen backup. It validates the backup and matching database credentials first. For a fresh deployment, restore its `deployment.env` as `.env` before creating the new project's empty database volume. Use the operator password associated with that backup, or reset it through the container command.

`make down` stops the main stack while keeping its volumes. `make logs` shows recent service output. Use `NUMEN_PORT` and `NUMEN_DASHBOARD_URL` in `.env` to change the local address.
